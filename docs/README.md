# AgentLilaraCode

轴插件第一批的注册方式、兼容策略与验证边界见 [07-轴插件接入.md](07-轴插件接入.md)。

## 是什么

一个**轻量但好用**的 agent 程序。与 AgentLilaraProject（下称 ALP）不是同一生态位——ALP 是重型服务器、功能高度内聚；本项目注重分离设计。

核心是**无头常驻进程**，类似 Claude Code 的典型 agent，但**没有头**：头是独立的 UI 程序，通过 HTTP/WS 与控制核心连接。核心不关心头在不在看。

## 硬约束

- **头 = 纯观察者 + 命令源**。核心不关心头在不在。
- **核心无头到底，但自带控制台**。常驻进程附着一条命令面（标准输入），可手动控制核心——逼急了当**纯手动头**用。⚠️ **它不是头**：同步收发，**没有视图**（[`04` §1.1](04-插件与内部结构.md)）。⚠️ 措辞：核心**进程形态**是"控制台程序"，它附着的那条**结构**叫「命令面」，两者不与「控制面」并列。
- **核心是本设备（至少本用户）唯一的**，避免竞争。核心管理全部会话资源。⚠️ 推论：**控制台天然独占**——不存在"第二个控制台来抢"。
- ⚠️ **核心启动后默认没有任何会话**。「配置提供商 → 自动建初始会话」是**头的行为**（策略），不是核心的（机制）——核心只认 `session.create` 命令（[`01` §8.1](01-会话设计.md)）。
- **单核心多会话**。
- **无头也能自跑**（自主续跑 / 会话持久与恢复 / 定时任务）。
- 技术栈：**.NET 10**。

## 与 ALP 的关系

**简化借鉴**：借设计思路，不搬引擎生态（弃 `MasterEngine + ISubEngine + SpawnCheck + 资源池`）。

| 借 | 弃 |
|---|---|
| 统一会话模型（不分子类） | SessionPool / claim / escalate（QQ 频道场景雕刻） |
| spec / state / history 三件套分离 | 三件套的内容（ALP 存真消息，本项目存骨架） |
| 工具契约（执行 / 渲染 / 优化 / 取消四钩子） | **「显式结束循环」** —— ⚠️ 本项目**不需要**：循环的停止条件是**主动性轴**，是核心的预设值，不是某个插件提供的 |
| session 管执行、core 管模型 | MailboxInputPort + `report_to_parent` 两套机制 |
| 父子链、depth 概念 | 30s 心跳循环 |
| —— | **ALP 意义上的「内置工具」** —— ⚠️ 本项目**核心不提供「内容」**：`bash` / 联网 / 装包这类**干活的能力**全部来自插件（[`04` §1.3](04-插件与内部结构.md)）。⚠️ **但核心自带 7 个「机制入口」**（`ls` / `read` / `update` / `write` / `fetch` / `ask` / `release`）——它们开的是**工作目录 / 历史 / 上下文**那三扇门，不是能力。那条修正与清单见 [`04` §1.3](04-插件与内部结构.md)，**别只读这一行** |

> ALP 的 session 有三重身份纠缠：**执行容器 / 频道占用单元 / 上下文构建者**。占用是场景强加的，本项目剥离。
>
> ⚠️ **引以为戒**：ALP 的端口模型在演进中已漂移（架构图说"输出端口决定工具注册"，`channel-connection-tools.md` 却说输出不走 OutputPort）。原因是**端口与消息分发耦合后长出了权重、订阅、子流**。本项目的端口必须更窄。

## 与 ApiPlan 的关系

ApiPlan 提供**多模型来源兼容能力**：以 canonical 中间语言双向转换三种协议（OpenAI Chat / OpenAI Responses / Claude Messages）。

**只借结构，不借职能**：
- 借：块类型划分（text / image / tool_call / tool_result / reasoning）、快照结构（SystemBlocks + Items）
- 弃：`ClientProtocol`、`RawJson` 兜底等**代理期概念**（本项目 canonical 是会话母语，不存在"还圆给谁"）
- 弃：计费、降级、路由——**那是中转站的职责**
