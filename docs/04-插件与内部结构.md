# 插件与内部结构

> 本文是**核心的内部组成**与**插件契约**——两者强耦合，一处处置。
> 会话本体见 [`01-会话设计.md`](01-会话设计.md)，调度见 [`02-多会话调度.md`](02-多会话调度.md)，接口见 [`03-控制面协议.md`](03-控制面协议.md)。

---

## 1. 内部结构

```
核心
├─ 注册表        provider / 项目 / 会话（索引，只读为主）
├─ 插件宿主      加载 · 收集贡献 · 分发钩子          ← 本文
├─ 资源管理器    声明 / FIFO / 解除阻塞              ← 01 §12
├─ 步调度器      决定下一个推进谁                    ← 02
├─ 推进器        渲染 → 调用 → 执行 → 落盘           ← 01 §3–§6
├─ 协议适配器    **内建，焊死**（Claude / OpenAI ×2） ← §1.2
└─ 控制面        WS + HTTP（头 · 控制台）            ← 03 / §1.1
```

**插件宿主是唯一的耦合点**：它收集全部贡献，各组件**从收集结果里读自己那一份**——调度器读驱动源，推进器读工具表与提示词，控制面读控制点。

> **没有任何组件直接认识插件。** 这是「知识与责任同处」（[`00` §1.3](00-设计哲学.md)）在结构上的样子。

### 1.1 控制台：控制面的第二个客户端

核心是**常驻的控制台程序**：附着一条命令面（标准输入），**启动即进交互循环，直到显式退出**——不是"跑完参数就退"的一次性工具。

⚠️ **它是控制面的一个客户端——与头同一个面，不是第三个面。**

```
核心
├─ 控制面        WS + HTTP
│    ├─ 头       观察者 + 命令源
│    └─ 控制台   只有命令源（stdin 是它的入口）      ← 本节
└─ 插件宿主                                        ← §2–§7
```

**它不是独立的面**，因为**控制台从不直连核心内部**——它把命令喂进控制面的通道，与头**走同一条路、同一套命令集、同一个回执**。所以：

| | 约束 | 由什么保证 |
|---|---|---|
| **不是头** | **没有视图**：同步收发（问 → 答 → 完），**绝不订阅、绝不流式渲染** | ⚠️ **一张没有状态的地方，挂不住视图**——结构性，非纪律性 |
| **不是一次性工具** | 常驻交互 | 它就是进程本身 |
| **不新增鉴权面** | 本机进程即可信（[`03` §10](03-控制面协议.md)） | 同一个信任模型 |
| **不新增并发面** | **控制台天然独占**：核心本设备唯一（[`README`](README.md)）⇒ 不存在第二个控制台 | 母约束的推论 |

**"命令投递即返回"在本地退化成"同步拿回执"** —— 投递与返回都是内存操作，所以交互体验是 RPC 式的，**而协议语义一点没变**。这是 [`03` §3](03-控制面协议.md) 那个设计的一次免费兑现：正因为核心不等结果，多一个客户端不需要任何新机制。

⚠️ **命令的语义与头共用同一份**（[`03` §3](03-控制面协议.md) 的命令 + [`03` §6](03-控制面协议.md) 的快照查询）——⚠️ **但它不是「不多一条」**：控制台另有**本地**的 `quit` / `exit`（退出循环是进程的事，头没有这条），以及 `history` / `status` / `claim list` 这类**快照查询**（[`03` §6](03-控制面协议.md)，不是命令）；`claim.acquire` 有控制台文本（`claim <路径>`）却**不在 §3 表里**——§3 资源那节只列 `release`（头从不发 acquire）。反过来，§3 表里也有几条控制台**没有文本形态**（`session.start` · `session.deactivate` · `approval.respond` · `project.setConfig` · `tool.setEnabled`）。

**控制台最常被用到的三类：**

| 用途 | 命令 |
|---|---|
| **当纯手动头用** | `session.send`（塞消息）· `session.start`（启动循环）· `session.activate` + 快照 HTTP（**检查消息**——读走快照，不走订阅） |
| **止血**（比头更常被用到） | `session.interrupt` · `approval.respond` · `claim.release`（**本就是"模型失控时的逃生口"**） |
| **引导**（无头时唯一入口） | `provider.upsert` · `session.create` |

> **「核心不关心头在不在」推到底 ⇒ 核心不该关心控制台在不在，也不该依赖它在。**
> ⚠️ 反过来说：控制台**关掉不影响任何东西**，核心照常自跑（[`README`](README.md) 硬约束「无头也能自跑」）。

### 1.2 协议适配器：焊死在代码里，不做插件

> **它是核心的一部分，跟协议走，不跟用户走。**

| | 理由 |
|---|---|
| **收益极低** | 一时半会就这仨协议（Claude Messages / OpenAI Chat / OpenAI Responses），**没有拓展需求** |
| **且是核心能力** | 做成可卸载的插件，等于把"能跑"变成可选项——**装错一个插件能让 agent 失联** |

⚠️ **与「MCP = 适配器插件」不矛盾，是镜像的两端**（[`00` §5](00-设计哲学.md)、§4）：

| | 方向 | 归属 |
|---|---|---|
| **上游协议适配器** | 出（canonical → Claude / OpenAI） | **内建**（本设备必备能力） |
| **MCP 适配器插件** | 入（MCP server → 我们的插件契约） | **插件**（引入外部能力） |

**一出一入，一个焊死一个外挂**——因为**出去的协议是产品的形状，进来的能力是用户的形状**。前者不该可换，后者必须可换。

### 1.3 核心是空壳：内容全由插件提供

> **核心提供机制与装配位；插件提供全部内容。**（[`00` §1.3](00-设计哲学.md) 机制与策略分离）

⚠️ **修正一个曾有的设想**：曾考虑让核心自带「最核心的插件」（内置工具 + 系统提示词）。**不做。**

| | 核心自带 | 由插件提供 |
|---|---|---|
| 提示词内容 | ❌ | ✅ **含系统提示词** |
| 工具 | ❌ **一个都没有** | ✅ 全部 |
| 装配位与装配机制 | ✅ | —— |
| 协议适配器 | ✅（§1.2） | —— |

**三条推论**：

1. ⚠️ **「没有任何插件」是完全合法的形态** —— 那就是**纯 chat**。而**裸核心连系统提示词都没有**——块数恒定说的是「最多各 1 块」，**不是说一定非有不可**。没有贡献者就没有块，这和"多个插件的贡献必须合并成 1 块"是同一件事的两头。
2. **ALP 需要显式结束循环，本项目不需要** —— 循环的停止条件是**主动性轴**（[`01` §3.5](01-会话设计.md)），是**核心的**预设值，**不是某个插件提供的**。所以拿掉插件不会让循环失控。
3. **`spec.json` 是唯一必须非空的东西** —— 会话至少要能回答"这一步是哪个模型跑的"（[`01` §7.2](01-会话设计.md)）。插件清单可以是空的，provider 不行。

⚠️ **由此，「核心自带哪些工具」这个悬而未决的问题消失了** —— 答案是没有。 [`01` §9](01-会话设计.md) 的「内置工具」一词**随之作废**。

⚠️ **修正（2026-10-06 最小工具批）——「零个工具」要拆成两半读，因为核心现在确实带了工具**：

| 那句话说的是什么 | 成立吗 |
|---|---|
| **核心不提供「内容」**——`read` / `write` / `bash` 这类**干活的能力**全归插件 | ⚠️ **2026-10-23 起这一条要重读**：`read` / `write` 早已是内建（它们是**机制**入口，见下表），而 `shell` 是**第一个越过这条线的内建**——它提供的正是「干活的能力」。判据变了，写清楚：**用户裁定 shell 属于核心**（每台机器上都该有、且要过核心的闸门），它落在**高危**类，边界只有权限轴与设备开关。`bash` 这个词在本仓库里从此指 `shell` 那个工具，不再是「插件才可以提供的东西」 |
| 「关键词**零个**」 | ⚠️ **不再字面成立**：核心带了 16 个（见下） |

**判据是「内容 vs 机制」**（`00` §1.3 机制与策略分离）：它们不是「干活的能力」，是
**核心的加载 / 渲染机制的入口**——没有它们，工作目录与历史这两个概念对模型不存在。
它们住在 `Session/Tools/BuiltInTools.cs`（**装配点**），**不可卸载**——判据同 §1.2 给协议适配器的
那一条（做成可卸载的等于把「能跑」变成可选项）。

⚠️ **内建工具的清单**——**判据是数 `BuiltInTools.All`**（今天 **22** 个）。⚠️ 这张表长期没跟上网联批与压缩批（原文写「十六个」，当时实际已经是十九个），2026-10-22 一并补上；2026-10-23 加 `shell`：

| 工具 | 类别 | 它开的是哪扇门 |
|---|---|---|
| `ls` · `read` · `search` | 只读 | **工作目录**：周围有什么 / 这一个是什么 / 这一片里哪里有它（2026-10-22） |
| `update` · `write` · `mkdir` · `path` | 写入 | **工作目录**：定点改 / 整份写 / 建单层目录 / 对文件移动复制重命名 |
| `delete` | 高危 | **工作目录**：删除文件或目录；必须显式给 `recursive`，递归删除不可恢复 |
| `shell` | **高危**（与 `delete` 同级） | **任意命令执行**（2026-10-23，用户裁定）：在工作目录里跑一段 POSIX `sh` 脚本（Unix 用 `/bin/sh`；Windows 用 Git for Windows 的 MSYS `sh`，经注册表 `InstallPath` 定位，再回落两个惯例位置）。⚠️ **它不是白名单**——`git_*` / `dotnet_*` 收得紧是因为各自只做一件事，而 shell 的价值恰恰是**组合**；边界换成三件事：权限轴（只在 `trusted` 直接放行、`authorized` 问）、设备开关（`shell.json` 的 `enabled` / `executable` / `timeoutSeconds`，控制面 `GET /shell-config` + `shell.configure` / `shell.test`）、超时（杀整棵进程树）与输出上限（`ToolLimits.MaxToolOutputBytes`）。⚠️ 不可重演（不给指纹）：一次 `ls` 与一次 `rm` 在判定上是同一类 |
| `system_info` | 只读 | **设备状态**：按需 CPU、内存、磁盘与可选 NVIDIA GPU 快照 |
| `git_read` | 只读 | **Git 仓库**：受限白名单的 status / diff / log / branch / rev-parse / show / blame；不改仓库、不联网 |
| `git_write` | 写入 | **Git 仓库**：受限本地 add / unstage / commit / branch_create / tag_create；需要写入权限；不联网、不支持 reset / clean |
| `dotnet_build` · `dotnet_test` | 写入 | **自检**（[`01` §3.5](01-会话设计.md) 的 `verify` 轴）：受限的 `dotnet build` / `dotnet test`；二者都过写入闸门，因为 MSBuild 会执行项目里的 target / task、测试更是任意代码——模型可以自己写 `.csproj` |
| `fetch` | 只读 | **自己的历史**（按记录的稳定 id 取回一条旧结果；可带 `offset` / `length` 按字节窗口取） |
| `floating_context` | 只读 | **每轮调用一次的记账工具**（2026-10-26）：真实读数由推进器插在**对话最前面**（`TimelineRender.RenderForModel`），不进记录；记录里每步留一对占位调用 + 结果，模型真调了就改写那条结果。⚠️ 返回值恒为一句占位（`ReclaimedBody`）：调用不带来新信息，这条由机械保证。 |
| `web_search` · `web_fetch` | 消耗型 | **公网**（2026-10-22，`network` 轴）：Tavily 搜索 / 抓取一个 URL；轴为 `off` 时工具仍在表里、调用只回一句人话（改轴不破前缀） |
| `finish_goal` | 只读 | **目标线**（2026-10-22）：只把主动性轴拨回 `standard`，真正的动作在推进器；拨回后普通工具循环还会再走一步让模型收尾 |
| `ask` | 只读 | **用户**（本批之前唯一不在「核心 / 工作目录」这条线上的一个） |
| `release` | 只读 | **上下文**（画一条线：这批资源我用完了，[`01` §12.4](01-会话设计.md)） |
| `compact` | 只读 · **不归闸门管** | **加载边界**（2026-10-22，[`01` §11.2](01-会话设计.md)）：摘要写进参数、检查点由推进器落；只在用户下发 `session.compact` 指令期间生效。⚠️ 它是唯一声明 `GatedByPermission => false` 的工具（`off` 档也放行）：它不改变世界，而指令本身就是授权 |

`delete` 的递归删除按 `PermissionClass.Destructive` 走高危闸门；`shell` 同一档（它执行的是任意命令，后果核心事后挽不回来）；`path` 首版只操作文件，不覆盖目标；`mkdir` 只创建单层目录。⚠️ **`release` 属于「说一句话」那一档，而它有两条执行路径**（2026-10-17）：`StepAsync` 与审批恢复 `ResumeAsync`；两条都只给执行器交回的、**真正执行过**的调用画线（`ToolExecutor.Batch.ExecutedCallIds`）——被闸门拒绝或从未执行的调用不画。`release` 的 `scope` 必须是**非空**字符串数组（空数组在工具侧同样报错，与画线判据一致）。画线之后由 `Stepper` 摘掉**本会话自己**在作用域内的声明（`ClaimStore.Release`，与 `claim.release` 同一个函数），`CommandDispatcher` 发 `claim.released` 与 `release.recorded`。
⚠️ **`release` 是这一列里最纯的一个**：它**连文件都不碰**——它做的是说出一句话，
而核心把这句话记成一条记录。判据同上面那条：它贡献的不是「干活的能力」，
是**「模型能按任务边界收敛上下文」这条机制的入口**。

⚠️ **`dotnet_build` / `dotnet_test` 是这一列里唯一「执行工作目录里的代码」的一对**，
它们仍然算机制入口而不是「干活的能力」：`verify` 轴（自检 / 严格）要求模型能**真的**跑编译与测试，
而在它们之前那句话对模型是**做不到的事**。⚠️ 边界收得很紧：只接受 `project` / `noRestore` /
`noIncremental` / `filter` 四个结构化参数，命令行前缀由核心拼死，不经 shell、不开放
`publish` / `clean` / `run` / `format` / 任意 dotnet 参数。⚠️ 同一工作目录的两次构建在进程内互斥
（`obj/` / `bin/` 撞文件锁会报出与源码无关的错误）。

⚠️ **工具结果的「全量保存 + 投递截断」**（2026-10-17 用户裁定）：工具把**全量**结果交给核心
（只受一个**保存**上限 `ToolLimits.MaxToolOutputBytes` 约束，防炸盘）；喂给模型时由
`TimelineRender.RenderForModel` 按**投递**预算 `ToolLimits.MaxResultBytes` **只保留开头**，
尾部换成一条带稳定 id 与下一个偏移的注记——模型用 `fetch(id, offset)` 接着看，**不必重跑工具**。
⚠️ 头 / 控制台走 `TimelineRender.Render`，**不截断**：那是查看存档，不是投递。
⚠️ 盘上的**总量**仍然无界，属于核心状态管理，单独解决。

⚠️ **而这张表今天**每个会话都一样**（没有工具白名单）**：派生源只有一个
`BuiltInTools.All`，`tool.setEnabled` 没上线（[`03` §3](03-控制面协议.md)）⇒
「按会话给不同工具集」今天没有落点（[`01` §14 #24](01-会话设计.md)）。
⚠️ 而**改这张表是最贵的操作**（[`00` §7 判据 5](00-设计哲学.md)：Claude 协议下 tools 在
**前缀最前端**）⇒ 别把它当成「顺手加个开关」。

⚠️ **而「内建」是一条属性，不是第三种来源**：来源仍然只有三种（内建 / 插件 / MCP）。
⇒ **别在工具接口上加 `IsBuiltIn`**——那会把「谁提供」与「能不能拿掉」混成一个布尔。
⚠️ 这个列表今天就是那个唯一的派生源；插件宿主落地时它变成「内建 ⊕ 插件贡献」，
而**调用方不用改**（它们始终拿到一份有序的 `ITool` 列表）。

⚠️ **工具不是独立实体**（修正 [`01` §9.1](01-会话设计.md) 的「工具 / 插件注册表」）：

> **工具是插件的贡献，不是兄弟概念。工具表是派生的。**

省掉一整套并行的注册与生命周期管理。MCP 工具同样派生自 MCP 适配器插件（§4）。

## 2. 插件 = 声明 + 回调

> **贡献是数据，钩子是行为。** 数据在加载时收集，行为在定义好的相位上被调用。

这是「数据与行为分离」（[`00` §1.2](00-设计哲学.md)）在插件层的复现。推论：

> **插件不是"被调用的"，是"被收集的"。**

## 3. 五个贡献面

⚠️ **前四个各自覆盖「一步」的一段相位**（`04` §6 的相位图上，驱动 / 渲染 / 执行各有着落；**模型调用与落盘是核心自己的**，不对外开放）：

| 面 | 给谁的 | 相位 | 挂在 |
|---|---|---|---|
| **工具** | 模型的**手** | 执行 | 执行 / 渲染 / 优化 / **取消**钩子 · 权限类别 |
| **提示词** | 模型的**眼** | 渲染 | 头槽位**首要块** + 尾槽位字段 |

> ⚠️ **这一面的「落点」与「有没有人往那儿写」是两件事，别读混**（2026-10-11 拼装批）：
> **落点已经有了**——首要块与尾块都真的进请求（`SystemBlock.Render` 一处装配，
> [`01` §3.1](01-会话设计.md)），而 **`premiers/<id>.md` 是今天唯一的写手：用户手写一个文件**。
> ⇒ **插件贡献一条都没收**（宿主不存在）。而这一面**排在最贵的位置**：
> 它进的是头槽位/尾槽位，`04` §7.2 那张表写着「**提示词贡献 ✅ 破**」。
> ⇒ 插件宿主落地时，这一面的第一条纪律就是 §7.3 机制 1（**贡献集合每步取一次快照**）——
> 今天它是免费的（只有一个文件、在步开始冻结），而**插件一进来它就不再免费**。
| **控制点** | 人的**手** | 任意 | 控制面命令（[`03`](03-控制面协议.md)） |
| **驱动与指令** | 循环的**扳机与轨道** | 驱动 | 驱动源 · `pendingDirectives` |

⚠️ **「提示词」这一面只进首要块**（2026-10-07 裁定）：**系统块是核心提供的恒定单文件，插件不可注入**
——理由与「随谁走」那条一致（[`01` §3.1](01-会话设计.md)）。这不是收紧权限：插件想加的那类约定按分工
本来就住首要块，**一个字都没损失**。

**第五个是横切面：事件订阅** —— 它**不对应任何相位**，是**只读观察者**。与控制点成对：**控制点是「人 → 插件」，订阅是「插件 → 人」**。通知、遥测、日志都挂这儿。

**两个统一**：

- **轴 = 控制点的特例** —— 命令固定为 `setAxis`。插件加轴不需要新机制
- **强制调用 = 一条指令** —— [`01` §11.5](01-会话设计.md) 的 `pendingDirectives` 已是通用形态，贡献一条即可

### 3.1 控制点：声明数据，头渲染

> ⚠️ **插件不带 UI。UI 全是头的事。**

```
插件声明：{ id: "clearCache", label: "清空缓存", 参数: [...] }
头渲染成：按钮 / 下拉 / 开关          ← 头自己决定
```

**"插件提供按钮"存在于声明层，不存在于代码层。** 真要做定制 UI，得与头单独协商——**不划算，不做**。

### 3.2 取消钩子

工具的第四个钩子是**取消**（见 [`00` §5](00-设计哲学.md) / [`01` §9](01-会话设计.md)）。

⚠️ **它必须有**：[`03`](03-控制面协议.md) 有 `session.interrupt`——**打断在工具层没有落点的话，在飞的调用怎么办？**

## 4. MCP = 适配器插件

> **MCP 服务器就是一个插件，其贡献恰好由远端提供。**

⚠️ **不存在「MCP 子系统」。** 这与上游协议适配器**完全镜像**：

| | 方向 | 干什么 |
|---|---|---|
| **上游协议适配器** | 出 | 我们的 canonical → Claude / OpenAI |
| **MCP 适配器插件** | 入 | MCP server 的能力 → 我们的插件契约 |

**同一个形状，相反方向。** 收益立刻出现：

- MCP 工具走**同一套**生命周期、权限类别、渲染策略 ⚠️ —— 但**钩子只有「执行」**：**渲染 / 优化 / 取消不在 MCP 原语里**，那三个走核心侧默认策略
- MCP 的 `prompts` 原语天然映射到**提示词贡献**——它本来就有的东西
- **反过来也成立**：想要隔离，就**把自己的插件包成 MCP server**。这是"带外插件"的标准形态

⚠️ **MCP 掉线不能改工具表** —— 工具表在最前，改它全废。沿用 [`01` §3.5](01-会话设计.md) 那条：**工具仍在，调用时拒**。掉线只是调用失败。

## 5. 插件形态与信任

| | **进程内** | **MCP** |
|---|---|---|
| 信任 | **完全信任**（能碰核心内存） | 隔离（带外） |
| 适用 | 自建插件、需要钩子的 | 异构语言、第三方、想要隔离的 |
| 能力 | 全部五个面 | 取决于 MCP 原语覆盖（工具 / prompts 有；**控制点、订阅、渲染 / 优化 / 取消钩子没有**） |

⚠️ **诚实地说：装一个进程内插件 = 把核心交给它。** 不粉饰。

**权限类别**（[`01` §3.5](01-会话设计.md)）：MCP 声明不了自己的类别 → **未声明即取默认类别**，默认取 **`Writing`**。

| 默认取 | 后果 |
|---|---|
| `ReadOnly` | ❌ 未知工具可能在标准档**静默删库** |
| `Destructive` | ❌ 只读的 MCP server 在**标准档被整个拒掉**，MCP 不可用 |
| **`Writing`** | ✅ 标准档**问一句**（可用），授权档放行 |

⚠️ **要认的洞**：一个真破坏性的工具若被误判为 `Writing`，在**授权档会不询问直接跑**。这是"不知道就打中档"的代价。

### 5.1 工具拿到的存储句柄：**只读数据根**（2026-10-06 定）

> **一个工具能看到多少字节，本身就是一条信任声明。** 别把它藏进「工具的实现细节」里。

**判据是「它需要读什么才能做它的事」，不是「核心愿不愿意给」**：

| 句柄 | 给谁 | 例子 |
|---|---|---|
| **只读数据根**（+ blob 读取器） | 需要**回看历史**的工具 | `fetch`（[`01` §8.0.2](01-会话设计.md)）——它要能定位**任意会话**的那一行，所以给的是根，不是某一个会话 |
| **工作目录** | 干活类工具 | `read` / `write` / `bash`（§5 那张表里的路径边界另算） |

⚠️ **为什么 `fetch` 必须拿到数据根、而不是「当前会话的 store」**：它要按**稳定 id** 定位一条历史行，
而 id 是**全局唯一、但不带会话信息**的（[`01` §8.0.2 第七节](01-会话设计.md)）⇒ 限定「当前会话」它就得先知道自己在哪个会话里，
而**工具在概念上是无状态的**。（今天这不成问题——`fetch` 只能取回本会话的注记所指的那一行——
但**把限制写进句柄，而不是写进工具的语义**，才不会在「跨会话取回」出现时变成一个静默的行为分叉。）

⚠️ **这条的后果要如实说**：拿到了数据根的插件，**读得到别的会话的 `store/`**。本机单用户（[`01` §8.1](01-会话设计.md)「数据根的选择本身就是隔离」）
⇒ 与它已经能读工作目录相比，**没有多出跨信任边界的暴露**。但进程内插件本来就「把核心交给它」（本节开头那句）——**这条不新增信任面，它只是把既有的说清楚**。

⚠️ **只读是结构性的，不是纪律性的**：句柄上**只有**读取方法。写盘那条路（`reclaim` / 改历史）留在核心——与
「`fetch` 只读、`compact` 改加载边界所以留在核心」（[`01` §8.0.2](01-会话设计.md)）**同一个判据**。

⚠️ **实现（2026-10-06，回收批）——句柄今天有第三个成员，而它兑现的是本节的「数据根」那一半**：

| 成员 | 给谁 |
|---|---|
| `WorkingDirectory` · `ResolvePath` | 干活类工具（`read` / `ls`） |
| `ReadBlob(sha256)` · **`SnapshotOf(stableId)`** | **回看历史**的工具（`fetch`） |

⚠️ **`SnapshotOf` 交回的是「当时那串块」，不是一个地址**——因为一条结果可以是
「这是那张图」+ 图那样一串块，也可以是纯图、一个字都没有（[`01` §3.6 ①之一](01-会话设计.md)）。
⚠️ 它**按记录的稳定 id 找**，而且从**记录**算（不是渲染后的形态）——
拿渲染后的内容去算会算出**那段注记**，`fetch` 当场永久取不回。
⚠️ **今天它只能取回本会话的行**：跨会话取回出现时**只改这个实现，工具一个字不动**
（这正是本节开头「把限制写进句柄、别写进工具的语义」那条要求）。

⚠️ **本节那张表说的「数据根」今天<b>只实现到「本会话」这一格</b>**，差额如实记在这里，别读成已经给了根。

## 6. 钩子与相位

```
一步 = 驱动 → 渲染 → 调用 → 执行 → 落盘
        │      │      │      │      │
        │      │      │      │      └─ 优化钩子（在 GC 窗口）
        │      │      │      └─ 执行钩子 / 取消钩子
        │      │      └─ （模型调用）
        │      └─ 渲染钩子（纯函数）· 提示词贡献
        └─ 驱动源（插件可产生）
```

## 7. 热重载

**要做，而且它本来就是「先制造前缀失效，再顺手做手术」的又一例**（与 `compact`、`release` 同族）。

### 7.1 快照已经解决了最难的部分

⚠️ 本来会担心：插件升级 → 渲染实现变了 → 历史里工具结果的**渲染字节变了**，而且从**最旧的那个**开始变。

**不用新增机制。** [`00` §5](00-设计哲学.md) / [`01` §9](01-会话设计.md)：**快照 = 上次实际喂给模型的渲染产物**。所以指纹一致时用的是**旧快照，新渲染代码压根不被调用**。

### 7.2 代价可精确预测

| 插件改了什么 | 破前缀吗 | 因为 |
|---|---|---|
| **工具的渲染实现** | ❌ **不破** | 快照钉住 |
| 工具的权限类别 | ❌ | 不在请求里 |
| 浮动贡献 | ❌ | 本来就每步在变 |
| **工具集增删** | ✅ 破 | 工具表在**最前** |
| **提示词贡献** | ✅ 破 | 在**头槽位** |

> **工具插件可以随便升；提示词插件升级就是它本来的目的。**

### 7.3 五条机制

1. **贡献集合每步取一次快照** —— 与 `now` 冻结同步开始（[`01` §3.2](01-会话设计.md)）同一个道理。否则渲染不再是纯函数：**半新半旧 → 每步都破前缀**
2. **顺序一并冻结** —— 快照里不只有**集合**，还有**顺序**（[`01` §3.1](01-会话设计.md)）。冻结之后"瞎变"不是被规则禁止，是**结构上没有东西可以变**
3. **前缀指纹** —— `hash(工具表 ∥ 系统块 ∥ 首要块)`，**每步比对**：

   > **指纹变了 ⇔ 缓存必然失效。** 不是"猜会失效"，是**同义反复**。

   它**顺手吃掉"什么算变更"的枚举**——不需要枚举，也就不会漏。而且它是**精确的**：只贡献浮动字段的插件变了，**指纹不变**（浮动块本来就不在缓存里），不误判。

   ⚠️ **只覆盖重建的部分** —— 历史是追加的（结构上不破前缀），GC / release / compact 是显式事件。
   ⚠️ **住内存，不落盘** —— 它是**预测**不是正确性依据。丢了 ⇒ 当作"冷"，而这**几乎必然是对的**（时间都过去了）。与 [`00` §5](00-设计哲学.md) 那个工具结果指纹**同一个定位**：优化的输入，不是正确性的机制。
4. **切换发生在步边界** —— 绝不在步中途
5. **在飞的调用钉住旧版本** —— 引用计数，最后一个在飞调用结束后才卸载。**失败保持旧版本**（原子切换，绝不半加载）

### 7.4 它打开 GC 窗口

前缀失效 = 唯一的免费改写窗口（[`00` §0](00-设计哲学.md)）。所以重载是**又一个回收时机**——与 `compact` / `release` 同族。

## 9. 插件的加载与物理形态（2026-10-07 定方向）

### 9.1 工具的排序键：名字，ordinal

⚠️ **本节是 2026-10-07 用户裁定的落点**——用户三条判断：**排序必须唯一** · **很多拼接可以现场做** · **插件可以合到一个 dll**。

**规则一句话**：**工具表的顺序 = 工具名的 ordinal 升序。**

**⚠️ 为什么它就是 [`01` §9.1](01-会话设计.md) 那条规则的退化形，而不是换了另一条规则**：§9.1 写的是
`sort by (priority, pluginId)`，而在「一个 dll 贡献一个工具」这个形状下 **`pluginId` ≈ 工具名**
⇒ **名字就是那把键**。⚠️ 更进一步：**键已经唯一时，tiebreak 是多余的**——所以不是「缺了 priority」，
是**这一档在本形状里没有东西可排**。

**为什么名字是最好的键（不是退而求其次）**：它**已经在契约里**（[`ITool.Name`](../src/Lilara.Core/Kernel/Tool.cs)）·
**已经唯一** · **已经不可变**（那条注释：「别改，改了等于让历史里已有的调用变成死链」）
⇒ **不需要第二把键，也就不需要 manifest 字段**——少一个会腐的东西。

⚠️ **ordinal，不是文化序。** 默认的 `OrderBy(x => x)` / `string.CompareTo` 走 **ICU 文化序**：
`i` 与 `I` 在 `en-US` 与 `tr-TR`（土耳其无点 i）下**序不同** ⇒ **同一份数据、两台机器、两个顺序**，
而且是**静默破前缀**。⚠️ **本仓已有家法**：`PresetStore` · `SessionStore` · `ProviderStore` ·
`EventBus` · `Axes` · `ListTool` 等 **11 处**都显式写 `StringComparer.Ordinal`。照做，并配一条测试钉住。

⚠️ **选字母序的代价要认**：今天的 `BuiltInTools.All` 是**字面量 `[ListTool, ReadTool, FetchTool]`**
——**不是字母序**（字母序是 `fetch, list, read`）。⇒ **改它会有一次前缀失效**。
今天**还没有已部署的会话** ⇒ 实际代价是零，**现在改最便宜**；越晚越贵。

**字母序不解决、必须单独补的一条：重名。** 今天 `ToolExecutor` 是
`tools.ToDictionary(t => t.Name, StringComparer.Ordinal)` ⇒ 重复**会抛**，
但**抛在执行时**——那时**请求早就带着两份定义发出去了**。⇒ 需要一条**加载期**硬错，
并报出**冲突的两个来源**（不是只报一个名字——那样用户不知道该摘谁）。

> **判据**：「名字唯一」这个谓词**得在两层都判**（装配期 / 执行期），而**早的那层赢**。
> 同 [`01` §8.0.2](01-会话设计.md) 那条「两层判据必须共用一个谓词」的同一个形状。

### 9.2 装配是每步的，扫描是事件

⚠️ **用户裁定：很多拼接可以现场做**——这条**成立**，而代码里已有先例（不是「可以接受延迟」，是**量不到**）：
`Stepper.StepAsync` 每一步本来就在 `ReadTimeline` + `TimelineRender.Render` **整条时间线** + `AppendEvents` 落盘。
在它旁边多拼几段字符串、排一次序，**测不出来**。

⚠️ **但两类动作的频率必须分开——这条分界线画错的后果比性能严重得多**：

| 动作 | 频率 | 为什么 |
|---|---|---|
| **装配**（收集贡献 + 排序 + 拼合） | **每步**（与 `now` 冻结同步，§7.3 机制 1） | 贡献集合是**这一步的输入**，不取快照 → 渲染不再是纯函数 |
| **扫描目录 / 加载 dll** | **只在显式热重载时** | ⚠️ **那一次扫描本身就是「窗口开了」的信号** |

⚠️ **如果扫描混成常态，症状是「完全看不出来」**：顺序不变（⚠️ **这正是字母序与 name 键顺带买到的性质**），
所以不会破前缀，看起来无害。**但你会失去「热重载发生了」这个事件的边界** ——
而它是 [`01` §11.7](01-会话设计.md) 那张「窗口触发 vs 压力触发」表里**今天唯一能由核心主动制造的真实触发源**
（激活那次试过、已撑回）。⇒ **扫描必须是一次事件，不是一种常态。**

### 9.3 插件粒度：贡献面才是纪律，dll 边界不是

⚠️ **用户的顾虑是「重蹈 ALP 一个 dll 乱七八糟的覆辙」。这个顾虑对，但诊断要换。**

**ALP 的病是「责任蔓延」，不是「物理打包太大」**：它的端口与消息分发耦合后
**长出了权重、订阅、子流**——那些是**机制蔓延**，不是**单个 dll 变大**。
（那 13 处文档互相矛盾是**后果**，不是原因。见启动时那份 ALP 盘点。）

⇒ **判据**：

> **一个 dll 乱七八糟 ⟺ 它能往一个没有声明的地方写字。**
> **dll 的数目不是纪律；贡献面才是纪律。**

⚠️ **而物理拆分的收益比预期的小**：进程内插件**共享整个地址空间、都能碰核心内存**
（§5：「装一个进程内插件 = 把核心交给它」）⇒ **dll 边界不是信任边界**。
「一个工具一个 dll」买到的是一条**命名约定**，不是隔离。

> **能用结构解决的，别用约定解决**（[`00` §7](00-设计哲学.md) 判据 4）。切小 dll 恰好是「用约定解决」。

**⇒ 三条实际手段**（防 ALP 复发靠这三条，**不靠切小**）：

1. **只能贡献已声明的面** —— §3 那五个面**已经声明过了**，加面要改 §3（一个显式的动作）
2. **`pluginId` 在 dll 内显式声明**，**不从文件名推** —— 改名不重排
   （§9.1 既然按名字排，**名字与文件名的分离**就是这一条的具体形态）
3. ⚠️ **原子加载**：一个插件的贡献**要么全上、要么全不上**（§7.3 机制 5「原子切换，绝不半加载」）
   —— **这才是防「乱七八糟」的实际手段**

⚠️ **切小 dll 有一个要认的副作用**：它把插件版本切成 N 份 ⇒ §8「`spec.json` 与插件版本的绑定」
从**一道题变成 N 道**（哪几个 dll 算一个「插件版本」？）。
⇒ **合成一个 dll 反而让那道题更小**——「一个 dll = 一个插件」是一条**边界清楚**的默认。

⚠️ **「贡献面已声明」在代码里今天只有半条**，别读成已经拦得住：
`BuiltInTools` 的类注释写着「插件宿主落地时这里会变成『内建 ⊕ 插件贡献』，
而**调用方不用改**」——那是**收集点**，它不拦贡献面。⇒ **拦得住靠的是 §3 那张表被人遵守**，
而 §9.3 这条判据的价值正是**把「遵守」变成一个可指的判据**（能往哪写），不是靠评审的记性。

### 9.4 插件的物理形态：一个工具一个 dll 是合法退化形

⚠️ **用户提出的形态**：「一个工具对应一个 dll，瞬发；其他功能单独塞到另一批 dll」。
**这与 §1.3「工具是插件的贡献，不是独立实体」不矛盾**——**那个 dll 本身就是插件**，只是它恰好贡献一个工具。

**但形态按 §9.3 那条判据收一下**：**一个 dll 可以贡献任意多个面**，
「一个 dll 一个工具」是它的**合法退化形**（而且是最常见的那种，会自然长成这样）。
⇒ **不该是「两批 dll」，是「两种 dll」**——否则一个完整插件会被迫拆成四个 dll，**而它们必须共享版本**
（§9.3 那条副作用的四个实例）。

**四个实现坑，前三个都属于「错了不会报错」那一类**：

| # | 坑 | 症状 |
|---|---|---|
| **1** | **顺序从目录扫描来** | [`01` §9.1](01-会话设计.md) 点名警告过「从容器里拿到的顺序一律视为随机」，列的第一个就是**文件枚举** ⇒ **每步破位置 0** |
| **2** | **类型同一性** | 要热重载就得每个 dll 一个 collectible ALC ⇒ **每个 ALC 必须把 `Lilara.Core` 解析回主 ALC**，不能自己加载一份。做错 ⇒ 类型转换失败（`ITool` ≠ `ITool`），而**它看起来像任何一个别的问题** |
| **3** | **卸载失败是静默的** | `AssemblyLoadContext.Unload()` 只是**请求**，真正回收要等 GC 且引用全断，**失败不抛** |
| **4** | **目录自动加载面太大** | 任何能往那个目录写文件的东西都能**执行代码** |

⚠️ **坑 3 是本仓反复栽的那个形状**（「意图 ≠ 生效」）：**热重载必须配一条「确认卸载真的发生了」的探针**
（弱引用 + `GC.Collect()` + `IsAlive`）。没有它，热重载**只增不减**——
每重载一次多一份旧代码常驻，**没有任何东西会告诉你**。

**两条要认的代价**：

- **「瞬发」是主动破位置 0**（§7.2：**工具集增删 ✅ 破**）⇒ 它该是**显式的开发模式开关，默认关闭**；
  开启时**顺手做 GC**（§7.4：热重载**打开 GC 窗口**）
- ⚠️ **目录自动加载 = 任何能往那个目录写文件的东西都能执行代码**。§5 已经接受了进程内插件的完全信任，
  但「扫描目录」比「显式安装」**面大**。**记下这句话就行，不是要现在做机制**
