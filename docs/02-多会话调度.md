# 多会话调度

> 本文涉及**核心如何同时推进多个会话**。控制面协议见 [`03`](03-控制面协议.md)，进程内部结构见 [`04`](04-插件与内部结构.md)。
> 母原则见 [`00-设计哲学.md`](00-设计哲学.md)，会话本体见 [`01-会话设计.md`](01-会话设计.md)。

---

## 1. 没有「会话引擎」

⚠️ **不存在 per-session 的活对象。**

| | ALP 的 `ISubEngine` | 本项目 |
|---|---|---|
| session 是什么 | **活对象**——有自己的循环、定时器、端口、订阅 | **数据** |
| 所以它必须 | 是个对象，因为它在**自己跑** | 不需要，因为它**不跑** |

**行为不挂在会话上**（[`00` §1.2 数据与行为分离](00-设计哲学.md)），行为发生在**发请求那一刻**。

> **所以不是「会话引擎」，是「步调度器」+「推进器」。**

引入会话引擎 = `SessionPool` 借尸还魂，等于把 ALP 的 `MasterEngine + ISubEngine + SpawnCheck + 资源池`搬回来。

## 2. 调度域的四个组件

| 组件 | 职责 | 状态 |
|---|---|---|
| **注册表** | provider / 项目 / 会话清单（**纯索引**，不含工具与插件——按 [`04` §1](04-插件与内部结构.md) 的口径） | 只读为主 |
| **资源管理器** | 声明、FIFO、**解除阻塞**（[`01` §5](01-会话设计.md)：解除 ≠ 启动） | ⚠️ **[`01` §12](01-会话设计.md) 已设计，而这四个里它做得最少**（2026-10-11 复核）：`ClaimStore` 只是**一层扁平路径比较** + 一个 `claims.json`；**FIFO 队列、解除阻塞、`WaitingExternal` 一个都不存在**（`session.delete` / `claim.release` 已经能清声明，那是它的全部实现） |
| **步调度器** | 决定下一个推进谁 | 本文 |
| **推进器** | 跑一步：渲染 → 调用 → 执行 → 落盘 | [`01` §3–§6](01-会话设计.md) 的全部内容 |

> 这里是**与调度相关**的四个。⚠️ **「谁决定换出」不在它们之中**——见 §5（**待定**）。完整的核心组成（含**插件宿主**与控制面）见 [`04` §1](04-插件与内部结构.md)。

**调度器与推进器的边界**：调度器**不认识**会话内容、模型、工具——它只回答"现在轮到谁"。一切"怎么做"在推进器里。

## 3. 调度粒度是「步」

> **步是唯一的时间单位（[`01` §4](01-会话设计.md)），也是持久化的原子单位——所以它也是调度的单位。**

调度器不"启动会话"，它**推进一步**：

```
可推进 = 队列非空 ∧ 未被阻塞 ∧ 未在运行 ∧ 全局并发未满
```

**「可推进」的判据就是这四个合取项**（[`01` §6.1](01-会话设计.md) 的「启动」只管头两项）——调度器不认识别的驱动概念，**四个驱动源都只是往队列里塞东西**。

**触发「可推进」的动作**：入队（用户消息 · 后台事项事件 · 定时器）· **显式「启动」**（控制面可直接调，也是步进档唯一的前进方式）· 上一步完成 · 锁释放（**解除**等待者，见 [`01` §5](01-会话设计.md)：解除 ≠ 启动）。

### 3.1 真并行：投递式，不是时间片

⚠️ **多个会话的步是真正同时在飞的**——不是一个跑完再跑下一个。

```
可推进事件到达 → 投递一步（非阻塞）→ 立即返回
  该步在飞期间，调度器继续处理别的会话
  步完成 → 产生新事件 → 该会话重新可推进
```

这与 [`00` §1.1 头核分离](00-设计哲学.md) 是**同一条哲学**——**"投递即返回，结果以事件形式流出，绝不阻塞式等待"**，只不过这次是**核心对自己的会话**。

模型调用是**纯 I/O 等待**（几秒到几分钟），所以：

> **不需要 thread-per-session。** async I/O 足够，只有 CPU 密集的工具（编译）才落到线程池。
> 会话"在等模型"时几乎不占任何东西——这正是 [`01` §13](01-会话设计.md)「未激活的会话不占运行时资源」的机制依据。

**三个副产物，都不需要额外机制**：

| 性质 | 因为 |
|---|---|
| **天然公平** | 每次只推一步就撒手，长任务饿不死别人——**不需要时间片** |
| **不伤缓存** | 缓存挂在前缀**内容**上，不挂在进程上。交错推进不同会话，只要各自前缀没动，谁的缓存都不破 |
| **重入保护只剩一把标志** | [`01` §13](01-会话设计.md)「绝不并发两步」= 一个布尔 |

### 3.2 会话内严格串行是正确性条款

⚠️ [`01` §13](01-会话设计.md) 的「会话内部串行」**不是性能条款，是正确性条款**：

> **至多一步在飞 → 不可能有两步同时往 `history.jsonl` 追加、同时改 `state.json`。**

**它是并发调度能成立的前提**，不是可以调的旋钮。（会话**之间**的并发才是旋钮，见 §6。）

## 4. 会话与子会话同层

> **调度器只认识「会话」，不认识「父子」。** 子会话不比别的会话优先，也不比它低。

**派生树只出现在四个地方，前三个都不在调度路径上**：

| 用途 | 位置 |
|---|---|
| 注入地址（父 ↔ 子） | [`01` §10.1](01-会话设计.md) |
| 声明 ceiling | [`01` §12.10](01-会话设计.md) |
| 权限收窄 | [`01` §10.3](01-会话设计.md) |
| **树级并发配额** | ← **唯一例外**：树在这里作为**分组依据**进入调度 |

**归属与派生正交**（[`01` §10.4](01-会话设计.md)）在这里的体现：调度看的是"谁可推进"，不是"谁属于谁"。

## 5. 激活即缓存

**内存里的会话只有两样**：**热数据**（记录 + 配置）+ **一把互斥标志**。

**没有循环、没有定时器、没有订阅、没有端口。**

> **「激活」是缓存策略，不是生命周期。** 没有"启动会话""停止会话"，只有"在不在内存里"。
>
> ⚠️ **待定：谁决定「换出」。** 换入有明确发起者（头要求激活，[`01` §8.3](01-会话设计.md)）；**换出没有**——是内存压力、`session.deactivate`（[`03` §3](03-控制面协议.md)）、还是两者，未定。**管理"内存中会话集合"的那个组件也不在 §2 的四者之中。**（见 [`01` §14](01-会话设计.md)）

**换出永远安全**（会话是数据，[`01` §2](01-会话设计.md)）：

```
换出 = 持久化队列（[`01` §6.1](01-会话设计.md)）→ 释放锁
换入 = 加载记录 → 重取锁 → **启动**（队列里有待办就继续）      （顺序见 [`01` §8.3](01-会话设计.md)；⚠️ 换入 = 那里的「激活」）
```

⚠️ 换出**必须先持久化队列**，否则换回来时不知道自己还在等谁（[`01` §12.8](01-会话设计.md)）——换出不是"丢弃内存"，是**先落盘再丢**。

**"卡住"同样是数据**：WaitingForInput / WaitingExternal / Blocked 都写在 `state.json`，不是内存里的挂起源。头重连、进程重启，都只是重新读出来。

## 6. 并发上限管什么

**全局 in-flight 上限**（[`01` §13](01-会话设计.md)）管的**不是 CPU**：

| 管的是 | 为什么 |
|---|---|
| 上游 **rate limit** | 超了会被限流 |
| **花钱的速率** | 并发 N 步 = N 倍烧钱速度 |
| 故障时的**扇出半径** | 上游挂了，在飞的都会失败 |

⚠️ **上限 = 1 时退化为严格串行**——**但那是配置，不是架构**。同一个机制，拧一个数就换行为。

## 7. 层级

```
核心（设备级，唯一）
  └─ 项目（分组键 = 工作目录；数据 + 作用域，不是运行时实体）
       └─ 会话（数据）
```

**核心不"拥有"某个目录，它拥有全部目录下的全部会话**；Project 只是**分组键**（[`01` §8.2](01-会话设计.md)）。
