> 本文是**两个子程序里的第二个**。核心见 [`01`](01-会话设计.md) / [`02`](02-多会话调度.md) / [`04`](04-插件与内部结构.md)，
> 两程序之间的接口见 [`03-控制面协议.md`](03-控制面协议.md)，母原则见 [`00-设计哲学.md`](00-设计哲学.md)。

## 1. 头为什么存在

> **头存在的唯一理由：核心是不可见的。**

核心为了前缀稳定性，把一切能压的都压扁了（[`00`](00-设计哲学.md)）：状态压成字段集、事件压成时间线、顺序压成派生、缓存压成指纹、脏压成一个指示。**这对模型是正确的，对人是不透明的。**

文档里有四处直说了这个代价：

| 代价 | 出处 |
|---|---|
| 归位错误「**拦不住，但看得见**」 | [`00` §2.4](00-设计哲学.md) |
| 语义冲突「无法自动消解，只能靠头的**可见性**」 | [`01` §13](01-会话设计.md) |
| 安全轴「价值**全在可见性**」 | [`01` §3.5](01-会话设计.md) |
| 审批「是**最需要头在场**的东西」 | [`03` §5](03-控制面协议.md) |

由此得到头的第一原则——一句反话：

> ## 核心越克制，头越要喧哗。

核心为**缓存**优化，头为**人的注意力**优化。**这两个目标方向相反。**

⚠️ **头如果模仿核心的克制（能省就省、能派生就派生、能藏就藏），它就没有存在价值。** 所以头**不做**这些：

| 核心做了 | 头不做 |
|---|---|
| 把浮动压成「字段集」 | 把字段**展开成控件** |
| 权限是「闸门」不是「裁剪」 | 显示**「工具在、但被拒」**（否则用户以为工具不存在） |
| 不持久化顺序与指纹 | **重新算并显示** |

### 1.1 头是可替换的

⚠️ **本文区分两件事**，这个区分本身就是设计：

| | 含义 | 谁定 |
|---|---|---|
| **义务** | 任何头都必须做到的事 | **本文 §4**（源自核心文档的既有承诺） |
| **本文的选择** | 这个头怎么做 | **本文 §5 起**（可被另一个头全盘推翻） |

> **换头是允许的，不履行义务是不允许的。** 义务只有四条（§4），其余全是实现自由。

## 2. 形态：本机 Web 应用

```
头进程
├─ 静态资源（前端）
└─ 极小 HTTP/WS 服务  ← 浏览器打开 localhost 即是头
```

| | 理由 |
|---|---|
| **零安装** | 核心已装即有，不用再装一个 GUI 运行时 |
| **拖拽 / 粘贴 / 文件选择** | 浏览器原生支持，正好对上 [`03` §9.1](03-控制面协议.md) 的 `POST /files` |
| **生态** | 这种高密度面板 UI，Web 前端最省工 |

⚠️ **头进程 ≠ 核心的一部分。** 它在**独立的进程**里托管 UI——⚠️ **但不转接协议**：页面 JS **直连核心**，头不代理、不缓存、不理解协议（核心因此**零 UI 耦合**，[`00` §1.1](00-设计哲学.md)）。

### 2.1 连接与发现

```
LILARA_CORE=<url>        默认 http://127.0.0.1:17988
```

> ⚠️ **实现（2026-10-05）**：是**环境变量**（`LILARA_CORE`；头自己的端口是 `LILARA_HEAD_PORT`，默认 17990），
> **不是**命令行旗标 `--core`。
>
> ⚠️ **2026-10-06 两个默认端口都改过**：原先是 **7790**（头）/ **7788**（核心），
> 而它们落在了 Windows 的**保留端口段**里（本机实测 7681-7780 / 7781-7880 / 7881-7980，
> 通常由 Hyper-V / WSL / Docker 的 NAT 预留）⇒ 绑定时 `SocketException 10013`，
> **两个进程都起不来**（头那次还是**未捕获异常砸栈**，现已改成与核心同样的一句人话）。
> ⚠️ **保留段会在重启后变** ⇒ 换默认值只是把坑挪开，**不是永久解**；
> 真正管用的是那两个环境变量。⇒ 遇到「起不来」先跑 `netsh int ipv4 show excludedportrange protocol=tcp` 对一眼。

> ⚠️ **2026-10-05 补：头的端口与核心的 Origin 白名单必须一致。**
> 核心的 WS 只放行**一个** origin。它**原先硬编码** `http://127.0.0.1:7790`——
> 于是用户改了 `LILARA_HEAD_PORT`、浏览器 origin 跟着变，核心**静默拒绝**（`onclose`，
> 浏览器不把 403 响应体交给页面 JS ⇒ 页面只会「已断开·重连中」）。
> 现在核心侧由 `AllowedOriginResolver` 解析：**`LILARA_ALLOWED_ORIGIN`（显式）>
> `LILARA_HEAD_PORT`（推导）> 默认（= 头默认端口，今天 17990）**，并在启动横幅上**印出它接受哪个 origin 与为什么**。
> ⇒ **两个变量是有意让两侧各读一份的**（跨进程约定，与 `LILARA_HOME` / `LILARA_CORE` 同形；
> 核心读不到头进程、头在握手被拒前也发不出任何 WS 命令，没有第二条通道）。
> 代价如实记：**它靠约定一致，不靠机制强制**——所以头页面断开时会去核心 `/info` 比对
> `location.origin`，把原因显示出来（那是唯一能兑现「别静默」的地方）。

⚠️ **核心不广播、不写发现文件**——[`03` §10](03-控制面协议.md) 定了「默认只监听本机」，那**地址就是约定的常量**，发现机制是多余的。

⚠️ 端口若被占，**核心必须显式失败并报告**，不许静默换端口——否则头连不上且不知道为什么。

### 2.2 头负责引导

> ⚠️ **核心启动后没有任何会话**（[`01` §8.1](01-会话设计.md)）。**"配置提供商 → 建初始会话"是头的行为**——它是**策略**，核心不做策略（[`00` §1.3](00-设计哲学.md)）。

```
头启动
  ├─ 连核心 → GET /projects
  ├─ 有 provider？
  │    否 → **引导页**：要求添加提供商（此时不能做别的）
  │    是 → 跳过
  └─ 当前项目下有会话？
       否 → **由头调** session.create
       是 → 打开最近的会话
```

> ⚠️ **实现（2026-10-05，第二个版本）**：头**做配置表单了**——顶部导航切到「供应商」视图
> 就能建 / 改 / 删 provider（`provider.upsert` / `provider.delete`），引导页也指向那里。
>
> **这一条纠正了一处引错的出处。** 本文与 `实现现状.md` 都曾写着
> 「头**不代发** `provider.upsert`（…**见计划 D5**）」——**D5 讲的是前缀指纹，与 provider 配置无关**
> （`docs/superpowers/plans/2026-09-30-head-obligations.md` 的 D5：「头不重算前缀指纹」）。
> 而同时 [`03` §6](03-控制面协议.md) 与 `provider-schema` 的设计一直写着它是
> 「头渲染配置表单的**真相来源**」。⇒ 两处互相矛盾，且那句「不做」的**出处不支持它**。
> **现在按 §2.2 的原文执行**：配置提供商**是**头的策略。

⚠️ **这条纠正了一个错误**：原先写在核心侧的「启动引导」把策略塞进了机制，而且会让**无头启动的核心凭空造会话**。核心现在只认 `session.create` 命令（[`03` §3](03-控制面协议.md)），**谁来调是头的事**。

⚠️ **头因此要在启动时多做一件事**：调 `GET /projects` 判断"有没有 provider / 有没有会话"。这正是它比控制台强的地方——**控制台没有视图，做不了这个判断**。

⚠️ **幂等仍要守**：头每次启动都会跑这段，所以「项目下有会话就打开它」是硬要求，否则每次开浏览器都多一个会话（[`01` §8.1](01-会话设计.md)）。

## 3. 头消费什么：核心渲染，头显示

⚠️ **这是本文最重要的一个决定。**

[`01` §3.4](01-会话设计.md) 定义了载荷的两种形态：**具体**（内容即渲染结果）与**托管**（内容是个引用，构造时向所有者要）。

**问题**：模型侧由核心渲染（那是权威且已存在）；头侧呢？

> **头拿到的是「渲染产物」，不是「骨架」。头不重新实现任何渲染。**

| | 谁做 |
|---|---|
| 解析骨架、向所有者要托管内容 | **核心** |
| 渲染成协议块 / UI 块 | **核心** |
| **显示** | **头** |

**四条理由**：

1. **渲染实现住在插件里**（[`00` §5](00-设计哲学.md) 的四钩子），头跑不了插件代码
2. **头侧没有任何托管内容的取用通道**——[`03` §6](03-控制面协议.md) 只有 `GET /store/{sha256}`（库对象），**工具 / 插件提供的托管块无路可取**。让头渲染等于给每个插件开一条头侧通道，那是在重建一遍核心
3. **快照是可回收的**（[`00` §4](00-设计哲学.md) 的头号可回收物）——头显示历史时快照可能已经没了，**只有核心知道该退化成什么**
4. **`now` 冻结在步开始**（[`00` §2.5](00-设计哲学.md)）——渲染是 `render(贡献, now)`，头没有那个 `now`

**这条决定了一个后果**：`GET /sessions/{id}/history` 返回的是**「当前可渲染的形态」**，不是原始字节。历史加载的倒查语义（[`01` §12.4](01-会话设计.md)：`≥R` 原文 / `<R` 简化）**在核心侧完成**——头不需要知道 `R` 在哪。

> ⚠️ **「检查消息」的缺口因此关闭**（[`01` §14 #26](01-会话设计.md)）：解释权归核心，头只显示。

⚠️ **实现（2026-10-06，回收批）——上面第 3 条理由兑现了，而且**头一个字都没改渲染代码****：
被回收的那条结果由核心渲染成**一句普通 `TextBlock` 注记**（`[已回收] … fetch(id="…") …`）
⇒ 头现有的块渲染直接显示得出来。
⚠️ **但头必须知道「该重拉了」**：回收**不改盘**，而 `/history` 返回的是核心**当时**渲染的形态
⇒ 核心发 `session.reclaimed`，头收到就重拉当前会话的历史（见 [`03` §4](03-控制面协议.md)）。
⚠️ 头侧**不需要**、也**不许**自己判「哪些被回收了」——判定只有核心一处（`Reclaim.Decide`）。
⚠️ **第三条理由的后半（「头显示历史时快照可能已经没了」）今天按「没就没」处理**：
注记里写明了「要现在的值就自己重调一次」，头不额外做降级样式。

### 3.1 头槽位也从核心来

[`00` §2.4](00-设计哲学.md) / [`01` §3.3](01-会话设计.md) 要求「**头的 UI 原样显示两个槽位**」，好让**归位错误看得见**。

⚠️ **原样显示 = 原样显示核心渲染的产物。** 头**不**自己做提示词装配（那是[`00` §1.3](00-设计哲学.md) 的「装配问核心」）。快照里带上两个槽位的渲染产物与**当前是否为空**。

## 4. 四条义务

> 这四条**不是本文的选择，是核心文档的既有承诺**。任何头都必须做到。

| # | 义务 | 出处 |
|---|---|---|
| **1** | **两个槽位原样显示** | [`00` §2.4](00-设计哲学.md) / [`01` §3.3](01-会话设计.md) —— 归位错误的唯一可见性 |
| **2** | **声明可见**（谁在动哪些文件） | [`01` §12.2](01-会话设计.md) 的「可见性单位」 |
| **3** | **审批走独立流，且显眼** | [`03` §5](03-控制面协议.md)「最需要头在场」 |
| **4** | **安全轴显眼**，不藏进配置 | [`01` §3.5](01-会话设计.md)「价值全在可见性」 |

⚠️ **义务 1 的具体含义**：两个槽位要**并排可见**，不是折叠在一个"详情"里。**归位错误（人设出现在两个地方）只在并排时看得出来。**

⚠️ **义务 4 的具体含义**：安全轴**不许收进"更多设置"**。它的全部价值就是"用户忘了说这是生产环境"时能提醒——**藏起来等于取消它**。

## 5. 布局：三栏

> ⚠️ **以下是本文的选择**（§1.1），不是义务。

```
┌──────────┬──────────────────────────────┬─────────────┐
│ 项目 / 树 │  专注会话                     │ 注意力      │
│ ● 重构    │  ⬤ Running · 第 12 步   ⏸ ⏹  │ 待决策 (3)  │
│  ├ A1 ⚠  │  ──────────────────────────── │ ▸ 写 auth.cs│
│  └ A2    │  [时间线]                     │ ▸ git push⚠ │
│ ○ 巡检   │                              │ ────────────│
│ ○ 基准⚠  │                              │ 在跑 (4)    │
│          │  ──────────────────────────── │ ⬤ 重构 步12 │
│          │  [轴面板]                     │ ⬤ 巡检 步3  │
│          │  [两个槽位 + 浮动]             │ ○ 基准 阻塞 │
└──────────┴──────────────────────────────┴─────────────┘
```

> ⚠️ **实现（2026-10-05）**：骨架（三栏）**在**，内容与上图仍不符（§5 是「本文的选择」，可被换头推翻）：
> 左栏是**按工作目录分组的会话列表**（有分组头与会话数，**没有**状态点 / ⚠ 声明标）；
> 右栏有安全轴、待决策、提供商、当前会话、项目、行为控制轴、声明，
> 但**没有「在跑」区**（待决策处只有一块「核心侧尚未实现」的说明）。
> ⚠️ **2026-10-05 做了一轮视觉改版**（信号机架：冷调底 + 等宽字承载一切「被测量的东西」+
> 底部核心自述栏）。**那只是皮**——三栏骨架、义务、数据来源都没变。

**为什么是三栏，而不是"任务控制台"或"纯 chat"**：

| 候选 | 判定 |
|---|---|
| 任务控制台（多会话平铺） | ❌ 单个会话读不进去——时间线是**要读**的东西 |
| 纯 chat（一次一个） | ❌ **并行不可见**——而"你不看它就不知道"正是核心甩给头的债 |
| **三栏** | ✅ 中栏保证**日常阅读**，右栏偿还**并行债** |

> **并行不可见是「债」（核心明确甩过来的），阅读不便是「税」（每天都要交）。**
> **而这两者的修法成本差很多——提并行的修法便宜（一栏），降阅读质量的修法贵。**
> 所以骨架押在阅读上，并行用一栏补。

⚠️ **右栏恒常占位，不收起、不浮出。** 理由：**浮出的东西你要先注意到它浮出了**——那正好抵消了它存在的意义。

## 6. 头的状态

| 层 | 谁保持 | 怎么更新 |
|---|---|---|
| **真相** | 核心 | —— |
| **视图** | 头 | 事件增量（[`03` §3](03-控制面协议.md)） |
| **重建** | 头 | 快照 + 游标重放（[`03` §7](03-控制面协议.md)） |

⚠️ **头是无状态的**（[`03` §1](03-控制面协议.md)）——**除了视图，什么也不持久化**。重启即重来。

### 6.1 会话列表是「派生」的

⚠️ [`03` §6](03-控制面协议.md) 的快照端点里**没有"全部会话"**——只有 `GET /projects` 与 `GET /projects/{pk}/sessions`。

**这不是缺口，是设计**（[`00` §7 判据 8](00-设计哲学.md)：能派生的就不要持久化）：

> **全局会话列表 = 对 `GET /projects` 的每个 pk 取 sessions 的并集。** 头自己拼。

⚠️ 头必须**自己维护这份派生索引**并随 `project:<pk>` 流（[`03` §5](03-控制面协议.md)）更新它。

### 6.2 游标与重连

```
每个订阅流各自一个游标（03 §7）
   重连 → hello(lastSeq) → 补发 → 转实时
   漏太多 → resync_required → HTTP 拉快照 → 重建
```

⚠️ **头的降级路径只有一条**（[`03` §7](03-控制面协议.md) 定的）：**拉快照，重建**。不要发明"部分合并"的聪明逻辑——**那是另一套状态机，且必然与快照对不齐**。

⚠️ **重建时保留的是「用户的选择」**（当前选中哪个会话、滚动位置、草稿），**丢弃的是「对核心的假设」**。

## 7. 四条义务怎么落到界面

### 7.1 两个槽位（义务 1）

常驻在会话底部，**系统 / 首要 / 浮动三块并排或堆叠**，可展开全文。

⚠️ **实现（2026-10-05）**：并排做了（系统 / 首要两格 + 浮动一行），**「可展开全文」没做**——
两格是固定高度（约 4 行）内部滚动。也不打算做成折叠：折叠与义务 1 的
「**归位错误只在并排时看得出来**」相冲（折起来就看不见了）。

⚠️ **空的也要显示**（标"（空）"）——「裸核心没有系统提示词」是合法形态（[`04` §1.3](04-插件与内部结构.md)），**但用户要能看见"它真的是空的"**，而不是以为头坏了。

### 7.2 声明（义务 2）

⚠️ 数据来自 `claim.acquired` / `.released`（[`03` §4](03-控制面协议.md)）+ `GET /claims`。

**呈现的关键不是列表，是「冲突」。** 头要把「两个会话声明了重叠路径」**顶到右栏**，而不只是画在树里——树里的 ⚠ 会被忽略。

### 7.3 审批（义务 3）

⚠️ 走 `approvals` 流（[`03` §5](03-控制面协议.md)），**不混在会话事件里**。

每条审批必须显示**上下文**，否则用户没法判断：

| 必显 | 为什么 |
|---|---|
| 哪个会话 / 哪个子会话 | 子会话的审批**上提到头**（[`01` §10.3](01-会话设计.md)），不区分就乱 |
| 工具 + 参数 | —— |
| **权限类别**（尤其 `Destructive`） | 「高危 = 不可逆」（[`01` §3.5](01-会话设计.md)）——**必须让"不可撤销"看得见** |
| **当时的权限档位** | 用户要知道"我在哪一档上被问的" |

⚠️ **`remember?` 参数的语义未定**（[`01` §14 #13](01-会话设计.md)）——头**先不暴露**，等语义定了再上。

> ⚠️ **更新（2026-10-08 询问批）**：语义**定了**，而且那条流**有生产者了**——
> 见 [`01` §3.8](01-会话设计.md)。两件事变了：
>
> - **`remember` 现在可以暴露**：两档（`args` = 记住这些参数 / `tool` = 这个工具都放行），
>   ⚠️ 而 `tool` 那档**必须在界面上把粗度写出来**（「本会话内不再问**任何** X 调用」），
>   不许与「记住这些参数」并排成两个长得差不多的复选框。
> - **必显那一列多了两条**：**多问**（一张卡上有几个问题）与**是否可改写参数**
>   （`Permission` 卡的参数框）。⚠️ 前者是因为一次询问可以是**一个信封多个问题**，
>   而「用户答完第一个就点了确认」是这类界面最容易犯的错。
>
> ⚠️ **但这一批头只做到「看得见」**：`GET /sessions` 的 `ask` 那一格 +
> `approval.requested` / `.resolved` 两条事件，在会话列表上标出「这个会话在等你」。
> **回答的 UI 没做**——它要处理多问 / 混合类型 / 改写参数 / remember 两档，
> 而一个只能填第一个问题的表单**比没有更坏**（用户以为答完整了）。
> ⇒ 今天回答走控制台：`approval allow|deny|cancel|answer <会话> <askId> …`。

### 7.4 安全轴（义务 4）

在轴面板里**最显眼**，且**跨轴告警**：`安全=生产` + `权限≥授权` → **右栏告警**（[`01` §3.5](01-会话设计.md) 定的那条）。

## 8. 附件

⚠️ **协议是两步**（[`03` §9.1](03-控制面协议.md)）：先上传、再发送。**头负责把用户的动作拆成这两步。**

```
拖拽 / 粘贴 / 选择
   → POST /files?sessionId&path?  → { ref }
   → session.send(sessionId, [ {text}, {attachment, ref} ])
```

⚠️ **头不判断"这个文件该进库还是进工作区"** —— 路由判据是**提供商配置里的模态能力声明**（[`03` §9.2](03-控制面协议.md)），**核心的事**。

⚠️ **但头必须显示路由结果**（[`03` §9.2](03-控制面协议.md) 硬要求）："进了工作区，路径是 X"。

⚠️ **上传失败时 `ref` 不落草稿**——[`03` §10](03-控制面协议.md) 的孤儿对象靠引用计数回收，但头不该主动制造孤儿。

## 9. 控制点：通用渲染

[`04` §3.1](04-插件与内部结构.md)：插件**声明控制点（数据）**，头**通用渲染**（按钮 / 下拉 / 开关）。

```
插件声明：{ id: "clearCache", label: "清空缓存", 参数: [...] }
头渲染成：按钮 / 下拉 / 开关          ← 头自己决定
```

⚠️ **头的义务到此为止**：插件**不带 UI**（[`00` §8.9](00-设计哲学.md)），头也不为任何插件做定制渲染。

⚠️ **但本文必须指出：这条路目前不通。** [`03`](03-控制面协议.md) **既没有列控制点的端点，也没有回调的命令**——头拿不到清单，也点不了按钮。**这是头的设计的第一个前置依赖**（§11）。

## 10. 头不做的事

| | 为什么 |
|---|---|
| **不保存业务状态** | 头无状态（[`03` §1](03-控制面协议.md)）；连"选中哪个会话"都只是视图 |
| **不重新实现渲染** | 本文件 §3 —— 渲染归核心 |
| **不做本地历史** | 历史在核心；头只有一次快照 + 增量 |
| **不做部分合并** | §6.2 —— 降级只有"拉快照重建"一条路 |
| **不判断附件路由** | §8 —— 归核心 |
| **不给插件做定制 UI** | [`00` §8.9](00-设计哲学.md) 已作废 |
| **不做请求 / 响应配对** | [`03` §10](03-控制面协议.md) —— 命令投递即返回 |
