# 上下文统计（核心设计草案）

日期：2026-10-16。对应实现：`772c83e`（统计与头部）及 `75efa1a`（正式压缩）。状态：第一批核心实现已落地，预估、阶段和账单仍未实现。

本设计以核心为本体。核心保存模型调用产生的 token 事实、来源与模型维度的聚合、当前会话的上下文统计快照，并通过查询和事件接口暴露。头是这些接口的一个消费者：可以做统计页，也可以在会话页显示实时状态，但不拥有统计真相。

当前已实现：三协议响应的基础 usage 归一化、追加式 `UsageStore`、会话调用与 provider 探针记账、来源/模型聚合、核心 HTTP 查询、会话流 `usage.updated` 事件、头部统计 tab，以及会话页最近一次实际输入 token。当前上下文接口提供最近一次实际报告，`Preview` 仍为空；尚未实现本地 tokenizer 预估、阶段标记和真实账单。正式压缩的独立闭环已在 `75efa1a` 落地，但不改变本设计中“统计不拥有压缩策略”的边界。

## 1. 范围

### 核心必须提供

| 能力 | 核心事实 |
|---|---|
| 单次调用用量 | 每次模型调用的输入 token、输出 token，以及协议提供的缓存/推理明细 |
| 调用归属 | 会话、项目、provider、模型、协议、调用用途、时间、步和调用结果 |
| 聚合查询 | 按时间、来源（provider）、模型、项目、会话和用途聚合 token |
| 上下文快照 | 最近一次实际请求的输入 token、统计来源、测量时间和请求指纹 |
| 当前上下文估计 | 基于核心实际渲染规则的只读估计；无法可靠测量时返回未知 |
| 阶段事实 | 模型声明的任务阶段，以及协议提供的消息回复阶段；两者分开保存 |
| 变化事件 | 调用开始/结束、用量更新、上下文快照更新、阶段变化 |

### 明确不属于核心

- 费用、余额、充值、上游账单同步和扣款核对。
- 价格表、币种换算、费用预算和“节省了多少钱”的反事实估算。
- 统计页、图表、筛选器、会话页布局、颜色和刷新策略。
- 自动压缩、自动换模型、预算硬拦截以及基于统计的调度策略。

核心可以保留可选的账单适配接口，但没有实际账单来源时只返回 token，不能伪造金额。账单接入应是独立模块，不改变核心调用与上下文事实的格式。

## 2. 现有代码的接入点

- `Protocol/ModelCall.cs` 的 `ModelReply` 目前只有 Blocks、StopReason、Refused；三个响应映射器需增加可空的标准化 usage 和协议原始摘要。
- `Session/Stepper.cs` 是实际请求的装配点；上下文快照必须对应这里冻结的提示词、时间线、工具定义和轴快照。
- `Hosting/CommandDispatcher.cs` 还存在 provider 连通性探针；所有模型调用入口都要经过同一个核心记账器，不能只在 Stepper 记账。
- `Hosting/SessionQueries.cs` 和 `Control/ControlServer.cs` 是查询投影的现有边界；读取统计不能激活会话、运行插件或触发模型调用。
- `OpenAiResponsesResponse.Map` 当前将 output 展平为 Blocks；若协议消息带阶段，需要在 canonical 消息边界保留阶段，不能在头部从正文猜测。

## 3. Token 口径

### 3.1 单次调用

核心账本单位是一次**可观察的模型调用尝试**，而不是一条用户消息。记录至少包含：

| 字段 | 说明 |
|---|---|
| `callId` | 核心生成的稳定调用 ID；与工具 `tool_call_id` 分开 |
| `sessionId` / `projectKey` | 会话调用必填，探针等调用可为空 |
| `step` / `purpose` | 所属步和用途，如 `session`、`probe`、`summary` |
| `providerId` / `modelId` / `protocol` | 实际发送时的来源和模型，而非仅会话初始配置 |
| `startedAt` / `endedAt` | UTC 时间；耗时为核心测量值 |
| `status` | `started`、`completed`、`failed`、`cancelled`、`unknown` |
| `usage` | 归一化 token 及各协议可提供的明细，缺失字段保持未知 |
| `rawUsage` | 有界的协议原始 usage 摘要，用于诊断，不保存完整响应 |
| `requestFingerprint` | 请求内容版本指纹，不保存 API key、认证头或完整正文 |

`inputTokens` 和 `outputTokens` 是首要字段。缓存读取、缓存写入、推理 token 等只作为可选明细；它们若已包含在协议总量中，不能再次加到总量。零、不适用、未报告和调用尚未结束必须可区分。

调用超时、取消或连接断开不代表上游没有处理；只有开始记录没有结束记录时，核心应保留 `unknown` 用量。正文映射失败、拒答或后续工具失败都不能抹掉已取得的 usage。

### 3.2 来源与模型统计

聚合至少支持以下维度，并允许组合筛选：

- 时间范围（原始时间保留 UTC，展示层自行选择时区）。
- `providerId`、`modelId`、`protocol`。
- `projectKey`、`sessionId`、`purpose`。

聚合结果必须同时返回调用数、已知/未知用量数，以及 `inputTokens`、`outputTokens` 和明细 token 的和。存在未知记录时，结果称为“已知合计”，不能返回看似完整的零值总额。探针进入核心总账，但通过 `purpose` 可排除。

账本追加写入，汇总可从账本重建。事件重复投递不能重复计入；核心应以 `callId` 和事件版本幂等。删除会话不应默认删除已发生的 token 事实，可将关联标记为来源已删除。

## 4. 上下文长度

### 4.1 最近一次实际长度

一次调用结束时，核心记录对应请求的上下文测量：

```text
ContextMeasurement {
    inputTokens: long?
    source: reported | counted | estimated | unknown
    measuredAt: timestamp
    modelId: string
    protocol: string
    requestFingerprint: string
    counterVersion: string?
}
```

上游报告优先于本地估算，但必须关联同一个请求指纹。没有可靠计数时返回 `unknown`，不能用字符数或 HTTP JSON 字节数冒充 token。

### 4.2 下一步估计

核心可提供只读的 `context.preview` 查询，复用真实请求的渲染规则，至少覆盖系统块、首要块、历史、工具定义、工具结果和浮动槽位。该查询不得执行 Stepper、插件副作用、文件回收或模型调用。

如果无法保证插件贡献和外部预设读取是纯的，核心只返回最近一次实际测量，并标记可能过时；不要为了刷新统计偷偷执行一次完整推进。

预览结果与实际调用一样携带来源、测量时间、模型/协议和请求指纹。窗口上限、输出预留和容量百分比只有在模型能力数据明确时才提供；`MaxTokens` 不能当作窗口上限。

### 4.3 构成

核心可返回互斥的归因项，供头决定如何呈现：系统、首要、工具定义、历史正文、工具调用参数、工具结果、推理/协议载荷、多模态、浮动。上游通常只报告总输入，分项属于本地归因；若分项只是估算，必须携带来源，不能宣称实测。

## 5. 两种阶段事实

阶段不等于执行状态、权限轴或完成条件。`Running`、`WaitingForInput` 等框架状态继续由现有状态机维护。

### 5.1 任务阶段

模型通过结构化机制声明任务阶段，例如调研、设计、实施、验证、收尾。核心记录阶段标记和区间：阶段代码、公开标题、来源（模型/用户/框架）、时间、关联 step 和前一个标记。重复标记可幂等，阶段可回退和重复，首次声明前为 `unknown`。

调用按**开始时的任务阶段**归属；本次输出声明的新阶段从下一次调用生效。核心不从普通正文猜阶段，也不把阶段自动转换成停止、压缩或释放动作。

### 5.2 协议回复阶段

提供该字段的协议可在 assistant 消息或消息项上携带回复阶段，例如 `commentary`、`final_answer`。核心必须保留原始值、消息边界和顺序；缺失就是 `unknown`，不默认填成最终回答。

协议回复阶段与 `StopReason`、`finish_reason`、任务阶段各自独立。一次响应可能包含多个消息项或不同阶段，不能把 `ModelReply` 设计成单一 phase 字段。目标协议不支持该字段时，核心返回“未提供”，回放时由适配器按能力投影。

## 6. 核心接口提案

只读接口建议放入现有控制面，具体路径可在实现批次定稿：

```text
GET /usage/calls?skip=0&limit=100 # 分页的单次调用账本
GET /usage/summary               # 全局/按来源/模型/项目/会话聚合
GET /sessions/{id}/usage         # 会话 token 总览与最近调用
GET /sessions/{id}/context       # 最近实测、下一步预估、构成和来源
GET /sessions/{id}/phases        # 任务阶段与协议回复阶段，分开返回
```

查询返回 `asOf` 或账本游标，保证分页明细和聚合能够对账。事件主题建议包含：

```text
usage.call.started
usage.call.completed
usage.context.updated
session.taskPhase.changed
session.messagePhase.recorded
```

头重连时用快照和游标重建，不需要核心知道头是否在线。控制台、未来的其他头和脚本应能使用同一组接口。

## 7. 头的体现方式（不属于核心模型）

头可以把核心接口呈现为独立的“统计” tab，与会话、提供商并列：调用明细、按来源/模型筛选的 token 汇总、未知记录提示、上下文趋势和阶段分布都属于头的布局选择。

会话页可订阅 `usage.*` 与阶段事件，在顶部实时显示“上次输入 token / 当前预估 token / 来源 / 测量时间”。刷新失败时保留旧值并显示过期，不在头部自行估算或发起隐藏调用。

图表、颜色、分页大小、时区、是否显示缓存明细以及是否将任务阶段和回复阶段放在同一视图，都由头决定。头不能把估算值改写成核心事实，也不能把账单价格混入 token 总量。

## 8. 可选账单适配（后续）

账单不是 token 统计的前置条件。后续若接入实际账单，适配层按 `providerId`、上游账单 ID、时间段和币种返回独立记录，并通过调用 ID 或时间/模型关联；关联失败时仍保留原始账单，不回写或覆盖核心 token。

核心最多暴露“调用可关联”的接口，不保存充值余额、不做扣款判断、不把本地价格估算称为实际账单。没有实际账单适配时，所有界面只显示 token 和“费用未接入”。

## 9. 实施顺序与验收

1. 扩展三协议响应映射，保留可空 usage 和原始摘要；用统一调用记录器覆盖会话调用与 provider 探针。
2. 增加追加式 `UsageStore`、幂等终态、重启可重建的来源/模型聚合和核心只读查询。
3. 在步开始/结束发布调用和上下文事件；先实现最近一次实际输入 token，再实现无副作用的预估。
4. 在明确消息边界后接入任务阶段和协议回复阶段，增加旧记录兼容与金样测试。
5. 头单独增加统计 tab，并在会话页订阅实时 token 状态；这些只消费核心接口。

验收必须覆盖：三协议有/无/部分 usage、缓存和推理明细不重复加总、失败/取消/超时、正文映射失败、探针计费、多会话并发、事件重放幂等、重启聚合一致、旧会话未知、上下文指纹对应实际请求、阶段重入及无 phase 回放。

账单适配、价格估算、自动优化和预算执行不阻塞前五步。
