# 会话设计

> 本文只涉及**单个会话**（§13 的 core 级已定项除外）。
> 母原则见 [`00-设计哲学.md`](00-设计哲学.md)，多会话调度见 [`02`](02-多会话调度.md)，控制面协议见 [`03`](03-控制面协议.md)，进程结构见 [`04`](04-插件与内部结构.md)。

---

## 1. 术语

| 术语 | 含义 |
|---|---|
| **核心** | 常驻进程，**本设备（至少本用户）唯一**，管理全部会话资源 |
| **会话** | **一个 agent 循环体**。本文的主题 |

**「实例」一词废弃**。它源自"可能多开"的假设（如两个 Claude Code 程序），而本项目核心是唯一的。

---

## 2. 会话是什么

> **会话 = 提供商配置 ⊗ 结构化记录**

两半都是**数据**，无行为。行为发生在发请求的那一刻。

**核心推论**：**会话是数据，推进是过程。**

| | 会话 | 推进（Run） |
|---|---|---|
| 性质 | 持久数据 | 过程 |
| 资源 | 不消耗 | 消耗 |
| 寿命 | 无限制 | **受能力边界约束**（§3.5），**而非受"预算"约束** |

这一条一口气解掉 ALP 的四个问题：

| ALP 的问题 | 本项目的解法 |
|---|---|
| 无强制 stop，working 会话可能失控 | 会话不限寿命（**它只是数据**）；推进由**能力边界**约束（工具表 / 权限闸门 / 循环控制，§3.5），**而非预算** |
| 重启恢复要判 `status ∈ {Running, Crashed}` | 每步落盘 → **任何记录都可续**，不需要状态判定 |
| 父死清理子链，子的工作丢失 | 父停 → 子**停止推进**，记录还在，可重新唤醒 |
| 空闲会话占资源 | 不占，它躺在磁盘上 |

> **"停止"要拆成两个**：停**推进** ≠ 停**会话**。ALP 把两者混在一起，所以必须用 `ColdTimeoutSeconds` 杀会话这种粗暴手段。

## 3. 记录的形状

> **记录 = 事件时间线 + 两个固定槽位（头、尾）**

| | 是什么 | 载荷谁渲染 | 持久化 |
|---|---|---|---|
| **头槽位** | **两个块：系统提示词 + 首要提示词** | 提示词装配器 | ❌ |
| **时间线** | 用户/模型发言、工具调用 | 发言＝具体文本；工具＝**工具自己** | ✅（工具结果见下） |
| **尾槽位** | 浮动上下文（字段集） | 贡献者集合 | ❌ |

⚠️ **时间线的 `✅` 有个例外：工具结果的「快照」是可回收的**——见 [`00` §5](00-设计哲学.md)（结果 = 引用 + 快照 + 指纹）与 [`00` §4](00-设计哲学.md)（快照是**头号可回收物**）。**骨架（引用 + 指纹）永久，快照只在想保缓存时才有价值。**

⚠️ **这条例外今天没有对应实现**（工具不存在）。两条**已经定下来的后果**：
**① 工具记录要有自己的 `TimelineEvent` 派生类型**（塞进共用的 `Block` 会在类型层面与用户文本不可分）；
**② 回收只动注入、不动持久化**，且**可恢复**（`fetch(id)`）。
形状契约见 [`§3.6`](01-会话设计.md)，生命周期契约见 [`§8.0.2`](01-会话设计.md)。

**关键区分：槽位不是事件。** 它们不在时间线上，是"每步现算"的两个位置。

这解释了"浮动像水面永远在表面"——**它本来就是个槽位而非消息**，所以替换成本恒定、**在 `Auto` 模式下永不累积**。首要提示词同理。

⚠️ **"永不累积"只在浮动模式成立**（`Auto`）。**降级**模式下（`00` §2.4：切换为普通上下文每步追加，用于 Responses 这类"链不可逆"的协议）它就是普通消息，**会累积**——这也正是降级的代价所在（`00` §2.5「`Always` / 降级的代价 ∝ 浮动体积」）。

### 3.1 头槽位：恒定的两个块

**块数恒定**：系统提示词 1 块 + 首要提示词 1 块。**无论多少插件贡献，协议看到的块数固定**——多个插件的贡献由装配器**自动拼合**。

⚠️ **恒定 = 「最多各 1 块」，不是「非有不可」。** **没有任何贡献者时头槽位就是空的**（[`04` §1.3](04-插件与内部结构.md)）——**裸核心是纯 chat，连系统提示词都没有**。这与"多个贡献必须合并成 1 块"是同一条约束的两头。

⚠️ **「空」今天可以是被选的**（2026-10-07）：系统块的**内容**是一个核心提供的文件，
而**它可删、可换**（预设的一个字段）⇒ 「我要纯聊天」是一个**合法的预设值**，不是缺省故障。
⚠️ 由此与 [`04` §1.3](04-插件与内部结构.md) 的「`ls`/`read` **不可卸载**」**不冲突**，两者说的不是一件事：
「不可卸载」防的是「**把编译器做成可选项**」（那判据是对协议适配器的：做成可卸载等于把「能跑」变成可选项）；
**具体某个预设有哪几条工具，是配置**。⇒ **纯聊天预设 = 空提示词 + 空工具表**，一句话都不用解释。

```
头槽位 = [系统提示词块][首要提示词块]
```

| | 系统提示词 | 首要提示词 |
|---|---|---|
| 回答 | 你是什么、能做什么 | 你要怎么做 |
| 内容 | agent 能力、全局约定 | 人设、项目约定、预设 |
| 随谁走 | 核心（与工具表一一对应） | 用户 / 项目 / 插件 |
| 变更频率 | 核心版本 / **用户改那个文件** | 项目 / 用户配置 |
| 失效半径 | **用同一个变体的那些会话** | **只废自己** |

⚠️ **两块的可写面不对称**（2026-10-07 裁定）：**系统块是核心提供的恒定单文件，插件不可注入**；
**插件贡献一律进首要块**。理由不是安全（插件的工具表本来就在位置 0）——是**位置 0 应当是一份
与核心版本同生共死、可审计的字节**，而「系统提示词该说什么」在 [`00` §2.2](00-设计哲学.md) 里
本来就限定为「**没法挂在单个工具上的全局约定**」，那是**核心的**约定。
⇒ 插件一个字都没损失：它想加的那类约定（「大改前先声明」）按本节的分工本来就住首要块（「你要怎么做」）。

⚠️ **「失效半径 = 全设备」改过**（2026-10-07）：原文是「全设备」，那**预设了所有会话位置 0 相同**。
而**会话可按任务类型选不同的系统提示词**（预设的一个字段，见 §7.1 / §10.3）⇒ 位置 0 改为
**按变体分片**：同一个变体的会话仍然共享（这才是分片，不是各自为政），跨变体本来就不该共享——
两套完全不同任务的提示词混着缓存，省下的缓存换不来答对。
⇒ 本节的核心原则**没有破**（「块边界 = 失效爆炸半径的边界，**该一起失效的才进同一个块**」），
只是把「该一起」的粒度收细了。

**系统提示词是最贵的缝**（位置 0，改它全废），所以：**放这里的贡献，不许随「每步都在变的东西」变。**
⚠️ **这句改过**（2026-10-07）：原文是「必须在会话期间**恒定**」，而它与**同节下面那句**
（「变更时机 ⊂ 已经要失效的时机…**这些都改变重建区的内容，因此本来就全炸**」）
**互相否**。判据按**触发源**切，不按「变不变」切：

| | 每步都变 | 外力才变 |
|---|---|---|
| 例 | 时间 · 上下文长度 · 尾槽位字段 · 轴当前值 | 核心升级 · 插件增删 / 热重载 · 用户改配置 · 换预设 |
| 进头？ | ✗ —— **每步**破位置 0，每步全废 | ✓ —— 只在那一刻废一次 |
| 后果 | **渲染不纯**（签名漏了输入，见 §3.2 的 `now` 冻结） | **一次正常的失效窗口** |

⇒ 用户「头铁要改」是**合法**的，它落右边那一格；而**那个窗口正是 [`00` §4](00-设计哲学.md) 的 GC 触发源之一**。

⚠️ **没有"贡献者优先级"这种东西，只有显式声明的装配顺序。** 装配器是**渲染器**，服从 [`00` §5](00-设计哲学.md) 铁律 1：

> **同一个贡献者集合 → 同样的字节。**

否则顺序一旦不确定（目录扫描顺序、字典迭代序、插件加载先后），**每步重排 → 每步破位置 0 的前缀 → 每步全废**——全系统最贵的崩法。

**排序规则（纯派生，不持久化）**：

```
sort by (priority, pluginId)      ← 两个键都来自插件自己的 manifest
```

⚠️ **核心不持久化任何顺序状态。** 顺序永远正好等于"插件集 + 排序规则"，**不可能失配**（见 [`00` §7 判据 8](00-设计哲学.md)）。

⚠️ **不追求"无扰动"**：既然插件变化必然炸缓存（见下），**已有序成员被扰动与否毫无价值**。所以**不需要安装序号之类的持久化计数器**。

⚠️ **变更时机 ⊂ 已经要失效的时机。** 插件增删 / 热重载（[`04` §7](04-插件与内部结构.md)）/ 配置变化 / 贡献形状变化——**这些都改变重建区的内容，因此本来就全炸**。顺序重算从不额外制造一次失效。

**前缀指纹**（见 [`04` §7.3](04-插件与内部结构.md)）：

> **指纹变了 ⇔ 缓存必然失效。** 不是"猜会失效"，是**同义反复**。

它只覆盖**重建的那些部分**（工具表 ∥ 系统块 ∥ 首要块）——历史是追加的（§4），结构上不会破前缀；GC / release / compact 是显式事件，各有处理。**指纹顺手吃掉了上面那份变更枚举**：不需要枚举，也就不会漏。

⚠️ **能进工具描述的，绝不进系统提示词。** 工具描述与工具同生共死、随核心版本发布、不会被 fork 掉；系统提示词是可替换内容，只留**没法挂在单个工具上的全局约定**（如"声明宜粗不宜细"）。
⚠️ **但「可替换」的是用户的替换权，不是插件的**（2026-10-07，理由与 [`00` §2.2](00-设计哲学.md) 那段合并写在一起）：系统块**可删、可换**（预设的一个字段），**插件不可注入**——插件贡献一律进首要块。

### 3.2 尾槽位：字段集，不是自由文本

贡献者提交 `(字段名, 值)`，装配器拼成一个块：

```
态势：时间 · 步数 · 用量
策略：主动性 · 权限 · 安全 · 验证强度        ← 六轴，见 §3.5
其他：<插件贡献，命名空间隔离>
```

- **同名字段归并**而非拼接 → 三个插件都塞时间，**不会变成三份**
- **位置稳定** → 同名字段永远在同一处
- **可裁剪** → 按模式（[`00` §2.4](00-设计哲学.md) 的浮动开关）/ 预设决定显不显示
- 核心预留一组，插件用命名空间（`persona.mood`）

**两条硬约束**：

| | |
|---|---|
| **有界** | 它在时间线**之后**，而时间线每步都在长 → **在浮动模式下永远不可能被任何缓存覆盖，每步全价支付**（降级模式下更贵：还会累积）。**每步成本 = 它的体积**，全系统唯一一处"体积 × 步数"线性放大 |
| **可信来源** | 尾槽位紧贴生成，**注入杠杆最高**。只有核心 / 插件能贡献；**绝不原样透传文件字节**——脏文件状态是"路径 + 哈希 + 时间"这样的**字段** |

⚠️ **`now` 冻结在步开始**：渲染是纯函数，而"当前时间"不是纯输入 → 签名 `render(贡献, now)`，`now` 步开始取一次并冻结，**同一步内**重复渲染逐字节相同。

⚠️ **策略是告知，不是要求**：浮动说"当前串行执行"，是让模型**知道自己处在什么环境里**；真正的约束在机械层（并发由核心定、工具表由核心定）。

### 3.3 归位规则

| | 去哪 |
|---|---|
| **状态**（"是"什么） | **槽位** |
| **事件**（"发生"了什么） | **时间线** |

**状态天然可被覆盖，事件天然不可变**——正好对上两个位置的性质。插件问"我这条该放哪"，答案就是这一个问句。

⚠️ **头尾不该出现同方向的内容**——出现了是**归位错误**，不是优先级问题。**拦不住，但看得见**（头的 UI 原样显示两个槽位）。真出现时以最新的为准（recency 天然如此），**不为此写优先级规则**（见 [`00-设计哲学.md` §8.8](00-设计哲学.md)）。

### 3.4 载荷的两种形态

时间线上每个事件的载荷是一串**块**，**每块各判形态**：

| 形态 | 含义 |
|---|---|
| **具体** | 内容即渲染结果（用户说的话、模型说的话）——不可变 |
| **托管** | 内容是个引用，**构造时向所有者要**（工具、插件、库对象） |

⚠️ **是逐块判定，不是逐事件。** 一条用户消息天然可以是混合载荷：

```
用户消息 = [ { text: "看看这个报错", 具体 } , { image: sha256:…, 托管 } ]
```

"工具在构造记录时自己返回一个块"就是**托管**机制。它同时是**插件 API 的表面**：插件选槽位（头/尾）还是选时间线（中段），就是选生存期。

### 3.5 行为控制轴

> **尾槽位存在的真正理由：它是行为控制面板。** "浮动上下文就是为了这一碟醋包的饺子。"

Claude Code 把这类东西做成**互斥的枚举**（`default` / `acceptEdits` / `plan` / `bypassPermissions`）。本项目把它拆成**正交的轴**——可独立调配，也覆盖枚举表达不了的组合（如"目标 + 只读"= 调研任务）。

#### 轴

> ⚠️ 这个标题原先叫「六条轴」——**条数不写在这里**：表就在下面，数一眼的事；
> 而写一个数就要有人记得加轴时同步它（它已经错过一次，`temperature` 加进来时没人跟着改）。
> 轴的条数只有一处出处：`Kernel/Axes.cs` 那张表。

| 轴 | 取值 | 机械层 | 进浮动 |
|---|---|---|---|
| **主动性** | 步进 / 标准 / 目标 | **循环的停止条件** | 部分 |
| **权限** | 0 禁用 … 5 信任 | **闸门** | 部分（告知当前档位） |
| **安全** | 开发 / 迭代 / 生产 | ❌ | ✅ 全部 |
| **验证强度** | 无 / 自检 / 严格 | ❌ | ✅ 全部 |
| **思考强度**（effort） | 低 / 中 / 高 | **请求参数** | **❌ 完全不进** |
| **温度**（temperature） | 0.0 … 2.0（步长 0.1） | **请求参数** | **❌ 完全不进** |

> ⚠️ **实现（2026-10-05）**：effort 实为 **5 档** `low / medium / high / xhigh / max`，且
> `Axes.cs` 与 `ClaudeRequestBuilder.ToEffort` 两处字面量互相钉死。上表的「低/中/高」是设计值。
>
> ⚠️ **温度是后来加的第六根轴**（同日），且它是**第一条「数值范围」轴**（不是枚举档）。
> **这和上面「纯请求参数」那句话不冲突**：effort 早就证明了「纯请求参数」是一种**合法的轴形态**，
> 温度只是又一个同侧的（`InContext: false`）。范围 `[0, 2]` 是**实测**的（本机网关对 2.5 回
> `valid range of temperature is [0, 2]`），值与 effort 一样住在 `state.json` 的 `axes` 里。

#### 主动性 = 循环何时停止

| 档 | 含义 | 机械定义 |
|---|---|---|
| **步进** | 用户说一步，模型动一下 | ⚠️ 需要**显式启动**才推进（§6.1） |
| **标准** | 自主行动，遇需决策处征询 | **自然停止**（模型不再产生动作） |
| **目标** | 完成前不停，自己权衡，不询问 | 模型不产生动作也**强制继续**，直到显式声称完成 |

⚠️ **「目标」把循环权交给了模型，而循环是核心在跑的。** 头离线时，这是整个系统**唯一的无限循环风险**——不是"任务天然长"，是"**没有进展也不停**"。需要核心侧的**最大连续步数熔断**。

> 那是**循环控制**，不是预算——判据是"有没有进展"，不是"花了多少"。

#### 权限 = 闸门，工具仍在

| 档 | 只读 | 消耗 | 写入 | 高危 |
|---|---|---|---|---|
| **0 禁用** | 拒 | 拒 | 拒 | 拒 |
| **1 只读** | 通 | 拒 | 拒 | 拒 |
| **2 调查** | 通 | 通 | 拒 | 拒 |
| **3 标准** | 通 | 通 | **问** | 拒 |
| **4 授权** | 通 | 通 | 通 | **问** |
| **5 信任** | 通 | 通 | 通 | 通 |

**结构上它是一条单调阶梯：每升一档，只移动一个边界。** 低档是**拒绝线**（硬），高档是**询问线**（软）——*档位 = 那条线在哪*。

⚠️ **实现（2026-10-07）——两处「问」今天实现成「拒」，这是刻意的降级**：

| 格 | 表里 | 今天 |
|---|---|---|
| `标准(3)` × 写入 | **问** | **拒** |
| `授权(4)` × 高危 | **问** | **拒** |

⚠️ **理由：「问」要转 `WaitingForInput`，而那个状态从来没有被写过**
（[`03` §4](03-控制面协议.md)：`approvals` 流零生产者；`SessionStatus` 全 `src/` 只写 `Idle`/`Running`）。
⇒ 本批只做**拒**那一半，审批**单独一批**（用户裁定）。

⚠️ **代价要认**：默认档位是 `standard`，而它的写入格本该是「问」——
降级成「拒」意味着**默认档写不了任何东西**。今天**看不出来**（三个内建全是只读，
闸门对它们永远是 no-op）；**第一个 `Writing` 工具落地时它立刻变成可见的瓶颈**。

⚠️ **所以「问」的截止线是：第一个 `Writing` 工具。** 在那之前它是空的，
在那之后它是**默认档能不能干活**的开关。⇒ **两者必须同批落地**。

⚠️ **而这一格不许用「静默降级」实现**：拒绝理由里要能看出**本该问**还是**档位不够**
（今天两者都印"档位不允许"——**这是本批的已知不精确**，记在这里，别当成完备）。

⚠️ **工具仍在，被调用时才拒。** 这是为了缓存：调整权限 = **改一个浮动字段**，零前缀代价、即时生效。**CC 做不到**（它的模式切换要么破前缀，要么重启）。

⚠️ **拒绝也必须产生 `tool_result`** —— [`00` §5](00-设计哲学.md)「一块的两面」是结构性的。形状：

```
tool_result: "当前权限为「只读(1)」，写入类工具不可用。"
```

「弹授权请求」那个变体 = **转 `WaitingForInput`**，与 §10.3 的审批流是同一条路。

**高危的判据 = 不可逆**（`git push` / 发邮件 / 删库）。这正是"确保操作可逆"那条守则在权限层的体现——**不可逆是最后一个被自动放行的东西**。

#### 工具自报类别

闸门需要知道工具的类别，而**工具自己最清楚**。落点就在 [`00` §5](00-设计哲学.md) 的钩子契约里——加一个**静态声明**：

```
PermissionClass = ReadOnly | Consuming | Writing | Destructive
```

闸门按 `档位 × 类别` 查表。**核心不维护一份"哪些工具危险"的清单**——那清单会腐烂（[`00` §1.3](00-设计哲学.md) 谁的知识谁负责）。

#### 安全：纯提示，标准化 = 防遗忘装置

> **安全不是机制，是提醒装置。** 它存在，是因为"用户忘了告诉模型这是生产环境"经常发生——删库新闻基本都源于此。

- 价值全在**可见性**，UI 应当**显眼**，而不是藏在配置里
- 跨轴提示（不联动）：`安全=生产` + `权限≥授权` → 告警
- 天然是**项目级**的（"这个仓库是生产系统"是仓库属性，且可分享 → `.lilara/config.json`，§8）
- ⚠️ **不设机械兜底**（如"生产 ⇒ 权限封顶"）——那是家长式干预，且会掩盖"安全是建议"这个诚实的定位

#### 验证强度：纯提示，但藏着一个礼物

| 档 | 含义 |
|---|---|
| **无** | 不验证，改完就报 |
| **自检** | 改完自己跑编译 / 相关测试 |
| **严格** | 必须跑完整验证；**验证未过，不得声称完成** |

> **「目标 + 严格」= 停止条件从「模型说完了」变成「验证过了」。**

这是**唯一一处**跨轴产生机械性的地方，且不新增机制——**验证本身就是一次工具调用，它的结果就是判据**。

> ⚠️ **这句原文是「这是五条轴里唯一一处…」，而轴早已是六条**（`temperature` 加进来时这里没跟上）。
> 写法已改：**不说条数**——「唯一一处跨轴产生机械性」这句话的**判据与条数无关**，
> 而写一个数就要有人记得同步它。**凡是「判据不依赖那个数」的地方，就别写那个数。**

#### 思考强度（effort）：纯机械轴，压根不进上下文

走**请求参数**，模型不必被告知自己的**推理预算**——行为机械地跟随参数。（⚠️ 这是**模型侧的推理预算**，与 §6.2 规矩 1 那个"核心不做预算"——**成本预算**——不是一回事。）

⚠️ **区分「态势」与「参数」**：**模型身份是态势**（模型要能回答"你是谁"，该进浮动）；**effort 是参数**（不进浮动）。告知 effort 是纯粹的浪费——它是全系统每步都付全价的槽位。

#### 两个独立的维度

> 一条轴可以「**有机械层 / 无**」，也可以「**进上下文 / 不进**」——**两者独立**。

**给头看 ≠ 给模型看。** effort 两边都走极端（全机械、零暴露）；安全与验证强度反过来（零机械、全暴露）。中间是主动性与权限（各有部分机械层，且需要告知模型当前状态）。

#### 谁能改

**模型不能自提权，只能请求**——而这正是 §10.2「要我决策」事件的又一个来源。

**子会话沿树收窄的是「档位」，不只是工具集**（见 §10.3 的委托表）。

#### 扩展

**轴 = 浮动字段族 + 可选机械层。** 插件加轴用命名空间（§3.2 已有 `persona.mood` 这种形式），不新增机制。**后话。**

### 3.6 工具记录的形状（**已实现**——2026-10-06 最小工具批 + 回收批）

⚠️ 本节原先写着「**未实现**」。工具批之后它**实现了**：这一节记的那几条硬约束
（① 不能是 `Block` ①之一/①之二 一串块不许折 ② 一对不能拆 ③ 步原子性 ④ 落盘顺序
+ 结果三件）**逐条落到了 `ToolResultEvent` / `ToolExecutor` / `HistoryLog.AppendMany` 上**，
各条下面都跟着「⚠️ 实现（…）」的注记。

**① 工具结果不能是 `Block`。**

`Block.cs` 的头注释规划的是「图片 / 工具调用 / 工具结果按同样方式追加 `[JsonDerivedType]` 即可」——**那个规划有个洞**：Claude 协议里 `tool_result` 住在 **user 角色**的消息里，把它塞进共用的 `Block`、配 `MessageEvent.From = User`，它在**类型层面与用户文本不可分**——而「用户消息是具体载荷、永久」（§3.4）是全系统的硬约束。

⇒ **工具记录要有自己的 `TimelineEvent` 派生类型**：引用 / 快照 / 指纹 / 类别，`Block` 一样都装不下。

⚠️ **「类别」那个字段**（[`00` §5](00-设计哲学.md) 的三分）**不是 GC 用的**（[`§8.0.2` 第三节](01-会话设计.md)已经把它从 GC 里摘出去了）——它是**三态判定**（指纹 / 脏）的输入。
但它**照样不能挂在 `Block` 上**：`Block` 是用户与模型共用的，用户贴的大图与模型的文本块落进同一批派生类型，**任何「只对某类发言成立」的属性都无处安放**。
⇒ 这条与「工具结果不能是 `Block`」是同一个理由的两面，就在这一刀里一起解。

**①之一、工具结果的内容是一串块，可混排、也可纯图。**

**三种形态缺一不可**，而这不是新设计——协议里 `tool_result.content` 本来就是**块数组**：

| 形态 | 例 |
|---|---|
| **纯文本** | `read` |
| **纯图** | ⚠️ `screenshot` 这类工具**只有图、一个字都没有** |
| **混排有序** | 「这是那张图」+ 图 |

⇒ 这是「工具结果不能是 `Block`」的**进一步收紧**：它甚至不是**一个**块，是一**串**。
⚠️ **协议细节**：只有一个文本块时，有些 API 要的是**字符串**而不是数组 ⇒ 那是**适配器的减法**（[`00` §6](00-设计哲学.md)：核心全量，适配器做减法），canonical 只管数组。

**①之二、⚠️ 图文**永远不许**折成一段文本。**

协议把「图文」表示成**数组**（一条消息 = 块列表），不是一个块里塞文字和图片。⇒ **文本与图片永远是兄弟块**，渲染时**逐段映射**。

⚠️ **「折成一段话」是最省事的实现，而它恰好毁掉降级**：

```
✅  [text: "报错在这里"] [image: store/abc…]
    图被回收 ⇒ [text: "报错在这里"] [注记]
    ⇒ 模型知道「这里有张图，没了」，也知道自己当时指的是哪儿

❌  [text: "（图：报错在这里）"]        ← 一个块，模态糊了，降级无从下手
```

**折了之后只有两种结果，都坏**：整块留着 ⇒ 那段文字**变成了模型自己编的**（图上写着 42，而图已经不在了）；整块降级 ⇒ 连用户/模型**打的字一起丢了**。

⇒ **最坏的一种失败不是少了信息，是多了一条假信息。**

折成字符串同时丢掉的还有：**块的边界**（引用 / 指纹挂在字节上，[`00` §5](00-设计哲学.md) 的三态判定对不上）· **顺序**（图文对照错位）· **每段的模态**（无法逐段降级）。

⚠️ **两条「不许折」的理由不同，别压成一句**：

| 对象 | 会降级吗 | 为什么仍不许折 |
|---|---|---|
| **工具结果** | ✅ | 折了之后图没了而**描述还在** ⇒ 多一条**假信息** |
| **用户消息** | ❌ 不归我们动（§8.0.2 定义域） | 折了 = **根本渲染不出图**，§3.4 的「逐块判定」当场失效 |

**② 一对不能拆。**

[`00` §5](00-设计哲学.md) 的「一块的两面」不是修辞：协议**强制配对**（Claude 每个 `tool_use` 必须有 `tool_result`；Chat 的 `tool_calls` 必须有 `tool` 消息）。

⇒ **要么整对在，要么整对不在。** ⚠️ 而「在」的时候，**降级只动结果那一半**（`tool_use` 原样保留）——不是拆对，配对照样完整。
**半个在拿到的不是「少点内容」，是上游 400。**

**③ 步原子性——今天不成立，做工具时必须补上。**

今天**一步只追加一条**模型消息（`Stepper` 那一次 `AppendEvent`）⇒ §4 的「步是持久化的原子单位」是**构造上免费**的。工具把它变成「assistant + N 个结果」的**多次追加** ⇒ 崩在中间会留下**悬空的 `tool_use`**。

⚠️ **后果不是「丢了点内容」**：§4 那句「崩了这一步就当没发生过」在工具面前**失效**——缺一条 `read` 结果只是空的，**缺一条配对的 `tool_use` 是上游 400**。

⇒ 二选一（都行，**必须选一个**）：**在落盘格式里加步标记**，或**加载时做结构配对校验**（尾部悬空 ⇒ 丢掉那一步）。
⚠️ **今天两者都没有**：`session.step.begin` / `.end` 只是**线上事件**，不是落盘记录；`HistoryLog` 只跳**语法**坏行，管不了**语义**不完整的步。

⚠️ **实现（2026-10-06 最小工具批）**：**选了「步末一次落盘」那一半**，另一半（加载时的结构配对校验）**没做**。
- `HistoryLog.AppendMany` = **一把锁 + 一次 open/close**；`Stepper` 把「模型消息 + 它那批结果」凑成一次 append。
  ⇒ **原子性从「一把锁 + 一次 open/close」来，不是从「调用得够快」来**——并发下每批的记录是连续的（有测试钉）。
- ⚠️ **它没解决的照旧没解决**：一次 `Write` 仍可能被部分落盘（断电），而 `ReadAll` 只跳语法坏行。
  **尾部悬空仍在可能范围内**，只是窗口从「N 次 append」缩到「一次 append 内部」。
  ⇒ 上一条那个「加载时结构配对校验」**仍然欠着**，而它的缺失后果是那句「悬空的 `tool_use` = 上游 400」。

**④ 落盘顺序 = 调用顺序，不是完成顺序。**

§4 已定，而工具**默认并发**（§4）⇒ 完成序天然乱。⇒ 在内存里缓冲、**步末按调用序一次落盘**。
**顺带也解决了 ③**：一次落盘 = 一个原子。

⚠️ **实现（2026-10-06）**：顺序由**结构**保证（`ToolExecutor` 按入参次序跑、按 `callId` 归位），
**不是**由「本批是串行」保证的 ⇒ 将来改并发，这一条不用动（见 §4 那条实现注记）。

**结果由三个部分组成**（[`00` §5](00-设计哲学.md)）：**引用**（依赖什么）+ **快照**（实际喂给模型的渲染产物，**不是文件原文**）+ **指纹**（判世界动没动）。

⚠️ **引用与指纹是两个不同的哈希**，别合并成一个。
⚠️ 同一个快照可被**多条记录**引用（同一个文件读两次）⇒ **「降级这条记录」与「释放那个对象」是解耦的**（引用计数管后者）。别写成一件。

⚠️ **实现（2026-10-06）——三件落在哪**：**引用** = `ToolResultEvent.DependsOn`，**指纹** = `ToolResultEvent.Fingerprint`
（⚠️ **两个都落盘**：三态判定要拿「现在的」与「当时的」比，而「当时的」只能从记录里读——它是**最不可派生**的一个，
`00` §2.2 写的「骨架（引用 + 指纹）✅ 永久」正是这个）。
**快照** = `ToolResultEvent.Content`：小于 `BlobStore.InlineThresholdBytes` 内联成一个 `TextBlock`，
过了阈值则**字节进库**、记录里留一个 `StoreBlock`（`01` §8.4）。
⚠️ **指纹可以为空**（`00` §5：不可重演类「无指纹」，永不可优化）⇒ 两个字段都是**可空**的，
而 `null` 与空串在盘上**长得不一样**（前者键整个不出现）。

### 3.7 工具结果的框架与内容（2026-10-07 定）

> **一条工具结果 = 「框架」+「内容」。** 框架**恒定在内容之前**、是**独立的块**。

⚠️ **本节超出 §3.6 的文字，如实说明**：那条只说结果内容是**块数组**（三形态：纯文本 / 纯图 / 混排）。
块边界**在**、类型**有**——而**「这一条结果是什么」今天无处安放**：它既不是内容，也不该是内容。
本节补的是这一格。

#### 协议层的兜底**不够**

`ToResultBlocks` / `ResultToJson` 交的不是一段文本（Claude 是 `tool_result` 块、Chat 是 `role: "tool"`）
⇒ 线上结构上二者是分开的。⚠️ **但这一层管不到块里面**：
`read` 自己交的是「**一个** `TextBlock`」，框架与内容挤在**同一个块**里。

⚠️ **而且这个病已经出现过一次**：**回收**。注记是框架语义，而替换发生在 `Content` 上
⇒ 今天是【整个 `Content` 换掉】。它没出事，**只因为工具结果是一对一**（一条结果换一条注记）。
**一旦一条结果里同时有框架与正文，「整个换掉」就会吃掉框架。**

#### 所以：框架从 `Content` 里拿出来，单独一格

```
ToolResultEvent
├─ CallId · Id · At
├─ Framing   ← 本节新增（**结构化**，不是一段文本）
├─ Content   ← 内容（**回收只换这一格**）
└─ DependsOn · Fingerprint
```

⚠️ **不是加一种新 `Block`**——§3.6 ① 已经裁过：工具结果不能是 `Block`，因为
**「任何只对某类发言成立的属性都无处安放」**。一个「只在工具结果里有意义」的块类型，正撞在那条判据上。

**渲染期**（[`TimelineRender`](../src/Lilara.Core/Session/TimelineRender.cs)，它今天正好是两步 ⇒ 变三步）：
**框架渲染成它自己的一个 `TextBlock`，恒定在内容之前。**

⇒ 模型侧看到的是：

```
framework:  [read a.log 1-8192/20971520]
content:    <文件那 8 KB>
```

**它不需要「分」——因为它看到的是外层，不是一段要解析的散文。**

#### ⚠️ 框架分**两半**：工具那一半落盘、核心那一半不落

⚠️ **本节初稿写的是「框架不落盘」，那句写宽了**——它把两半混成了一句，
而**两半该不该落盘的理由正好相反**：

| 哪一半 | 例 | 落盘吗 | 谁产生 | 为什么 |
|---|---|---|---|---|
| **工具那一半** | `read` 的路径与段号 · `ls` 的表头与**「共 M 条」** | ✅ **落**（是事实） | 工具（`ToolOutcome`） | 它说的是「**那次调用返回了什么**」——**不落就丢了**，而记录只追加、**丢了补不回来** |
| **核心那一半** | 「这条**已回收**」 | ❌ **不落** | **渲染期，从核心状态算** | 它说的是「**你现在还能看到多少**」——**随回收状态变**，与注记**是同一类东西** |

**⇒ 一条判据管两半，方向相反**：

> **「那次调用发生的事」→ 工具，落盘。**
> **「这一刻的可见性」→ 核心，渲染期算。**

⚠️ **于是回收那一步的形状**：`Reclaim.Apply` **只换 `Content`**，
而**核心那一半（「已回收」）是渲染期叠加上去的** ⇒ 两半**不相干**，
各自的判据也就不该共用一句话。

#### ⚠️ 框架的文本必须是**定长、位置固定**的，不是散文

**别指望模型「读得懂一段说明」**——那是把约束写成提示词，而
[`00` §7 判据 5](00-设计哲学.md) 明说「**能进机械层的，绝不靠嘴说**」。
⇒ 模型认**位置与形状**，不认语义。首行永远是那个形状：

```
[read a.log 1-8192/20971520]
[ls src 前 50 条，共 1240]
```

#### `ls` 的元数据就是框架，**截断也归框架**

`ls` 今天一行一条、目录加尾斜杠。**加元数据 = 加列，而列就是框架**：

```
[ls src]
ListTool.cs        4.1 KB     2 分钟前
big.log            20.0 MB    3 天前
```

⇒ **表头是框架，行是内容**，截断同样归框架（`[ls src 前 50 条，共 1240]`）
——**同一个机制，不发明第二个。**

⚠️ 一条要认的性质：**一条 `ls` 结果被回收后，框架仍然说「这是 `ls src` 的结果」**
（那是**事实**），只是**内容**换成注记。**这正是把框架拿出去的价值。**

#### ⚠️ 唯一的致命不变量：框架**不许**与内容共用字面量

**模型只能靠「这是一个独立的块」来区分二者。**
若框架是文本型，而内容**恰好**以同样的形状开头（一个 log 文件的第一行刚好长得像 `[read …]`），
**模型没有任何办法分辨。**

⇒ **必须配一条测试**：喂一个**首行伪装成框架**的内容，断言它没被当成框架。
（同 `HeadScriptTests` 那三条的性质：**拦得住「谁又用错了」，拦不住「渲染出来长什么样」**。）

⚠️ **另有一条实现期的约束**：框架进的是 Claude 的 `user` 角色消息里的 `tool_result` 块，
而**工具的 `Content` 今天只可能是文本块** ⇒ 只要**框在内**（`content: [...]` 数组里），
两者就是同一个块数组里的**两个元素**，天然分得开。
⚠️ **将来若 Content 要承载图片块**，那就要再核一次
（`ToResultBlocks` 今天为「只有一个文本块」走字符串捷径）——**写在这里，别当成已经验证过。**
## 4. 时间模型：步

| 单位 | 定义 | 用途 |
|---|---|---|
| **步 (Step)** | 一次模型调用 + 其工具执行 | **持久化的原子单位** |

**「轮」已废弃**——持有轮的概念太麻烦，且优化/回收的触发点本来就只靠前缀失效。

**步边界持久化**：ALP 的"assistant 与 tool_result 一起写**防半截轮**"做法正确，沿用——只不过我们写的是**骨架**，不是原文。（引号内是 ALP 的旧词；本项目对应的说法是**防半步**，§4。）

**步内默认并发执行工具，用户可配置强制串行。**

> ⚠️ **并发时工具记录顺序 = 模型发出的顺序，不是完成顺序。** 否则重放时记录会漂移，而记录是事实。

⚠️ **实现（2026-10-06 最小工具批）**：**本批是串行（一个 `foreach`），刻意的偏离**。
理由：本批只有 `ls` / `read` 两个**纯读**工具，并发零收益；而取消钩子打进**一个**执行
比打进 N 个并发简单得多（`session.interrupt` 在飞调用的落点还没做）。
⚠️ **改成并发不需要动别的**：记录顺序由「按调用序归位」**结构**保证
（`ToolExecutor` 里结果按 `callId` 入位，与执行策略无关）⇒ 换 `Task.WhenAll` 时，
缓冲、排序、落盘全都不用动，**测试断言也不用改**。
⚠️ 另外「用户可配置强制串行」那一半**没做**——今天没有开关，行为固定为串行。

## 5. 状态机

```
Idle ──驱动──▶ Running ──┬──▶ Idle              (本次推进无事可做)
                          ├──▶ WaitingForInput   (等头决策：审批/追问)
                          ├──▶ WaitingExternal   (等外部：子会话/HTTP/定时/**锁**)
                          └──▶ Blocked           (故障退避)
```

三种暂停**必须分开**，因为超时语义和解除方式完全不同。⚠️ **注意这列不是 §6.1 的「启动」**——「启动」是"从 Idle 推进一步"，会让状态**变成** Running；这里是"用什么把它从暂停里**解除出来**"：

| 状态 | 解除方式 | 超时行为 |
|---|---|---|
| WaitingForInput | **仅头**（审批 / 回答） | 永不超时（核心不关心头在不在） |
| WaitingExternal | 事件到达 / 超时 / **锁释放**（§12.2 的等待单位） | 超时后转 Blocked 或 Idle ⚠️ 判据未定（§14 #5） |
| Blocked | 退避到期 / 头介入 | 退避重试 ⚠️ 退避曲线与上限未定（§14 #5） |

> **解除暂停 ⇒ 接着「启动」**——解除只给一次机会，真正推进仍走 §6.1 的队列。

⚠️ ALP 缺这个分类，它的"等待"全靠 `WaitUntil` + 30s 心跳轮询。**本项目用事件驱动替代轮询。**

## 6. 驱动模型

```
驱动源 = 用户消息 | 后台事项事件 | 定时器 | 控制面「启动」（见 §6.1）
```

⚠️ 这四个源**都只是把东西塞进队列**（§6.1）。**驱动不是一个独立的子系统，是"队列 + 启动接口"。**
**关键机制：记录追加是即时的，推进是合并的。**

> 推进中来了 3 条用户消息 → **立即追加为记录**（它们是事实），但**只触发一次推进**——**合并是队列的副产品**（§6.1）：三次入队、三次启动，但第一次就把状态变成 `Running`，后两次是 no-op。

与浮动槽位同一条哲学：**追加免费，重复劳动才贵。**

### 6.1 待办集合 = 消息队列

⚠️ **驱动不是"规则引擎"，是一个队列加一个显式的启动接口。**

```
待办集合 = 该会话的消息队列        ← 就是它，不是另一套结构
```

**入队**：

```
入队(x)  → 若 x 是事件，立即追加进记录（它是事实，见上）
         → 安排一次「启动」（去重：已有待启动则不再安排）
```

**启动**（核心侧的一个显式接口）：

```
启动(s)  → 会话 Running？  → no-op（会话内串行，§13）
         → 队列空？        → no-op
         → 否则取空队列 → 推进
```

> **合并是队列的副产品，不是一条规则。** 连发 3 条消息 = 3 次入队 + 3 次启动，但第一次就把状态变成 `Running`，后两次是 no-op → **自然合并成一次推进**。

**四个驱动源在此汇合**：

| 驱动源 | 动作 |
|---|---|
| 用户消息 | **入队 + 启动**（复合动作，对用户透明） |
| 后台事项事件（§10.1） | 入队 + 启动 |
| 定时器（§6.2） | 入队 + 启动 |
| **控制面** | **可直接调「启动」** ← 留的口子。⚠️ **这就是 §6 开头那个「控制面「启动」」**——它列的四个源里，只有它不是"入队"，而是直接启动 |

⚠️ **主动性档位决定「入队后是否自动启动」**（§3.5）：

| 档 | 行为 |
|---|---|
| **步进** | ⚠️ **不自动启动**——只在显式「启动」时推进。这就是"用户说一步，模型动一下" |
| 标准 / 目标 | 入队即自动启动 |

> ⚠️ **实现（2026-10-05）**：这条**整体未生效**。`CommandDispatcher` 对任何档位都在入队后**自动起一步**；
> `HandleSessionStart` 是 **no-op**（当前 `send` 已直接完成一步）。⇒「显式启动」接口存在但无行为。

⚠️ **队列进 `state.json`**（§12.8）→ 崩溃重启后**待办还在**，启动一次即可继续。这是"不知道自己还在等谁"那个问题的完整答案：**待办就是队列，队列就是持久化的**。

> ⚠️ **实现（2026-10-05）**：**未兑现**。队列是 `SessionHandle` 里的**内存** `Queue<>`，
> `state.json` 的 `Pending` **恒为空数组** ⇒ 崩溃后待办**会丢**。这是计划里已声明的偏离。

### 6.2 自主的三种形态

| 类型 | 触发 | 上下文 | 例 | 状态 |
|---|---|---|---|---|
| **持续任务** | 一次下令 | 延续同一会话 | "重构完这个仓库"，头离线也继续 | 首版做 |
| 定时作业（**新建型**） | 时机 | **新建会话** | 每日巡检 | 首版不做 |
| 自发活动 | 空闲 | 延续 | ALP 的做梦/维护 | 首版不做 |

**"头离线继续干活"是三者共有的性质**（来自头核分离），不是"自主续跑"独有的——自主续跑特指**不需要新输入也能推进**。

**两条规矩**：

1. **核心不做「预算」，只做「循环控制」。** ⚠️ 两者判据不同：预算是**花了多少**（策略，归**插件**），循环控制是**有没有进展**（机制，归核心）。核心侧唯一需要的是 `目标` 档的**最大连续步数熔断**（§3.5）——那是防止"没有进展也不停"。
2. **"延续"与"新建"是本质区别，不是配置项**。延续复用现成的记录 / 优化 / 回收机制，成本为零；**新建需要一个新的实体「任务定义」**（模板 + 每次执行的记录），首版不引入。

⚠️ 推论：首版**定时作业只能是"定时唤醒同一会话"**，不是"定时跑一个新作业"。

## 7. 配置分层

三层继承，**配置即类型**：

| 层 | 持有 |
|---|---|
| **全局** | Provider 定义（端点、key、协议类型）、**插件清单**（配置；插件宿主据此加载并收集贡献，见 [`04` §1](04-插件与内部结构.md)） |
| **项目** | 工作目录、默认提示词插件、默认工具白名单、默认模型 |
| **会话** | 模型选择、结构化记录、状态、驱动配置 |

### 7.1 类型应该消失，只留预设

ALP 的 `SessionTypeProfiles` 是好东西（命名配置包），问题在于 `Type` **同时是配置键和行为开关**——代码里会长出 `if (type == "task")` 这类分支。

**本项目：配置即类型。** 行为完全由数据决定，代码里不出现类型分支。

证据：ALP 的"task 禁止套娃"实现其实是**工具白名单里没有 system-ops**，即**配置驱动的**——类型分支是多余的。

```
预设 (Preset) = 一份可复用的配置模板     ← 保留，纯数据
类型 (Type)   = 代码里的行为开关          ← 删除
```

会话之间的结构差异（**有没有父**）是**关系**，不是类型。

### 7.2 配置继承：引用，不是本体

Provider 定义存全局（含 key），会话只存**引用 + 选择**。但会话必须能回答"**这一步是哪个模型跑的**"，否则重启后历史来路不明。

> 会话持有：**解析结果的快照 + 指向定义的引用**。

"换模型 = 改会话配置"改的是**选择**，不是**定义**。

⚠️ **Rejected config**（曾用过但已不在注册表中的配置）不能报错——历史记录带着它们。行为：只读告警 + 禁止再选。

## 8. 持久化布局

判据：**可分享 vs 私有**。

```
<全局数据根>/                       (见下)
  providers/                        提供商定义（key 在这）
  presets/<id>.md                   系统提示词（**文件内容就是那段话**；`default` 是默认那份）
  store/<sha256>                    库：内容寻址的不可变大对象（跨会话共享）
  projects/<projectKey>/            projectKey = 目录规范化后的指纹
    project.json                    目录路径 + 元数据  ← ⚠️ 见下
    sessions/<sessionId>/
      spec.json                     一次写为主，**但 `session.configure` / `session.archive` 会改它**
      state.json                    每步原子重写
      history.jsonl                 每步追加（骨架，非原文）

<工作目录>/.lilara/
  claims.json                      声明：谁在动哪些文件（**已实现**，唯一一个）
```

⚠️ **`presets/` 与 `providers/` 刻意不同**（2026-10-07，预设批）：那里是 **JSON（结构 + key）**，
这里是**纯文本**（就是一段话），因为它**给人编辑**——包一层 JSON 就得处理转义、换行、以及
「我少打了个引号」。⇒ 它也没有 `version` 键，没有「损坏」这一说：**任何字节都是合法内容**。
⚠️ 会话那边存的是**引用**（`spec.json` 的 `systemPromptPreset`，`null` = 跟随 `default`），
**不是内容**——改文件对下一次请求立刻生效（用户裁定），代价见 §3.1 那张「外力才变」的表。

⚠️ **这张表原先是四行**（`sessions.json` / `project.md` / `config.json` / `inbox/`），2026-10-06 逐条核过 `src/` 之后改成一行：

| 原表里那条 | 实情 |
|---|---|
| `sessions.json` **反向映射** | **代码里没有**。会话目录在数据根，按 id 找会话靠**扫盘**（`SessionStore.FindSession` 遍历 `ListProjects`）——项目数是个位数，代价可忽略。⚠️ 但 §8.0.2 第九节的「目录移动 / 改名 ⇒ 可重新绑定」**仍然指着它**；那是**设计意图**，写在那里的是它**该**长成的样子，不是今天的机制 |
| **`project.json`**（数据根那半的第一行） | ⚠️ **代码里也没有**，但它**不是同一类**：那四条旁边没有第二条路，而这一条**旁边有**——`projectKey` 是**工作目录的哈希**（`ProjectKey.FromPath`，sha256 前 16 位），**单向** ⇒ key → 目录这一步**算不回来**，今天只能靠读会话的 `spec.json`。⚠️ 也就是说：**目录移动 / 改名之后，key 与目录再也对不上，而没有任何记载说它们曾经是一对**。（§8.0.2 第九节那句「可重新绑定」要的就是这份记载。）⇒ 今天不写它；要写的话得先回答「路径移动之后谁改它」 |
| `project.md` · `config.json` | 都没做（项目层配置整块见 [`实现现状`](实现现状.md) §二） |
| `inbox/` | 没做（附件整族没做） |
| **`claims.json`** | ⚠️ **原表漏了它**——而它是这里**唯一真的在跑**的东西，`ClaimStore` 一直在写。漏掉的原因值得记下来：**漏的是「不该分享」的那个**，而这张表的标题是「可分享 vs 私有」⇒ 它被当成「数据根那一侧」的东西，而实际上它按位置就该在这里 |

⚠️ **`store/<sha256>` 与上表**：库**不是**「写了没做」——它**做了**（`BlobStore`，0b）。⚠️ 但要说准：**它今天连挂都没挂上**（全仓 `new BlobStore` 零命中，只有测试构造过它），而且**没有写入方**（工具还不存在）⇒ 「库里放快照」（§8.4 那条）今天**没有发生**。⚠️ 另：`03` §9.4 的 `GET /store/{sha256}` **没做**（[`实现现状`](实现现状.md) §五 第 ⑨ 族）。

**数据根怎么定**：

```
1. 环境变量 `LILARA_HOME`（若设了）
2. 否则 `~/.lilara`         ← Windows 下 `~` = `%USERPROFILE%`
```

⚠️ **多用户天然隔离**——每个 OS 用户一份数据根，**正好对上**「核心是本设备（**至少本用户**）唯一的」（[`README`](README.md)）。**不需要额外的换用户机制。**

**核心原则**：

- **对话内容绝不进工作目录** —— 很多聊天内容不适合上传 git。`.lilara/` 只放**适合与其他人分享**的内容
- **大对象进库，不进会话目录** —— 库在全局、内容寻址、跨会话共享（§8.4）
- 好处：**别人拿到你的项目，继承你的项目配置，但看不到你的聊天记录**
- 项目**声明**（可分享）在工作目录；会话**状态**与**库**（私有）在数据根
  ⚠️ **而声明是「可分享」这条的例外**（`claims.json` 就在上面那张表里）：它进工作目录的理由与分享无关——
  **声明约束的正是「谁在动这个目录里的文件」，所以它必须与那些文件同处**。判据是**作用的边界**，不只是可分享性。

### 8.0 三种字节：按「能不能重算」分

⚠️ **上面那张布局图只说了「放在哪」，没说「谁可以动、丢了会怎样」。** 判据是**能不能重算**：

| 层 | 定义 | 例 | 条款 |
|---|---|---|---|
| **L0 事实** | **不可重算** | `history.jsonl` 的消息 · `claims.json` · `providers/*.json` · `spec.json` 的身份与出生信息 | **只追加**（能追加的）· **耐久** · **永不因过期被回收** |
| **L1 状态** | 能从 L0 **导出** | `state.json` 的 `turn` / `status` / `axes` · `spec.json` 的 `title` / `archivedAt` | **原子重写** · **丢了是对的成本**（[`00` §7 判据 8](00-设计哲学.md)）· **带版本** |
| **L2 索引 / 派生** | 能从 L0+L1 **重算** | `DataRootLock` 的锁文件 · 会话列表 · 全局会话列表（[`05` §6.1`](05-头设计.md)） | **不许持久化**——算得出来就不该落盘（[`00` §7 判据 8](00-设计哲学.md)） |

⚠️ **这条轴一立起来，三类问题各归其位**，不再是「一堆散落的小毛病」：

- **GC 是 L0 的「载荷」的条款**（§11）——注意**不是** L0 的全部：骨架永不回收
- **耐久是 L0 的条款**——`state.json` 不必 fsync，它是 L1
- **版本是 L1 的条款**（见下）

⚠️ **L1 丢了不是缺陷，是它存在的理由**：`turn` 可以从 `history.jsonl` 数出来，
所以它本来就是一个**缓存**。把 L1 当 L0 对待（给它加 fsync、给它加迁移脚本）是在为
「可以再算一遍的东西」付永久的代价。

#### 8.0.1 版本：L1 必须能说出「我是哪一版」

⚠️ **今天每份 JSON 的顶层都有 `version`**（`Kernel.Json.FormatVersion`）。这不是仪式，是补一个**结构性缺口**：

> 读到 `turn: 3`，你怎么知道它就是 3，而不是某个更新版本里的第 3 条记录、别处还写着「共 9 条」？

没有版本号时，**这个问题没有答案**——只能拒绝、崩溃、或**静默重解释**，而三者都没有条款。
有了它，判据就一句话：**文件版本 > 本程序 ⇒ 明确拒绝并说人话**（`Storage.FileFormat`）。

⚠️ **「缺 `version` 键」= 版本 0，不是「未知 ⇒ 拒绝」**：那批是加这个字段之前写的，
而在格式冻结期间它们是**唯一**的历史。拒绝它们等于把用户已有的会话全部作废。

⚠️ **两种「读不出来」的处置方式正相反，别折成一个 `null`**：

| | 原因 | 该怎么办 |
|---|---|---|
| **文件损坏** | 写到一半断电 | 重写一份就好 |
| **版本太新** | 是**另一个版本的核心**写的 | **别覆盖**——覆盖会把它降级成旧格式，**那是丢数据** |

⚠️ 所以有两套读取：**按身份找**（`ReadSpec` / `FindSession`）要**响亮**，
**枚举列表**（`TryReadSpec` / `ListSessions`）要**活下来**（一个太新的会话不该让整张列表打不开）。
两者都做到了，用户才既看得见原因、又不至于打不开程序。

⚠️ **它不管 `history.jsonl`**：那是只追加的，行与行可以来自不同版本，而且断电会留半行 ⇒
**坏行必须跳过**，那一份的策略在 `HistoryLog` 的注释里。

### 8.0.2 载荷的生命周期：回收只动注入，持久化只增不减（**契约；回收器已实现，压缩那半没有**）

⚠️ 本节原先写着「**今天零代码**」。**回收那一半已经落地了**（2026-10-06 回收批）：
判定（`Reclaim.Decide`）· 注记（`Reclaim.NoteText` / `Apply`）· `fetch`（`FetchTool` + 句柄的 `SnapshotOf`）
· 手动触发（`session.gc`）——**实测跑通过一次完整链**。
⚠️ **仍未实现的**：本节提到的 **compact / release 那两个边界**（整块为零，见 [`§11.2`](01-会话设计.md)），
⇒ 今天没有「加载边界」，倒查（§12.4）也就无从谈起。
⚠️ **九节里的每一条都核过一遍**，下面各节就地标着「⚠️ 实现（2026-10-06）」。

⚠️ **本节是给「第一次做工具」那次准备的形状契约，现在只落字、不加代码。**
理由不是保守：**今天连「一条工具结果长什么样」都没有定，而回收的形状依附于它**——
先写回收器等于对着空气定形状，而那正是会腐的形状。

#### 一、判据：回收只处理「注入」，不处理「持久化」

> **磁盘上那份永不因回收而减少。** GC 只改变**加载时喂给模型的东西**。

依据是 §11.2 已经立住的加载边界模型（压缩**不改变文件落盘的历史记录**）+ §12.4 的倒查（`≥R` 原文 / `<R` 简化）——两者都是**加载期解释**，不是落盘时改写。

⚠️ **由此，`history.jsonl` 上永远没有「删掉一个块」这个操作。** 物理删除是**另一个操作**（`session.delete` / §14 的截断），别和回收混——`HistoryLog` 那套崩溃安全（「完好前缀才是值钱的部分」）全靠只追加。

⚠️ **§11.1 那句「压缩真正减少增长」只说对了上下文那一半。** 磁盘那一半**不成立**：**截断是唯一的减量操作**，而它**不可逆、也不可恢复**。

#### 二、可恢复性：这是「可以回收」的前提，不是补救

> **某个工具调用被回收后，模型必须仍有办法拿回它的内容。**

没有这一条，退回按「可重演 / 外部易变 / 不可重演」三分保守处理；**有了它，默认可以激进地回收**——失败模式从「丢数据」变成「多一次调用」。

**恢复路径上不跑任何工具代码**：

```
取回 = 读 store/<sha256> → 原样交回
```

⚠️ **不要重新渲染。** 重渲染要过 `render(贡献, now)`，而 `now` 一步一个（§3.2）⇒ 交回的是**另一个时刻的产物**，那不叫恢复，叫「重造一份看起来像的」——「事实不可变」当场破。
⚠️ 机制是现成的：`03` §9.4 的 `GET /store/{sha256}` 就是「取字节」。

**「可回收」的充要条件是事实，不是声明**：**这个结果的快照真的落盘了**（[`00` §7 判据 4](00-设计哲学.md)：结构上排除，而非规则禁止）。

- 落盘了 ⇒ 取回**一定**成功（盘没动）
- 没落盘 ⇒ 取回**必然**失败 ⇒ **不许回收**

⇒ 这条把「靠工具自觉」换成「靠事实判」。今天所有结果都是块、都可序列化 ⇒ 恰好恒真；等出现「太大不落盘」或「流式结果」时，这条会自动把它们挡在外面，而**不需要工具作者记得声明什么**。

⚠️ **实现（2026-10-06，回收批）——判据落在哪，以及一处窄读的更正**：
**可回收 ⟺ `fetch` 取得回 ⟺ 内容自己就够**（`Reclaim.Recoverable`）——
内联的块在记录里就是它本身；`StoreBlock` 要看那个对象在不在库里；空的无内容可收。

⚠️ **我第一版把它读成了「字节必须在 `store/` 里」，于是整类内联快照被判成不可回收**
（小文件——而回收器存在的意义正是收它）。错在哪：本节上一句自己写着
「今天所有结果都是块、都可序列化 ⇒ **恰好恒真**」——**内联就是落盘**。
⇒ 判据落在「取不回就不许回收」，**不落在「字节躺在哪个文件里」**。

⚠️ **大小与形状都不进这个判据**：内联的、留地址的、混排的、纯图的，**一律可回收**；
区分只在「持久化到哪」，**模型视角不分大小**。⚠️ 为此**写入侧总是 `Put` 一遍**
（小的内联进记录、库里**也**留一份；`01` §8.4 ¶1「凡是被记录引用的字节，都在库里」）。

##### ⚠️ 回收的**定义域**：只有**工具结果**（2026-10-06 补）

> **上一条判据原先漏了定义域**——按字面读，用户贴的图也在 `store/` 里、也落盘了 ⇒ **它满足，会被回收**。那是错的。

**正确的界是「有没有 call id」，而它不是新规则，是从 `fetch` 反推出来的**：

| 内容 | 有 call id？ | `fetch` 取得回？ | 归谁 |
|---|---|---|---|
| **用户消息**（含图） | ❌ | **取不到** | **谁都不动** |
| **模型的发言** | ❌ | 取不到 | **compact**（写摘要替代——**是改写，不是回收**） |
| **工具结果** | ✅ | ✅ | **GC** |

⇒ **`fetch` 的句柄就是 call id** ⇒ 用户消息**根本没有取回入口** ⇒ 按上面那条「取不回来就不许回收」，它**自己就被排除了**。

⚠️ **模型发言那半也顺带归位**：它**不是 GC 的业务**，是 compact 的（§11.1 那两列的分工本来就写着）。

> **工具结果里的图**同样是工具结果 ⇒ **归 GC**。
> **对话里的图**（用户贴的 / 模型生成的）不是 ⇒ **谁都不动它**。

##### ⚠️ 托管 ≠ 可回收（两个词挨着出现过，别读成同义）

**托管是渲染机制**（§3.4：「内容是个引用，构造时向所有者要」）；**回收的机器是 [`00` §5](00-设计哲学.md) 的引用 / 快照 / 指纹三样**。

⇒ **用户贴的图是托管的，但不是可回收的**——它照样在 `store/<sha256>` 里，但它**没有调用记录、没有指纹**，三样一样都没有。
⇒ 「在 `store/` 里」是**存储位置**，不是**生命周期类别**。

#### 三、取回对所有工具统一开放（**不按类别分**）

> **`fetch` 是常驻工具，对全部工具结果一视同仁。模型不必知道任何一条工具属于哪一类。**

理由不是「省事」，是**别把我们的分类学塞进模型的上下文**：

- 工具是**插件**贡献的，模型可能从没见过某条工具，**光看名字推不出类别**
- 让 `fetch` 的可用性随类别变 ⇒ 等于要求模型先建模一遍我们的生命周期分类
- 而那份知识**进的是上下文**，每步全价付（§3.2 的尾槽位是「体积 × 步数」）

⇒ 统一的判据是：**「向前 / 往回」退化成选方向，而不是「这个能不能往回」**。

⚠️ **这条改过**（2026-10-06，用户裁定）。原文是「类别决定注记里写什么」——按类给不同的注记。
现在的模型**自己能判断该向前还是往回**（它清楚 `send_email` 不能重调），不需要我们代它分。

⚠️ **类别没有全死，但它**不再是 GC 概念**。它只是 [`00` §5](00-设计哲学.md) 三态判定（指纹 / 脏）的输入：

| 问题 | 现在的答案 |
|---|---|
| 能不能回收 | **事实**：快照真的落盘了吗（第二节）——**不是类别** |
| 注记写什么 | **统一**（第四节）——**不分类别** |
| `fetch` 给不给 | **全给**——**不分类别** |

#### 四、注记：**只降结果，调用不动**

> **注记 = 降级形态。它不是新钩子，是给 §5 已有的「渲染」多一个输入。**

```
渲染(结果, 快照可用性) → 块
  快照 = 有  → 正常形态
  快照 = 无  → 注记
```

⚠️ **不加新钩子的决定性理由：MCP 工具。** [`00` §5](00-设计哲学.md) 写着 MCP **只给得出执行**，渲染 / 优化钩子走**核心侧默认策略**。若回收行为是新钩子，**所有 MCP 工具都提供不出来 ⇒ 全都没法回收**。做成「渲染的一个输入」，核心侧的默认策略**白送**给它们。

⚠️ **注记是渲染的输出，所以它**不是**「记录里的一个标记」**——记录本身不动（第一节）。这与 §6.2 那条一般规则一致：**外观绝不能是持久化状态。**

##### ⚠️ 降级的是结果，**不是整对**（2026-10-06 更正）

> **`tool_use` 原样保留，只把 `tool_result` 换成一条短注记。**

```
[tool_use read(path="src/auth.cs")]                                       ← 不动
[tool_result "已回收。fetch(#7f3a) 取回当时的；要现在的值自己再读一次。"]      ← 降级
```

**本文原先写的是「注记**替代整对**」，那是错的**，三条理由：

1. **`tool_use` 是模型自己的输出——那是事实。** 把它删掉，等于**为了省一点上下文去改模型说过的话**。而它恰好是这整件事里最便宜的东西（几个参数）。
2. **`tool_use` 是锚。** 模型看见自己发过 `read(src/auth.cs)`，紧跟一条说「这个被回收了」——**关联是位置给的**，不需要额外说明。
3. ⇒ **注记因此可以说得更少**：原先那张「必含」表里的「什么工具」「参数摘要」**可以整行删掉**——它们就紧挨着在 `tool_use` 里。
   （旧写法把锚删了、再把锚的信息抄回注记——**抄了一遍，还丢了关联**。）

**注记仍然必须说够**（这是本设计唯一一条**无法自动检查**的属性——不像「快照落盘了」可以查），
而且**对所有类别是同一份**（第三节）：

| 必含 | 缺了会怎样 |
|---|---|
| **`[已回收]` 这个标记本身** | 模型以为自己看到了全部 |
| **取回地址（id）** | 拿不回来。⚠️ id 放在**结果**里——它是在那儿被用到的 |
| **「要现在的值就自己重调一次」** | 模型不知道它还有另一条路 |

⚠️ **这不是「工具名与参数不必知道」——是它们已经有地方了**（`tool_use` 里）。别把这条读成「注记可以说得含糊」。
⚠️ **最后一行不是客套，而模型**判断不了盘上还有没有**——那是核心的状态。所以注记要把**它有哪些选择**列出来，而不是丢一个 id 让它自己猜。
⚠️ 那一行**对所有工具都写**，不按类别省略：判断「重调有没有意义」是**模型**的事（它知道 `send_email` 不能重调），而**核心替它省掉这一行**只会让它不知道该往回还是往前。

**固定点**：同一条记录 + 同样的「快照不可用」⇒ **逐字节相同的渲染**（[`00` §5 铁律 1](00-设计哲学.md)），否则每渲染一次破一次前缀。

⇒ **注记里不许出现**「什么时候回收的」「这是第几次降级」这类东西——而那正是最容易顺手加上去的。

#### 五、那条预期靠**说明**成立，不靠模型自己猜到

⚠️ **「模型自己会知道向前还是往回」是一条关于模型能力的假设，不是可以推出来的性质。**
⇒ 它成立的**条件**是**工具被介绍过**——而这和「别把分类学塞进上下文」不冲突：要交代的是**机制**，不是**分类**。

```
✅ 说机制：「旧的工具结果可能被回收，那时你会看到一条只带 id 的注记。
            fetch(id) 拿回当时的内容；想要现在的值，就自己重调一次那个工具。」
❌ 说分类：「read 是可重演的，email 是不可重演的……」（那是我们的内部账）
```

⚠️ **这与 CC 自己会介绍运行环境（工作目录 / 工具 / 约束）是同一件事**，不是例外。
「能进工具描述的绝不进系统提示词」（§3.1）管的是**每一条工具各自的说明**；
而「一套工具被回收之后怎么取回」是**跨工具的机制**，正属于「**没法挂在单个工具上的全局约定**」——§3.1 那句原文的落点就是这类东西。
⇒ **它该进系统提示词。**

⚠️ **`fetch` 必须常驻工具表**，不能「有回收物时才出现」：工具表是**前缀指纹的一部分**，而改工具表是最贵的操作（[`00` §7 判据 5](00-设计哲学.md)）⇒ 动态增删它会让**第一次回收**全废一次前缀，正好抵消回收省下的东西。
⚠️ **`fetch` 必须是独立工具**，不能做成已有工具的一个模式（如 `read(path, 旧版: true)`）——那样模型又得先判断「这个工具有没有旧版模式」，正是第三节要消除的那种纠结。

#### 六、取回：以**新的工具对**回来，不是把旧对复原

```
旧行：[tool_use X] [tool_result X]                  ← 被回收（只降了结果）
→     [tool_use read(path=…)]                        ← 调用原样留着
      [tool_result "已回收。fetch(id="7f3a") …"]       ← 结果降级

…后来模型要了（这一对是**新**的，记在**当时**的位置）：
      [tool_use fetch(id="7f3a")] [tool_result <那时那串块>]
```

⚠️ **注记里那句要写成一条能直接抄走的调用**（`fetch(id="…")`），不是给人看的陈列形
——模型下一步就要发出它。（上面示意图早先写作 `fetch(call#7f3a)`，那是**示意**，不是要发的字节。）

⚠️ **取回不该重调**，两个操作回答两个不同的问题：

| 操作 | 答案 | 代价 |
|---|---|---|
| **取回**（`fetch(#id)`） | 「我当时看到了什么」——**那时的渲染产物** | **读一次库**，无副作用 |
| **重调**（`read(path)`） | 「现在是什么」——当前内容 | **做一次副作用**（可能发邮件、跑命令） |

⚠️ **两者都是普通工具**（2026-10-06，用户裁定；本文原先在这里写「取回是核心特权工具」）——**归属见本节末**。

三条理由：**①** 重调不需要核心做任何事（模型随时能自己调）；**②** 取回的价值恰恰在「重调拿不到」那一半；**③** 重渲染不是恢复（见第二节）。
⚠️ 用词：是**那时的渲染产物**，**不是文件原文**——`00` §5 写死了快照「**不是**文件原文」（[`01` §8.4](01-会话设计.md) 同）。

##### ⚠️ `fetch` 的结果**就是原内容本身**——不包装、不注入

```
call:   fetch(call#7f3a)
result: <src/auth.cs 当时的内容>          ← 没有包装层，也没有伪造的调用
```

**两种「看着更整齐」的写法都是错的**，而且各有硬理由：

| 写法 | 为什么不行 |
|---|---|
| 结果是 `{ toolcall: read, toolresult: … }` 那样一个**装着旧对的信封** | 身份信息（id 在参数里、是什么工具在注记里）**不需要塞进结果**——再包一层是**同一件事说两遍** |
| 把内容的 `tool_use` **也一起注入**（不是模型主观发的） | ⚠️ **这正是 [`00` §8.1](00-设计哲学.md) 作废过的「分层折叠」**（渲染时以别处的记录代偿）。而它更坏：**记录会开始谎报「模型看到过什么」**——记录里写着它调过 `read`，而它调的是 `fetch` |

⚠️ 第二种还顺手砸掉**头存在的那个理由**（[`05` §1](05-头设计.md)：核心越克制，头越要喧哗）——**核心自己造一句假话，头就没得显示**。

⇒ **`fetch` 的结果就是「那一串块」本身**——**内容**，不是引用。

⚠️ **这条改过**（2026-10-06，用户在实测之后裁定）。原文写的是「记录里存**引用**、不复制字节」，
理由是「**会被取回的东西按定义它大**，复制回来正好抵消回收省下的东西」。
**那个理由在内容寻址下不成立**：`store/` 里同一个字节只有一份 ⇒ `fetch` 再写一遍**不多占盘**，
差的只是记录里「12 位 id」对「64 位 sha256 地址」那五十来个字节。

而「存引用」换来三样东西，全是负的：

| 代价 | 说明 |
|---|---|
| 多一层**「找不到」** | 引用会失效（目标被截断、id 写错），而内容不会 |
| 一条**零调用方**的空转链 | 写侧 → 执行侧 → 渲染侧 → 三条适配器的守卫，**今天没有任何产出方** |
| 引用型结果**永远收不了** | 它的 `Content` 是空的 ⇒ 按「内容自己就够才可回收」它不合规 ⇒「回收 → 取回 → **永久占位**」——⚠️ **正是本节自己警告过的那个形状** |

⇒ 带内容的那版反过来还**照常进回收范围**（`fetch` 的字节也 `Put` 进库、也 `DependsOn`/`Fingerprint` 都可判）。

⚠️ **同一条 fetch 取两次 ⇒ 两条独立的 fetch 对，各自带着当时那份内容。**
⚠️ **`fetch` 一个 `fetch` 的结果**：取回的是那条 fetch 的**快照**——也就是它当时取回的东西。
⇒ **不会串成链**，因为记录里存的是内容，不是又一个指向别处的引用（「解到最底」由构造保证，不靠规则）。

##### ⚠️ 由此两条硬约束

**① `fetch` 的结果压根不进三态判定。**

⚠️ **这不是特例**（原文写「必须豁免」，那是把它当成需要开的口子）：`fetch` 的结果是**「具体」载荷**——
正是 [`00` §5](00-设计哲学.md) 那条**已有**的落法（「不可重演类**冻结形态**：渲染结果直接落成具体载荷，
此后不再被重新渲染」）。**三态判定看不到它，是因为那个判定器里根本没有这一类**，
不是因为谁给它开了后门。`send_email` 的渲染结果早就在用同一条规则（为的是热重载不让已发出的邮件在上下文里改写）。

⇒ 说「豁免」会把一条**通用规则**说成一处**特殊照顾**，而那正是「能不能走特权」这个问题会反复回来的原因。

**② `fetch` 不加「这是取回的内容」这类头**——**除非它是从记录派生的一行**。render 必须纯（[`00` §5 铁律 1](00-设计哲学.md)）：**不许**写「取回于 …」，那会每渲染一次变一次。

⚠️ **取回的结果照常进回收范围**——否则「回收 → 取回 → 永久占位」一次调用就把 GC 打败了。
⚠️ **取回在截断之后会合理地失败**：模型要收到「它已经不存在了」，**不是空结果**（空结果会让它以为「那次调用没有输出」）。
##### ⚠️ `fetch` 的归属：**它是一个普通工具**（2026-10-06，用户裁定）

本文原先写「取回是核心特权工具」（照 §11.2 给 `compact` 的同一条理由）。**那一条不成立**，理由按顺序：

| 前提 | 成立吗 | 说明 |
|---|---|---|
| **它只是读存档、返回一个工具结果** | ✅ | 这就是它的全部行为 |
| **它读到的一切核心本来就都能读** | ✅ | 稳定 id（§8.0.2 第七节）· 快照在库里 · 数据根本机唯一（§8.1）⇒ **不对称的特权本来就是空头** |
| **可恢复性不靠「核心在做」** | ✅ | 取回 = 读 `store/<sha256>` 原样交回，**不跑任何工具代码**（第二节）⇒ 与谁提供这个工具无关 |

**「取不到」的代价是均匀的，不是缺陷**：取回能力来自**句柄里有数据根**，那就该被**按句柄配置**（`tool.setEnabled` 那一族）——
与「工具表上有什么，模型能做什么」（§9.2）同一条。⇒ 没有 `fetch` 时，注解仍写「要现在的值就自己重调一次」，
模型少的是**一个方向**，不会拿到**假信息**。

⚠️ **`compact` 不同，它仍是核心特权工具**（§11.2）：`fetch` 只**读**，`compact` 改的是**加载边界**——那是核心的机制本身，插件改它等于改核心的行为。

⚠️ **这条裁定要求一件事**（否则「普通工具」是空话）：**插件句柄必须含一个只读的数据根 + blob 读取器**（用户裁定，2026-10-06）。
句柄里没有它的话，`fetch` 就只能回核心，而那样「核心零工具」（[`04` §1.3](04-插件与内部结构.md)）当场破掉。

⚠️ **「全类别开放」（第三节）与这条不冲突**：那一节说的是**模型看到的行为统一**，与**这个工具归谁实现**是两件事。

#### 七、配对与两个 id

**一对不能拆**（完整推导在 §3.6）：**要么整对在，要么整对不在**——而「在」时降级只动结果那一半。半个在拿到的不是「少点内容」，是**上游 400**。

**两个 id，别合并**：

| id | 谁生成 | 用途 |
|---|---|---|
| **协议 id**（Claude 的 `toolu_xxx`） | **provider** | wire 配对。我们不控制它的唯一性与稳定性（重试可能变） |
| **稳定 id**（`call#7f3a`） | **我们** | 盘上那条记录的身份——**取回 / 改历史（§14 批次 2）/ 头引用**共用同一个 |

⚠️ 模型只需看见**我们那个**，且**只在注记里给**（内容还在时不必显示——省 token，也不动前缀）。
⇒ 这与批次 2 要的稳定 id 是**同一个机制、三个消费者**。

#### 八、磁盘只增不减的后果

| 操作 | 动磁盘 | 可逆 |
|---|---|---|
| **回收（GC）** | ❌ 一字不动 | —— |
| **恢复（取回）** | ❌ 只读 | —— |
| **截断**（§14 批次 2） | ✅ **唯一减量** | ❌ **不可逆、不可恢复** |

##### ⚠️ 那「回收状态」存哪？——**哪都不存**

> **持久化永远存原文；注入与否只取决于 GC 状态，而 GC 状态不落盘。**

这不是省事，是 [`00` §7 判据 8](00-设计哲学.md)（**能派生的就不要持久化**）**已经推出来的结果**——
而且它顺手关掉了一个一直标着「缺失」的问题（原先这里写的是「回收状态写在哪一行：**没有**」）。

| | 存哪 | 为什么 |
|---|---|---|
| **注入边界**（compact 记录 / release 标记） | ✅ **落盘** | 这是一条**事实**（模型生成过、或模型声明过），不可重算（§11.2 / §12.4） |
| **逐条的「这条回收了没」** | ❌ **不落盘** | 它是**加载期派生的**：边界 + 策略 ⇒ 结论。**没有第二个真相来源** |

⚠️ **一个意外的好后果**：**回收策略改了不破磁盘格式**——策略在代码里，字节里只有边界。
⚠️ **重启即重新决定**：`00` §4 早把「**激活**」列为 GC 触发源（「恢复即事件」，§8.3 同）——所以
「加载时按策略重新决定哪些回收」不是新机制，**它就是那条既有触发源**。

⚠️ **头要看得见降级**（[`05` §1](05-头设计.md) 的同形先例：「工具在、但被拒」要显示，否则用户以为工具不存在）——
「这条结果被回收了」也要显示，否则用户看到的是一段**看着完整、其实少了一半**的历史。

#### 九、压缩记录仍然永不可 GC

§11.2：它是那段历史的**唯一载体** ⇒ **永不可 GC**。今天没有这个类型；它出现时必须**在类型层面**钉住，而不是靠某处记得判断。

**启动时双向匹配**：数据根里的会话带目录路径 → 找 `.lilara`；扫到的 `.lilara` → 找数据根的会话。两路对账。

**目录移动 / 改名**：路径对不上但 uuid 列表对得上 → **可重新绑定**。反向映射表正好兜住这个场景（列表本身泄漏无害）。

⚠️ **销毁面（2026-10-05 实现）——这三条各自动的东西不一样，别混**：

| 命令 | 动什么 | 可逆 |
|---|---|---|
| `session.deactivate` | **只摘内存里的激活项**。磁盘一字不动（激活本来就是内存账，`state.json` 从不存它） | 是（下次 `session.activate` / 快照回落时重新载入） |
| `session.archive` | `spec.json` 加一个 `archivedAt`，**原地标记** | **是**（重跑同一条命令带 `--unarchive`） |
| `session.delete` | **整个会话目录**（记录 / 状态 / 配置一起）＋ 它占的声明 | **否**——`history.jsonl` 只追加、从不另写，删了就没了 |

⚠️ **归档会话仍然会被 `ListSessions` 列出来**，这是刻意的：`ListSessions` 是「一个项目下有哪些会话」
的**唯一定义**，而 `/claims` 也走它（归档的会话可能仍占着路径）——滤掉一半会让用户看到两份
自相矛盾的真相。**过滤在显示层**（头折叠、控制台照列）。

⚠️ 三条都**拒绝「正在跑」的会话**（不是原地掐断）：`Stepper` 的收尾会把 `state.json` 写回去，
留下一个**有 state、没 spec** 的目录，而 `ListSessions` 静默跳过它 ⇒ 下次同 id 建会话时
`WriteSpec` 会翻出这个孤儿 state。**半删状态比一句拒绝坏得多。**

### 8.1 项目是隐式的

**用户不需要意识到 project 存在**——和 Claude Code 一样，**一个文件夹天然就是一个 project**。不强制用户先建项目。Project 是**涌现**的，不是**声明**的。

#### 启动时**不初始化任何会话**

> ⚠️ **修正一个曾有的设想。** 原话是「配置提供商后，自动在当前工作目录准备一个初始会话」——**那是错的**：它把**策略**塞进了**机制**。

⚠️ **「启动时该不该建会话」是策略，不是机制**（[`00` §1.3](00-设计哲学.md) 机制与策略分离）。推论：

| | |
|---|---|
| **核心启动后，默认没有任何会话** | 一个都不建 |
| **建会话是一条命令** | `session.create`（[`03` §3](03-控制面协议.md) 早有），**谁调是上层的事** |
| **无头启动的核心不凭空造会话** | 那是策略，而核心不做策略 |

**「配置完提供商 → 自动建一个会话」是头的行为**：头连上核心 → 发现没有 provider → 要求先添加 → 添加完 → **由头调 `session.create`**。

⚠️ **由此，核心侧的"引导"退化成两件很轻的事**：

1. **解析数据根**（§8，纯机制，没有策略）
2. **对未知命令回答人话**（"还没有配置提供商"，而不是崩）

> **核心只负责"能不能"，头负责"该不该"。**

⚠️ **不引入多用户开关** —— 数据根的选择**本身就是隔离**（数据根解析见 §8）。

### 8.2 项目层不是运行时实体

⚠️ **最大的陷阱：Project 膨胀成迷你 ALP。** 一旦它开始持有事件总线、共享状态、常驻组件，重量就回来了。

> **Project 是数据 + 作用域，不是运行时实体。** 它没有循环，没有生命周期，不"启动"也不"停止"。

**Project 存在的理由**：会话天然有工作目录（工具要读写文件），而**工作目录就是资源边界**。多个会话落在同一目录 = 同一个项目。**这个聚类是客观的，不是人为抽象。**

### 8.3 激活：默认全部未激活

⚠️ **重启后所有会话默认处于未激活状态，不加载进内存。** 头主动要求激活某个会话，才加载它。

```
激活 = 加载记录 → 恢复锁（§12.8）
```

> **顺序不能反**：崩溃已让锁自动释放（§12.8），这中间别人可能占了地盘。

⚠️ **撤回一个概念**：曾经写的是"加载记录 → 做一次 release 检查 → 恢复锁"，但**「release 检查」这个东西没有定义、也不需要**——原因见 §12.4：**激活本身就是一次 GC 事件，回收是它触发的，不是一个额外的检查步骤**。

好处：启动不必批量恢复全部会话；**恢复锁从"启动时的批量操作"变成"激活时的单次操作"**。

### 8.4 库（store）：内容寻址的不可变对象

> **凡是被记录引用的字节，都在库里。** 这是 [`00` §2.1](00-设计哲学.md)「落盘的是骨架不是文本」**推广到二进制**。

- **内容寻址**（`sha256` 做文件名）→ 同一对象只存一份，**跨会话去重**；**引用即指纹**，与 [`00` §5](00-设计哲学.md) 同构
- ⚠️ **模型压根不该意识到库存在** —— 它是**控制面概念**。库对象渲染成协议原生块后，模型看到的就是**内容本身**，没有 id、没有来源
- ⚠️ **只读** —— 不可变 ⇒ **结构上排除冲突**（[`00` §7](00-设计哲学.md) 判据 4），**不受 §12 声明约束**
- **引用计数决定清理**：`release` / `compact` 让引用从记录里消失 → 计数归零 → 可回收（由 §11.1 的两种 GC 自然驱动）
- **库里也放快照**（[`00` §5](00-设计哲学.md)「结果 = 引用 + 快照 + 指纹」里的快照，渲染结果的大对象）
- 核心提供**清理功能**，允许用户自己清理会话或文件

⚠️ **实现（2026-10-06，回收批）——上面第一句现在是字面成立的**：
写入侧**总是 `Put` 一遍**（`Reclaim.Materialize`），过 `InlineThresholdBytes` 才在记录里留
`StoreBlock`、没过的**内联进记录而库里同样留一份**。
⇒ **内联与否只决定字节躺在哪**，不决定进不进库——库里因此真的有「凡是被记录引用的字节」。

⚠️ **两种库对象，靠 `mediaType` 分**：`text/plain` = 单文本块的**原始字节**；
`application/vnd.lilara.blocks+json` = **块数组 JSON**（混排 / 多块 / 纯图的快照）。
⇒ **读的人必须分得开**，混着读会让 `read` 的库对象吐出一段 JSON 来（而它本该是原文）。

⚠️ **「引用计数决定清理」今天不存在**，而且本批**没做**计数：回收的判据是
**「内容自己就够（取回得回）」**，不是「引用计数归零」——见 §8.0.2 二。
⚠️ **盘上仍然只增不减**：回收一字不写（判据只读），唯一的减量操作是**截断**（不可逆）。

### 8.5 工作区：其余文件

**走不了原生模态的东西，落进工作区**（`.lilara/inbox/` 等），**以普通文件路径**交给模型。

| | **库** | **工作区** |
|---|---|---|
| 模型看到 | **内容本身**（协议原生块） | **一个路径**，走工具处理 |
| 模型知道 | ⚠️ 无机制、无 id、无来源 | 文件系统（它本来就知道） |
| 生命周期 | 内容寻址 + 引用计数 | §12 声明 + [`00` §5](00-设计哲学.md) 指纹（全套现成机制） |

> **库面向「模型的眼睛」，工作区面向「模型的手」。**
> **眼睛看的东西不需要名字；手要操作的东西必须有路径。**

**路径**：客户端可指定，不指定则核心给默认落点。**路由与判据见 [`03-控制面协议.md` §9.2](03-控制面协议.md)**（判据 = **提供商配置里的模态能力声明**）。

⚠️ **工作区上传不受 §12 约束** —— 那是"**人类编辑**"那一格（本文件 §12.6 已认下的洞），**不新增机制**；会话照常收到**脏指示**。

### 8.6 写前规则

⚠️ **先落对象，再落引用。**

| 崩溃点 | 结果 |
|---|---|
| 写完库、追加记录之前 | **孤儿对象** → 引用计数 0 → 回收。**安全** |
| 追加了记录、写库之前 | **悬空引用**。**坏的那个方向** |

库是内容寻址的 ⇒ **重复写幂等，重试免费**。

> 与 §4「assistant 与 tool_result 一起写防半截轮」同形——**步边界持久化规则的二进制版本**。

## 9. 工具契约

见 [`00-设计哲学.md` §5](00-设计哲学.md)（工具观）、[`00` §2.2](00-设计哲学.md)（工具结果在上下文中的位置）。摘其要点：
- **四个钩子**：执行 / 渲染（**纯函数**）/ 优化（有损）/ **取消**（在飞调用的落点，见 [`04` §3.2](04-插件与内部结构.md)）
- **结果 = 引用 + 快照 + 指纹**，三态判定
- **不可重演类**（执行命令、发邮件、取时间）**永不可优化**，且**渲染结果冻结为「具体」载荷**——否则插件热重载会让**已发出的邮件在上下文里改写**（[`04` §7](04-插件与内部结构.md)）
- **淘汰规则**：ALP 的 `FileToolKit.Shared`（共享基类）不需要——**但它解决的问题（工具如何声明生命周期）仍然要解决**，落点是 [`00` §5](00-设计哲学.md) 的四钩子契约 + [`04` §2](04-插件与内部结构.md) 的「声明 + 回调」
- **权限类别**：工具自报 `ReadOnly | Consuming | Writing | Destructive`，供权限闸门查表（§3.5）。**未声明即取默认 `Writing`**（[`04` §5](04-插件与内部结构.md)）。「高危」的判据是**不可逆**
- **工具是插件的贡献，不是独立实体**；工具表是派生的（[`04` §1](04-插件与内部结构.md)）——**不要把它当成"第 6 条轴"或"第 6 个贡献面"**——轴与贡献面是两回事，条数见 §3.5 那张表（[`04` §3](04-插件与内部结构.md)）。⚠️ **这里原先写「轴只有五条」，而 `temperature` 加进来之后是六条**——**凡是要报条数的地方，去数那张表，别抄这句话。**
- ⚠️ **核心自带零个工具**（[`04` §1.3](04-插件与内部结构.md)）——`read` / `write` / `bash` 全部来自插件。**没有插件就是纯 chat。** 所以本节的「工具」一律指**插件贡献的工具**，没有"内置"这个类别
  ⚠️ **例外（2026-10-06 最小工具批）**：核心带了 `ls` / `read` 两个**内建**工具。判据是「内容 vs 机制」——
  那句「零个」说的是核心不提供**干活的能力**（写文件、跑命令），而这两个是**「模型能操作自己的工作目录」那条机制的唯一入口**。
  归属与理由见 [`04` §1.3](04-插件与内部结构.md) 那条修正。

### 9.1 工具集解析

```
tools(step) = 插件宿主收集的工具贡献 → 会话配置 ∩ 指令限制 ∩ 步覆盖
```

⚠️ **起点是「插件宿主的收集结果」，不是某个「工具注册表」**——工具不是独立实体，工具表是**派生**的（[`04` §1](04-插件与内部结构.md)）。⚠️ **没有任何插件时，结果是空集**，工具表为空——合法形态（[`04` §1.3](04-插件与内部结构.md)）。

⚠️ **成员定了，还要定顺序**：`sort by (priority, pluginId)`，**纯派生、不持久化**（§3.1）。工具表在 Claude 协议下位于**前缀最前端**，改它最贵——但**顺序稳定性由"不持久化"保证，不是由"只追加"保证**。

⚠️ **从容器里拿到的顺序一律视为随机**：`Dictionary` / `HashSet` 枚举序（.NET 下未定义，**一次 `Remove` 后新 `Add` 会复用空槽跑到前面**）· 文件枚举 · 反射 · 并行收集的完成序 · MCP 服务端的 `tools/list` 顺序。**顺序只从显式键来。**

⚠️ **今天那把键就是工具名，ordinal 升序**（2026-10-07 用户裁定「排序必须唯一」）。
⚠️ **它不是换了另一条规则，是本行那条规则的退化形**：在「一个 dll 贡献一个工具」的形状下
**`pluginId` ≈ 工具名** ⇒ **名字就是那把键**；而**键已经唯一时 tiebreak 是多余的**。
⇒ **不需要第二把键，也就不需要 manifest 字段**。
**ordinal 的理由、代价、以及重名那一格**（今天 `ToolExecutor` 的 `ToDictionary` 会抛，
**但抛在执行时**——那时请求早发出去了 ⇒ 要一条**加载期**硬错）见 [`04` §9.1](04-插件与内部结构.md)。

MCP 工具与插件工具在此汇合。

### 9.2 工具表 vs 权限闸门

> **想要模型「想不到」→ 工具表**（能力塑形，贵，只在冷窗口做）
> **想要模型「做不成」→ 闸门**（授权，免费，随时可调）

| | 工具表 | 权限闸门 |
|---|---|---|
| 表达 | 能力塑形 | 授权 |
| 粒度 | 会话级的静态属性（"聊天会话" / "编码会话"） | **步级的动态属性** |
| 代价 | 改它破前缀最前端 | 改一个浮动字段，**零成本** |

所以**粗粒度塑形照旧，细粒度授权走闸门**——各自待在成本付得起的地方。

⚠️ 但两者**不是替代关系**：纯聊天会话仍应只带聊天的工具，不是把 40 个工具塞进去再全部拒绝——那是把 token 浪费在永不使用的定义上。

⚠️ **工具限制的落点是闸门，不是工具表**（2026-10-07 用户裁定：**「不在于模型是否可以调用，而是调用后能不能生效，保住工具列表」**）。
⇒ 本节那条分工按这条裁定读：**表进请求（贵），闸在执行（免费）**——
落点在代码里是现成的两处，一行不用挪：`Stepper` 把工具表投影成 `ToolSpec` 进请求，
执行走 `ToolExecutor`。

**三个要钉死的点**：

1. ⚠️ **权限类别挂 `ITool`，绝不挂 `ToolSpec`。** 今天 `ITool` 上**没有**这个成员（`Kernel/Tool.cs` 明写「本批不做…权限类别」）。
   判据在 [`04` §7.2](04-插件与内部结构.md) 那张表：**工具的权限类别 ❌ 不破前缀**，**因为它不在请求里**。
   ⇒ 放进 `ToolSpec` = 把它写进**前缀最前端**，本节那条「免费」**当场作废**。⚠️ **这个位置选错测不出来，只会慢。**
2. ⚠️ **类别是插件契约 ⇒ 必须早于第一个插件 dll 落地。** 否则每个已发布的 dll 都得跟着改一遍。
   （它就是「管理权限之前总得先有个东西能被管」里那个**被管的东西**——**类别声明**，不是闸门。）
3. ⚠️ **一个非显然的后果：被拒的调用也是记录。** §3.6 ② 要求 `tool_use` ↔ `tool_result` **强制配对**
   ⇒ 拒绝**必须**写一条结果进记录，而**记录只追加** ⇒ **它永久留在时间线上**。
   **⇒ 由此推出：拒绝理由必须是「当时的事实、冻结成具体载荷」，不能在渲染时按当前权限档位重算。**
   否则同一个权限档位一改，**同一条历史会渲染出不同的原因**——「事实不可变」当场破。
   机制是现成的（[`00` §5](00-设计哲学.md)：**不可重演类 ⇒ 冻结成具体载荷**），
   **而「拒绝决定」正是不可重演类**（那条决定属于那一刻）。
   ⚠️ 这条不写下来，实现时几乎必然写成「渲染时按当前档位判」。

⚠️ **一个要认的代价**：模型会**去调那些它其实不该调的**（它看得见工具表）。
一次无用调用 = **一步**。⇒ 分工是：

> **策略性禁用**（这个会话就是不该有这个能力）→ **工具表**，在建会话那个**冷窗口**选一次
> （§3.1：「纯聊天预设 = 空提示词 + 空工具表」，它是**配置**不是权限）。
> **瞬时 / 实例性拒绝**（这一步不行 / 这个目标不行）→ **闸门**。

⚠️ **别拿闸门当「永久禁用」用**——那会变成模型反复调、反复被拒的死循环。

### 9.3 工具的三个扇面：上限 · 分页 · 元数据（2026-10-07）

⚠️ **本节是 2026-10-07 用户裁定的落点**：「read 文件大小…**必须有所限制**，尤其是大文件一个 read
下去直接给自己上下文撑爆了」·「偏移、限制长度我觉得都是必要的」·「ls 也许可以顺带包含一些
文件或文件夹的元数据…**防止模型一不小心 read 了一个大文件**」。

#### ⚠️ 三条各自是**不同性质**的东西，别当成一件事

| # | 是什么 | 判据 |
|---|---|---|
| **硬上限** | **结构**——模型**不可能**撑爆 | 真正的防线 |
| **`offset` / `limit`** | **结构**——模型**有退路** | 把策略变成能力 |
| **元数据** | **软信号**——模型**知道**该不该 | 只是辅助 |

⚠️ **元数据是辅助，不是防线**：[`00` §7 判据 5](00-设计哲学.md)「**意图靠工具表表达，不靠提示词请求**」
——`ls` 里写「这个文件 20 MB」是**告诉模型**，它可以照做、也可以忽略。
⇒ **「防住」要靠 `read` 自己的上限，`ls` 只降低「不小心」的概率。**

⚠️ **所以「加个上限数字」不够**：只有上限的话模型**只有两个选择**——要么拒（**永远读不了那个文件**）、
要么全读。**中间没有路。** 三条**一起**才完整：软信号告诉它、能力让它有退路、硬约束兜底。

#### ⚠️ `ls` 自己就是同一个洞，**而且更大**

`ls` 今天无上限（`ListTool` 把目录项**全列**）⇒ 一个 5 万条目的目录**一次结果就把上下文撑爆**，
**不需要任何大文件就能触发**。⚠️ 而**加元数据会让它更严重**（每条更贵）。
⇒ **两件必须一起做：加元数据 ⊗ 加截断。**

⚠️ **设计早就裁过这一条**（§12.5）：**展开枚举**（给头与清扫看的清单）**可截断**。
⚠️ 截断要**明说截了多少**——同 §3.6 ①之二「**最坏的失败不是少了信息，是多了一条假信息**」：
静默截断会让模型以为目录只有 50 个条目。

#### ⚠️ 上限只能有**一个源**（本仓反复栽的那个形状）

若 `ls` 说「这个文件太大，read 读不了」，而 `read` 自己也有一份上限 ⇒ **那个数字出现了两次**。

> 改 `read` 的上限而忘了改 `ls` 那句话 ⇒ **`ls` 当场开始说谎，而且没有任何东西会红。**

⇒ **判据**：上限只能有**一个源**（一处常量 / 一个函数），两个工具都从它读。
同 §8.0.2 那条「**两层判据必须共用一个谓词**」。

#### ⚠️ 「分段读」的坑：读回来的是**一段**，别让模型当成全文

读回前 8 KB，而模型可能当全文 ⇒ 又回到「多一条**假**信息」。
⇒ 结果里必须**显式写清**：`第 1–8192 字节，共 20,971,520 字节`。
**宁可明着少，不可暗着假。**（这条现在由 §3.7 的**框架**天然承担。）

⚠️ **上限那个数是策略值，取保守值 + 注释明写「这是占位」**——同 `Reclaim.ProtectedRecentResults = 4`
那条纪律（`01` §11.3 那条「最近 N 步」的 N 本身也是未定项）。

#### `ToolArgs` 只认字符串 ⇒ **它是复制粘贴的第一现场**

今天 `ToolArgs` 只有一个 `String` 方法，而 `read` 因此**加不了 `offset` / `limit`**（取不出数字）。
⇒ 加第四个工具时作者要么补一个 `ToolArgs.Number`、要么**自己写一份解析**——而那正是本仓栽过的形状。
⚠️ 它今天只有一个 37 行的文件、一个方法 ⇒ **现在把契约补全是零成本**。

#### ⚠️ 与本批的关系：`read` 的 `offset`/`limit` ⊗ §3.7 的框架**同批**

框架那一条（§3.7）是本节三样的**表达层**：`第 1–8192 字节，共 …` 与 `前 50 条，共 1240 条`
都落在框架里。**分开做等于把同一件事说两遍、走两条路。**

## 10. 子会话与后台执行

ALP 用了两套机制（父→子 `MailboxInputPort`、子→父 `report_to_parent` 直接注入），因为它的端口模型是消息驱动的。

**本项目用一套：纯注入。** 因为会话就是记录：

- **父 → 子**：往子的记录里注入消息
- **子 → 父**：往父的记录里注入消息（挂上"来自子会话 X"的来源标记）

**双向对称，同一机制。**

> **没有「信箱」这个概念，而这正是它好用的原因。** 信箱是为了补「tell to subagent 只能喊一次、必须当场收回结果」的缺陷——那是把子会话建模成**一次函数调用**。追加式注入没有这个缺陷：**可重复、不要求对方在线、不阻塞**。「信箱」的全部内容 = **派生树上的双向追加权**，而派生树本身就给出地址。

### 10.1 后台执行与事件回流

**子会话不是特例，它是「后台事项」的一类。** 统一视角：

| 后台事项 | 事件数 | 例 |
|---|---|---|
| 一次性 | 1（终态） | 后台 shell、长 HTTP |
| **流式** | N | **子会话**（每一步都可能有事） |

**回流机制完全相同**：事项的**值得上报的事件**追加进时间线并**入队**（§6.1），能否推进交给队列启动规则。

⚠️ **准确说不是"完成才激活"**：任何值得上报的事件**入队**（§6.1），**启动是队列的副产品**——**完成只是终态事件**。

三个动作全有归宿，无需新机制：

| 动作 | 归宿 |
|---|---|
| **扇出** | §4「步内默认并发执行工具」——一步内 N 次 spawn |
| **续话** | 父随时 `send(childId, …)`，子活着就收到 |
| **汇合** | 子的上报 = 注入父的记录 + 入队，由 §6.1 的启动规则合并 |

### 10.2 降噪：什么才值得打扰父

⚠️ **一个跑 20 步的子会话若每步都唤醒父，父被叫 20 次。**

**父只该看到两类事件**：

| 类别 | 例 | 时机 |
|---|---|---|
| **要我决策** | 缺权限、要审批、要澄清 | 立即 |
| **我落定了** | 终态、关键节点 | 可合并 |

**中间步骤是子自己的事。** 子是**决定何时值得打扰父的那个人**——这与"工具决定自己的渲染"是同一条哲学（[`00` §1.3](00-设计哲学.md)：谁的知识谁负责）。

**上报的形状**：

- 上报进父的**时间线**，载荷是**「具体」**（§3.4）而非托管——它**不可重演**，父在压缩掉它之前必须一直留着
- **必须有硬长度约束**，否则父的上下文被孩子淹没
- 落点：**产物写文件，上报只带指针 + 摘要**——这就是 [`00` §4.1](00-设计哲学.md)「保留知识、扔掉字节」跨会话的样子

### 10.3 权限范围：委托模型

> **子会话是委托，不是分身。委托的第一性质：授权范围 ⊆ 父。**

不满足这条的设计都是提权——一个能做成父做不到的事的孩子，就是沙箱逃逸。

| 维度 | 规则 | 理由 |
|---|---|---|
| 工具集 + **权限档位** | ⊆ 父（配置收窄） | 只减不增；**收窄的是档位，不只是工具集**（§3.5），**沿树传下去** |
| 目录 | 默认**共享父的项目**；要隔离 → git worktree（可选能力） | 同目录干活，声明树（§12.10）保证安全 |
| 父的历史 | **不可见** | 隔离的实质，也是防污染 |
| 危险操作审批 | **上提到头**，同时让父看得见 | 父是模型不是权威；且父可能正卡在等汇合上 |
| 深度 | **限量而非禁止**（区别于 ALP 的"禁止套娃"），硬天花板 | 防爆炸；收窄沿树传递 |
| 并发 | 全局池 **+ 树级配额** | 一棵树不能吃光 in-flight（§13） |
| 循环控制 | **继承父的熔断**（不做新预算） | §6.2 规矩 1 |
| 终止 | 父可停子；子上报通知父 | |
| 父停 | 子停止推进，**记录保留** | |

**审批为什么不经父**：让父批准孩子的危险操作是**剧场**——那是模型批准模型，不是安全边界；而且父此刻多半正阻塞在汇合上。**上提到头，同时让父看得见**（子状态在树形视图 / 浮动槽位播报），父就不瞎。

⚠️ **代价**：自主模式下被卡的孩子会**一直等**——**这正是本文件 §5「WaitingForInput 永不超时」该有的样子**；逃生口是头介入，或父判定它已无意义（**核心不做预算**，因为无人为它设预算，这正是 §6.2 规矩 1 的立场）。

**子会话预设**在这里第一次真正赚到钱：spawn 收一个**预设名**，预设 = 工具白名单 + **权限档位** + 提示词插件 + 模型。纯数据，无类型分支（§7.1）。

### 10.4 两个正交的结构

```
归属（作用域）          派生（运行时树）
  Project                 Session
     │                       │
     ├─ Session A            ├─ 子 Session A1
     ├─ Session B            │    └─ 子 Session A2
     └─ Session C            └─ ...
```

- **归属**回答："你能碰哪些文件、继承什么默认配置"
- **派生**回答："谁创建了谁、谁向谁汇报、谁停谁"

**两者正交。** 子会话归属于**父会话所在的项目**，但在派生树上是子节点。把两者合并会立刻出问题——比如"项目根会话"死了，它凭什么是项目的根？

## 11. GC 与压缩

### 11.1 两种操作压的不是同一种东西

| | 被动 GC | 主动压缩 |
|---|---|---|
| 对象 | **托管载荷**（快照、浮动残留、旧提示词） | **事实本身**（时间线上的事件） |
| 手段 | 丢弃可重演的字节 | **摘要替代** |
| 损失 | 失去"字节等同"，**不失去信息** | 失去原文，**换得信息密度** |
| 效果 | **上下文**变小，**磁盘一字不动** | 同上——**磁盘也一字不动** |
| 触发 | 前缀失效 / **释放事件**（见 §12.4） | 阈值 / 自决 / 头下令 |

> **GC 是缓解，压缩是治本。**

> ⚠️ **「效果」那一格改过**（2026-10-06）：原文写的是「空间回收 / **真正减少增长**」，
> 而**两者都不动磁盘**——加载边界模型（§11.2）与倒查（§12.4）都是**加载期解释**。
> ⚠️ **磁盘上唯一的减量操作是截断**，它**不可逆且不可恢复**。完整契约见 [`§8.0.2`](01-会话设计.md)。

⚠️ **回收不是「删掉」，是「换个渲染」**（§8.0.2 第四节）——而且**可恢复**（`fetch(id)`）。
⇒ 与其说是空间回收，不如说是**「把字节换成指针」**。

**耦合点**：主动压缩**自己制造前缀失效**，而前缀失效正是 GC 的触发条件。

> **主动压缩是 GC 的又一个触发源，GC 是主动压缩的清理工。** 两件事在同一时刻发生，代价只付一次。

### 11.2 压缩就是一个特殊的工具调用

压缩**不改变文件落盘的历史记录**——它是**加载边界**：系统加载上下文时**只从最近的压缩记录开始加载**。

```
加载窗口 = [系统提示词][首要提示词][压缩记录(摘要)][增量事件][浮动槽位]
```

**三个必须钉死的后果**：

1. **压缩记录是唯一载体 → 永不可 GC。** 摘要就是那段历史的**全部**，属于"不可重演"类。同理**压缩工具是核心特权工具**，插件不能实现——它改变加载边界。
2. **是滚动累积摘要，不是分层折叠。** 第二次压缩看到 `[上次摘要 + 增量]`，产出**覆盖全部历史**的新摘要。每份新摘要**蕴含**旧摘要 → 不会层层叠加损耗；旧压缩记录天然可裁剪。
3. **压缩立即生效。** 第 K 步调 `compact`，**第 K+1 步的请求就必须是压缩后的窗口**。工具结果为空（摘要本来就是模型自己在参数里写的），它的意义在于**标记**。

### 11.3 保护带：按步，不按 token

| 保护 | 对象 | 规则 |
|---|---|---|
| **GC 保护窗** | 工具结果 | 最近 N 步**不优化** |
| **压缩保护带** | 时间线事件 | 最近 N 步**不压缩** |

> ⚠️ 「折叠」是「压缩」的早期用语，**不作为术语沿用**（[`00` §8.1](00-设计哲学.md) 作废的是"分层折叠"那个*方案*，与保护带无关）。

**按步而非按 token 的理由**：保护带保护的是**动作链**，不是内容预算。模型失忆的真正危害**不是忘了内容（可以重读），而是忘了因果**——不知道为什么读那个文件，重读也无从下手。

token 计数会**不可预测地塌缩**：一个超大文件从最新往前吃光预算，窗口瞬间归零。**条数给出稳定的"往回 k 步"。**

**边界情况**：保护带自己可能撑爆阈值（某步读了 20 个巨型文件）→ 保护带要能**在压力下降级**（N → … → 0）。平时按 N，危急时核心强制出手。

⚠️ **实现（2026-10-06，回收批）**：`Reclaim.ProtectedRecentResults`（**最近的几条工具结果**，
不是「几步」——一条工具结果属于哪一步是**派生的**，不落盘，`00` §7 判据 8）。
⚠️ **这个数是占位的**：本节只写了「最近 N 步」，N 本身是**未定项**。
⚠️ 「压力下降级」那一半**没做**——今天没有压力信号（阈值、token 计数）可用。

### 11.4 压缩的实现形态

| | `compact` | `lite_compact` |
|---|---|---|
| 谁执行 | 当前模型 | **指定轻型模型**（**换模型**接管） |
| 额外调用 | 无（搭正常**步**） | 有（换模型，需重读全量上下文） |
| 缓存 | **命中** | 不命中（新模型＝新前缀） |
| 摘要反映 | **当事者**的理解 | 旁观者的理解 |
| 成本 | 主模型费率 × 摘要长度 | 轻模型费率 × 全量上下文 |

**两个工具不共存**（配置选择其一）。

⚠️ **硬约束**：lite 模型必须**读得下**被压的全部上下文。**lite_compact 省的是钱，不是窗口。**

### 11.5 工具表收窄 + 强制调用

> **收窄工具表是必要条件，强制调用（`tool_choice`）才是充分条件。**

用户发送压缩指令 → **模型只剩压缩一个工具可选** + `tool_choice` 强制。

| 杠杆 | 强度 | 代价 |
|---|---|---|
| 工具表收窄 | 只剩一个，大概率会调 | 破前缀（但已在窗口内） |
| `tool_choice` 强制 | **协议层保证必须调** | **参数级，不碰前缀** |

⚠️ 待实证：**部分模型在开启思维链时不允许强制 `tool_choice`**。

**强制压缩是持久化指令，不是瞬时动作**：

```jsonc
// state.json
{ "pendingDirectives": [{ "kind": "force_compact" }] }
```

否则核心崩在压缩途中，重启后指令丢了、工具表恢复正常、模型接着跑——**永远压不成**。

**模型在压缩的同一步里顺手调别的工具？让它调。** 它自己会退化成本来就要的行为：

```
[压缩记录(摘要)] [被顺手读的 a.cs] [增量…]
      ↑加载边界从这里开始
```

摘要 + 紧跟其后的新鲜文件内容——**和"压缩时结构化输出激活清单"是同一个形状**。结构上不构成问题，就不需要规则去禁止（见 [`00` §7](00-设计哲学.md) 判据 4）。

### 11.6 预取：压缩即预取

> **总结时直接激活接下来还会用的文件。**

**压缩边界本来就是一次前缀失效，而那正是唯一免费的改写窗口。** 既然反正要重建，就在此刻把接下来要用的文件一并读了：

```
压缩调用 → { 摘要, activate: [文件A, 文件B] }
              │
              ▼
   压缩记录   +   A、B 的新鲜内容块（紧跟其后）
```

三重收益：**省调用**（不必再花工具调用重读）· **保新鲜**（读的是改写后状态，天然无脏数据）· **不额外破缓存**（缓存已在压缩点破了）。

实现：摘要调用是**结构化输出**（摘要 + 激活清单）——这就是"特殊系统提示词"的落点——**摘要提示词不只要求总结，还要求预测下一步需要什么**。预取的块**直接带新鲜快照 + 指纹**进来，后续 GC 判定照常工作。

### 11.7 触发与时机

| 触发 | 何时 | 代价 |
|---|---|---|
| **阈值**（兜底） | 上下文逼近上限 | 反正要破缓存，必做 |
| **空闲 + 缓存已冷**（默认甜点） | 会话闲着且缓存本来就过期 | **几乎免费** |
| 模型自决 | 模型主动调压缩工具 | 中 |
| 头下令 | 用户手动 | 中 |

> **「空闲 + 缓存已冷」是甜点**：此时压缩不额外破坏任何东西，而且没人在等。**建议作为默认的主动压缩时机。**

**成本可配**：用哪个模型做摘要（⚠️ 省小钱亏大钱的典型）· 摘要粒度。

⚠️ **实现（2026-10-06，回收批）——本节的四个触发源一个都没接**。
今天的触发源是**手动**（`session.gc`，用户裁定「先手动、后续再加自动」），
而它与本节这张表是**两件事**：这张表讲的是**压缩**的时机，回收今天只被手动触发一次。

⚠️ **这不是省略，是与 `00` §0 同向的**：回收改的是前缀**中段** ⇒ 每触发一次破一次缓存
⇒ **窗口本来就不该自动开**。而 `00` §4 列的那四个触发源（前缀失效 / 主动压缩 / 资源释放 / 激活）
**今天一个都还不存在**：缓存过期信号不在核心手里 · 压缩整块未做 · 声明系统未做 ·
`session.gc` 也不在激活路径上。⇒ **「重启即重新决定」今天是「重新决定**只有你手动喊**」**。

⚠️ **接上「激活」试过一次，撑回去了**（2026-10-07，`27c69b5` 落 → `36a1870` 撑回）。
**这一段的全部价值在下一次要接自动触发源的人身上**——它不是「试错记录」，是一条**判据**：

> **「进了内存」≠「开始用」。** 而 `CoreHost.Activate` 是**四条路径的汇合点**，其中一条不是「开始用」：

| 路径 | 是不是「开始用这个会话」 |
|---|---|
| 控制台 `session.activate` | ✅ |
| `CommandDispatcher.TryFind` 的 miss 回落 | ✅ |
| **`ControlServer.TryFind` 的 miss 回落**（`/state` / `/history` 都走它） | ❌ 只是**看一眼** |
| **头首次加载**：`app.js` 对每个它还不知道的会话各拉一次 `/state` | ❌ 只是**扫列表** |

⇒ 挂在 `Activate` 上 = **打开头一次，全部会话都被回收一次**（`_activated` 只增不减，
只有显式 `deactivate` 才摘）。会话越多越贵，而你什么都没做。
⚠️ 更根本的是它**把这一档实现成了另一档**：激活本该是**窗口触发**（前缀反正要重建、顺手捡），
而「刚打开页面」时前缀**本来是热的** ⇒ 窗口没开，那次回收是**主动破中段**，
正是本节的「压力触发」——**用错了档位，代价从零变成全废**。

⇒ **要接它，落点是「第一步真的要拿它渲染」那一刻**，不是「它进了内存」那一刻。
（那也顺带解释了为什么 `deactivate` 之后重算是对的：那时**下一步一定会重新渲染**。）

⚠️ **要靠压力来触发的那一档，单独说清楚**（2026-10-07）：`00` §4 那四个触发源**全都以「窗口已经开了」为前提**
——前缀反正要重建，回收是**顺手捡**，边际成本为零。而 §11.3 那句「保护带**在压力下降级**」是**另一回事**：

| | 窗口触发 | 压力触发 |
|---|---|---|
| 前提 | **前缀已经失效**（激活 / 换预设 / 外力改 / 压缩 / 释放） | 前缀**好好的**，但上下文要爆了 |
| 回收的代价 | **零**——反正要重建 | **主动破位置 0** ⇒ 每破一次全废 |
| 类比 | 捡 | **买** |

⚠️ **压力触发是唯一会"主动制造失效"的一档，所以它的判据必须严**：一旦松了，就退化成
**每步回收、每步破前缀**，把回收省下的全赔进去。⇒ **本批只做窗口触发的一档**，
压力那一档留到有真信号（阈值 / 用量）时再说，**且它必须先证明"这一次破前缀换回来的比失去的多"**。

### 11.8 显式 GC —— 已由「资源释放」取代

**结论：不做独立的显式 GC。**

用户最初的设想是"标记与回收分离"——模型随时**标记**（"这个观测我用完了"，零成本），核心在下一个免费窗口**回收**（"模型表达意图，系统决定时机"）。

**作废理由**：`release`（见 §12）已经提供了这个能力的**唯一有价值的形态**，且更好——

| | 标记/回收分离 | release |
|---|---|---|
| 性质 | **模型主动要求 GC** | **释放资源**（正常动作）→ **事件触发** GC（§12.4） |
| 时机 | 任务中段任意时刻 | **任务边界**，工作集真的是垃圾 |
| 前缀代价 | **收费的**（自己制造失效） | 落在边界上，**增量式压缩**，代价被摊掉 |
| 粒度 | 单个结果 | 整棵声明树 |

在任务中段把单个结果标记为可回收，意味着**为省一点上下文而主动破坏前缀**，而保留下来的东西本来还会继续便宜地留在缓存里。**这是微操，收益不抵代价。**

> **release 是 GC 的正确粒度。** 上下文不再增长于任务中段，只在任务边界收敛。
>
> ⚠️ 而且**连"主动"这个词都不该用**——模型只是释放资源，回收是**被触发**的（§12.4）。

### 11.9 流式：一个标志，不是一套机制

> **流式是控制面关注点，不是会话关注点。**

⚠️ **根本理由：前缀在步的中间本来就不可用。** 要构造请求，必须先知道**完整**的模型输出（才能填 `tool_result`、才能知道有没有工具调用、才能决定下一步）。所以：

> **模型输出在流式期间只存在于内存，落盘只在步结束。**

这与「**步是持久化的原子单位**」完全一致（§4）——**没有任何完整性风险**：崩了，这一步就当没发生过，反正它本来也没落盘（§4 的步边界持久化）。

**因此流式只是一个渲染标志**：

| | |
|---|---|
| 核心侧 | 解析增量 → 转发事件（[`03` §4.1](03-控制面协议.md)），**不落盘** |
| 步结束 | **合并成一条完整模型消息** → 按正常路径落盘 → 这就是唯一的事实 |
| 断开续传 | ⚠️ **没有**。重连时头只能拿到"已完成的"——未完成的那一步尚不存在于记录里 |

> **"断线不能续传"不是缺陷，是"事实不可变"的必然**：那一步还不是事实。头看到的半截文本是**预览**，不是记录。

⚠️ 唯一需要决策的是**头的呈现**：是"半截文本立刻显示"，还是"取完整块后一次显示"。**那是头的策略，核心两种都支持**——核心只负责把增量转发出去。

⚠️ 一个必然推论：**流式的不确定前缀与缓存无关**——缓存只认已构造好的请求前缀，流式发生在请求**之后**。

## 12. 资源声明与释放

> **母题是文件系统。** 多 agent 并行互相捣乱，在 ALP 里是分布式问题；在单核心架构里降级成**进程内的一次路径比较**。

### 12.1 核心红利

**核心是本设备唯一的** —— 这条最初只是防御性理由（"避免竞争"），实际是**进攻性**的：

> 我们天然持有统一调度的权利。多 agent 的文件冲突问题**不存在**，只剩一次路径判定。

**判定规则**：两个声明冲突 ⟺ 一个路径是另一个的**前缀**。

⚠️ **这条规则有一个例外：同一派生树内不阻塞**（否则父子当场死锁）。见 §12.10。

⚠️ 路径规范化要求：Windows 下需处理大小写不敏感与符号链接。

### 12.2 检查是自动的，声明是主动的

⚠️ **声明不是强制的。** 若要求每次修改都先声明，仪式过重——写一个文件是**原子的、瞬时的**，没有"被打扰"的窗口。

**真正的机制是两格**：

```
写入时（自动）：目标在他人声明内？ → 是则阻塞，否则放行
声明时（主动）：我要做工程 → 独占这片区域 → 期间他人写入被阻塞
```

- **检查自动** —— 内置修改功能天然受锁限制；目标**未被占领时甚至不需要建锁对象，检查通过即放行**
- **声明主动** —— 锁的意义是模型**认为自己需要在区域内搞大工程、不被打扰的时候才启动**

⚠️ `check-then-write` 存在竞态（检查完、写入前别人刚好声明）。因为工具执行在**同一进程内**，把"检查 + 写入"做成不可交错的原子段即可——**不需要为此引入真正的锁对象**，一把瞬时微声明足够。

**那 claim 在保护什么？**

不是"保护文件不被并发写"，而是：

> **保护我的工作集不被作废。**

威胁模型：读了 10 个文件、推理到一半，别人改了其中 3 个 → 快照全脏 → 得重来。**claim 防的是这个**，手段恰好是"让别人进不来"。所以它是 opt-in——**只有当你有"正在进行的理解"时，才有东西值得保护**。

**一个机制，四张脸**：

| 身份 | 体现在 |
|---|---|
| **互斥单位** | 期间他人写入被阻塞 |
| **回收单位** | 释放 → 清扫（§12.4） |
| **可见性单位** | 头显示"谁在动哪些文件" |
| **等待单位** | 抢不到 → **WaitingExternal**，锁释放时被唤醒（**解除阻塞**，不是 §6.1 的「启动」——它是 §6.1 启动条件里「未被阻塞」那一项） |

> **本文件 §5**（状态机）的 `WaitingExternal` 此前是个空状态，**资源声明给了它第一个具体用例**。

### 12.3 扩张协议：抢占-重启-等待

模型常常**一开始没预料到**要锁某个目录，意识到时已被占领。因此：

```
要新资源
  → 扩张：先放掉全部锁（纯锁操作，不动内容，见下）
  → 原子化重取（旧的 + 新的，一次给全）
  → 取不齐 → 空手等待，不持任何锁；资源管理器按 FIFO 逐个处理申请，
             一旦满足即解除阻塞
```

**关键不变量：等待者不持有任何锁。** 死锁不是被排序规则排除的，是**被这个不变量排除的**——永远不出现"A 持 1 等 2、B 持 2 等 1"。

⚠️ **「扩张」与「release」是两回事，必须分开**：

| 操作 | 放锁 | GC | 清理 | 需清单 |
|---|---|---|---|---|
| **扩张 (expand)** | 全部 | ❌ | ❌ | ❌（就是要清空重取） |
| **release**（§12.4） | 清单指定 | ✅ | ✅（含未改动残留） | ✅ |

> **扩张本质是扩张而非释放**——它顺带清空了锁，但**不动内容**。否则扩张一次就冲掉工作集，代价不可接受。

#### 扩张既不触发 GC，也不失去机会

⚠️ **扩张掉锁是一个事件，但它不是 GC 事件。** 扩张**只是换一批锁，不动内容**——理由就在上面那张表：真在扩张时清扫，等于夹带一次 `release`，而 §12.3 明说不可接受。

**它也不失去 GC 机会。** 释放集只可能**变小**（扩张后拿回来的声明仍在），所以**扩张后那次 `release` 覆盖得住**——GC 等它。

> **一次资源动作，一次 GC 机会。** 扩张是锁操作（`放锁 → 原子重取`），`release` 才是内容操作（`解锁 + GC + 清理`）。

**已认下的代价**：扩张失败时会丢掉原有的锁 → 可能出现"本来有得用，扩张失败后连原来的也没了"。**在找到更好方案前接受这个代价**，因为它换来的是"无死锁"这个更强的性质。

**调度**：资源管理器在有会话释放资源时，**按先来后到（FIFO）顺序**逐个处理占有申请，一旦满足即解除该会话的阻塞。

> FIFO 天然**无饥饿**——等待者不会被新来者插队。

### 12.4 release：释放即回收

任务完成后释放声明树。**这个动作要求模型提供要释放的资源列表**（也可直接全选，即树内全部释放）。

```
release(scope: [...], summary: "...")
          │             │
          │             └─→ 取代被清扫的字节 → 上下文保留「知识」，扔掉「字节」
          └─→ 既是解锁清单，也是 GC 清单
```

**它同时做三件事**：

1. **解锁**
2. **触发 GC** —— 上下文剧变（本来要等到缓存失效或压缩）
3. **额外清理** —— 连带收起**未改动**的文件（工作集整体退场，不留残渣）

⚠️ **这是「事件驱动的 GC」，不是"模型主动要求 GC"。** 模型做的是**释放资源**（一个正常的动作）；**GC 是这件事引发的事件**。区别很实在：

- 模型不需要理解 GC，**只要正常释放**
- 释放集为空时**什么也不会发生**（见 §12.3 那个条件）
- 所以"主动 GC 是收费的"这个顾虑**根本不成立**——它不是主动的，是被触发的

**为什么这解决了"超前 GC"的紧张感**：`release` 不是随机 GC，它是**任务边界**。任务边界上工作集**真的是垃圾**——此时为保缓存留着它，等于为一批只剩缓存价值的内容永久付费。而且它**自我调节**：不在任务中段 GC，只在边界 GC；若不在此 GC，上下文继续膨胀，最终仍要压缩，**只是那时垃圾更多**。

> **release 是增量式压缩。**

**统一视角 —— `release` ≈ 作用域化的 `compact`**：

| | 范围 | 摘要 |
|---|---|---|
| `compact` | **全部**历史 | 一份 |
| `release` | **本任务的工作集** | 每条声明一份 |

**"保留知识、扔掉字节"** 回答了"释放后还想记得那个文件怎么办"——**摘要就是那个"记得"**。想连字节一起留，那就别释放。

#### release 的加载语义：倒查

⚠️ **`.jsonl` 永远不重写——「简化」是加载期解释，不是落盘时改写。** 这保住了"事实不可变"，比覆盖层干净（[`00` §8.1](00-设计哲学.md) 作废的那个方案）。

加载会话时**从尾往前扫，只扫标记、不加载内容**：

```
从尾往回扫（只扫标记）
  ├─ 第一个 release  → 记下位置 R
  ├─ 第一个 compact  → 开始计数
  └─ 再往上 n 步      → 停止，从此处往下加载
```

**以 R 为界解释**：

| 区间 | 加载方式 |
|---|---|
| `≥ R` | **原文**（新鲜工作集，本来就该是原文） |
| `< R` | **简化结果** |

⚠️ **唯一例外：压缩记录在简化区内仍按原文加载。** §11.2 定死了「压缩记录是唯一载体 → 永不可 GC」——若它落在 `< R` 区被简化掉，那段历史的**全部**就没了。

> **compact 标记永远存在**（除非从未压缩），所以"扫到第一个 compact 才开始计数"不会空转。

⚠️ **恢复（激活，§8.3）是一次 GC 事件**——工作集在崩溃期间可能已不成立。**不是一个叫"release 检查"的额外步骤**：激活本身就是事件，回收由它触发。

### 12.5 展开上限：阻塞与展开必须分开

目录展开需要上限，但**截断的清单 = 有洞的阻塞**——若靠展开清单判冲突，上限会造成"锁了个寂寞"。

**解法：把两件事分开。**

| | 粒度 | 需要展开 |
|---|---|---|
| **阻塞判定** | 路径前缀判定 | ❌ 天然完整，**无上限问题** |
| **展开枚举** | 文件清单 | ✅ 服务可见性与清扫，**可截断** |

> **阻塞按声明粒度（目录节点）判定；展开只用于"给头和清扫看的清单"。** 上限因此永远不会削弱互斥性。

### 12.6 分级保障：能防的防，能察的察

**不假装能防住一切。** 三层能力边界必须明确：

| 层 | 手段 | 覆盖 |
|---|---|---|
| **预防** | 核心的文件访问 API（写入前检查是否落在他人声明内） | **走该 API 的插件工具** —— ⚠️ **核心自己没有工具**（[`04` §1.3](04-插件与内部结构.md)） |
| **检测** | **指纹** | 全部——含绕过 API 的、MCP 的、外部进程的 |
| **无能为力** | —— | **人类编辑**、进程外改动 |

> **声明管住的是「会话之间」的竞争，不是「世界」的竞争。**

四个洞要认：

| 洞 | 说明 |
|---|---|
| **越界写入** | 会话写到自己没声明的区域（只要不撞他人声明，**默认放行是正常的**；撞了则被 §12.2 的自动检查拦住） |
| **人类编辑** | 锁只约束会话，**约束不了坐在编辑器前的用户** |
| **范围外的读** | 读不需要声明（§12.7），读到的东西不在锁的庇护下 |
| **外部资源** | HTTP / DB / 时间根本不在文件系统里 |

两条机制互补：**声明覆盖"我知道会冲突"的部分，指纹兜住"我不知道的"**。指纹不是被取代，而是被**收窄了适用范围**。

### 12.7 读不需要声明
**读不声明**——不在锁的语义里引入"读"这个概念。理由：我们已经有**脏指示**，脏状态写进上下文即可（浮动内容或中间内容）。

脏指示有两种可用形态：

| 形态 | 放哪 | 语义 |
|---|---|---|
| **状态型** | 浮动槽位 | "当前持有的这些引用，哪些脏了" |
| **事件型** | 时间线 | "你刚读的 a.cs 在 t 时刻被改了" |

> **浮动上下文 = 状态播报栏。** 时间、模型配置、文件脏状态——全是"此刻的世界是什么样"。

**读与写的不对称是有意的**：写的代价是**污染别人的工作集**（所以自动检查），读的代价只是**自己的工作集可能过期**（所以只需告知自己）。

### 12.8 崩溃语义

**锁在会话崩溃后自动释放**（否则死掉的会话会一直掐着锁）。

**会话重启后自动重新获取锁**；若已被其他会话占领，**就等着**（进入 WaitingExternal，由 FIFO 队列调度）。

> 注意这意味着崩溃到重启之间，别的会话可以合法抢占它的目录。这是接受的——那个会话已经停了，让它干等更浪费。

⚠️ **父的队列（§6.1）必须进 `state.json`**，连同**它正在等哪些后台事项 / 子会话**。否则重启后汇合关系丢失，父**不知道自己还在等谁**——要么永远不醒，要么被已经死掉的事项吊住。

⚠️ **写前规则**（§8.6）也属于崩溃语义：**先落对象，再落引用**，否则会产生悬空引用。

### 12.9 声明是可追加的

声明**可追加**（模型后来才意识到要锁别的目录）。但每次扩张都走 §12.3 的完整协议：**释放全部锁 → 原子重取（旧的 + 新的）**。

⚠️ 由此推出的实践建议：**声明宜粗不宜细。** 因为每次扩张都要冒着"重取失败、空手等待"的风险，逐文件细粒度声明会频繁触发扩张。**声明目录而非文件**是常态。

### 12.10 声明树与作用域天花板

⚠️ **先补一个洞。** §12.2 定的是**声明 opt-in**，默认不声明。若字面执行"子只能占父持有的树" → **父没声明时，子什么都占不了**——规则会在最常见的场景下把子锁死。

**边界得是作用域，沿派生树单调收窄**：

```
ceiling(根) = 项目工作目录
ceiling(n)  = 父的声明（若非空），否则 ceiling(父)
子的声明    ⊆ ceiling(n)
```

- **父声明了** → 子树活动范围 = 父声明的范围 ← 这就是委托边界
- **父没声明** → 上界自动落到项目目录，**行为与现在一致**
- **子想越出** → **不能自己扩**，得让父扩张（§12.3）——而"我要申请"正好是 §10.2 的**「要我决策」**事件，会把父叫醒

**这条规则顺手回答了「树内声明到底在干什么」。**

树内不互斥（§12.1 例外），所以**树内声明根本不是锁**。那它是什么？——**作用域声明**：

| 用途 | 对应 |
|---|---|
| 限定子树活动范围 | 上面的 ceiling |
| **释放时的 GC 单位** | §12.4 |
| 可见性 | 头显示"谁在动哪些文件" |
| 它自己起子时的委托边界 | 递归 |

于是**「子不能和兄弟抢树」不需要额外规则**——**树内没有可抢的东西**。对**非上级**则照旧阻塞（§12.1 原样），那是真的互斥。

**一个要明确的分寸：ceiling 管的是「声明」，不是「写入」。**

子越出 ceiling 去写一个**没人声明**的文件——按 §12.2 的哲学**照样放行**（写入是原子的、瞬时的，没有被打扰的窗口；重加写沙箱等于把刚拆掉的仪式装回去）。这一格交给**检测**：

> **预防管「声明」，检测管「实际动作」。** 与 §12.6 一致——**能防的防，能察的察**。

**代价要认**：**兄弟互相覆盖，互斥机制不拦。** 但这正是 §12.6 说的"防不了也**不该防**"那一格——真拦起来，兄弟争同一对资源就会触发 §12.3 那个"空手等待"的活锁，而且是**自己给自己造的**。检测层照常兜底（脏指示）。

⚠️ **扩张同样可能失败**：§12.3 的"取不齐 → 空手等待"适用于任何声明操作，包括子的这次。**失败不破坏上面的 ceiling 规则**——子只是回到"未声明任何东西"的状态，等父替它拿。

## 13. 并发（core 级）

**本节只列已定项，细则待多会话调度阶段展开。**

- **资源管理器是核心的一个组件**（§12 的调度者）：持有全部声明，按 FIFO 处理申请，**解除阻塞**的会话（解除 ≠ 启动，见 §5）
- **未被激活的会话不占任何运行时资源**（§8.3）——这补上了 §2「空闲会话占资源 → 不占，它躺在磁盘上」的机械依据
- **队列（§6.1）与运行标志都在 `state.json`** —— 换出/崩溃后待办不丢
- 会话**内部串行**（绝不同时跑两步）
- 会话**之间并发**，但有**全局并发上限**（in-flight 模型调用数）
- 同一目录多会话 → **允许**（多 agent 协作场景常见），互斥由 §12 的资源声明提供
- 会话在资源声明上等待时进入 **WaitingExternal**，由资源管理器的 FIFO 队列调度

**已认下的代价**：①"自己改的自己知道"这个优化失效（是优化损失，非正确性问题）②语义冲突无法自动消解，只能靠头的可见性让用户看见。
