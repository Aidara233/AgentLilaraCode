# 控制面协议

> 本文是**头的接口面**：头能下什么命令、能收到什么事件、怎么重建视图。
> 会话本体见 [`01-会话设计.md`](01-会话设计.md)，调度见 [`02-多会话调度.md`](02-多会话调度.md)。

---

## 1. 三条判据

1. **核心不关心头在不在** → 头断连不影响任何东西
2. **命令投递即返回，结果走事件** → 没有任何 RPC 式阻塞调用
3. **头是无状态的** → 状态在核心，头随时可以重建

**结论：一条 WebSocket（双向、持久、有序）+ 一组 HTTP（一次性读 / 大对象）。**

## 2. 三层消息

| 层 | 方向 | 语义 |
|---|---|---|
| **命令** | 头 → 核心 | 改变状态。**不返回结果**，只回执 |
| **事件** | 核心 → 头 | 已发生的事实，**有序、单调增 id** |
| **快照** | 核心 → 头 | 全量状态，用于**重建视图** |

> ⚠️ **「命令不返回结果」是三者的分界线。** 要结果的都是**查询**，走快照那条路。
>
> ⚠️ **唯一例外：分配型命令**（`session.create` 等）——它**必须**回传新身份（`sessionId`），否则后续命令无从指涉。回执仍是 `ack(id)`，只是带上分配的 id。

## 3. 命令（头 → 核心）

```
# 会话生命周期
session.create(projectKey?, preset?, cwd?, title?, askTimeoutMinutes?) → sessionId
                                        # ⚠️ askTimeoutMinutes（2026-10-11）：一次询问最多等多少**分钟**。
                                        #    缺省 = 不超时。必须 > 0（0/负数 ⇒ rejected，见 01 §3.8）。
                                        #    它是「无人看管的会话撞上要授权的东西」那条路的答案。
session.activate(sessionId)
session.deactivate(sessionId)
session.archive(sessionId, archived?)   # archived 缺省/true = 归档，false = 取消归档
session.delete(sessionId)
session.start(sessionId)                # ⚠️ **真的会推进一步**（2026-10-12 打断批改）
                                        #    此前是 no-op，而它一直是**接了**的 ⇒
                                        #    先 start 再 send 的客户端拿到 ack 却一步不跑、不报错。
                                        #    ⚠️ 它也是**唯一**能在「崩在步中」之后把那个会话
                                        #    收回来的命令（那时队列是空的，`send` 用不上）。
                                        #    回执带 Note 说清结果（「开始推进。」/「已经在推进了。」/
                                        #    「没有待办，直接推进一步（继续）。」）
session.gc(sessionId)                   # ⚠️ **观察口，不是任何东西的前提**（2026-10-11 改）
                                        #    判定住在渲染里、每次现算（01 §8.0.2），所以它
                                        #    现在**不含点杀**（那要碰文件系统）⇒ 它报的数比
                                        #    模型实际收到的**少**。见下面的注。
```

⚠️ **`session.gc` 的性质 2026-10-11 变过一次**（`01` §8.0.2 / §11.3）：它原先**写入**一份
内存账（`SessionHandle.Reclaimed`），那份账是回收的真相来源；判定搬进渲染之后它**只观察**——
立刻算一次并把结果说出去。⚠️ **它不再是触发源**：回收不需要有人喊。
⇒ 它今天唯一的用途是「**现在会收掉几条**」这个问题的一个粗略答案。

⚠️ **而它报的数与模型看到的不是同一份**：它走 `Reclaim.Decide`（**只有距离与线**），
而渲染那条带 `staleProbe` 的重载**还并上点杀**。⇒ **它偏小**，而且差额随「有多少条过时」变。
⇒ 别拿它的数去判断「模型到底收到多少」——**那个数只能从渲染那一侧看**。

```
# 预设（系统提示词的存放；01 §3.1）
preset.set(id, content)                 # 写入 <数据根>/presets/<id>.md（content 原样，不折叠空白）
preset.list()                           # 列出 id（头做下拉用）
preset.delete(id)                       # 不存在 ⇒ 拒绝（不是幂等成功）
```

⚠️ **预设三条都走命令通道**（连 `list` 也走）——与 `provider list` **刻意不同**，那条是
**控制台本地查询**。判据：**头只有一个入口**（命令 + 快照两层），没有第二套本地查询通道，
而头要用它做下拉。⇒ 结果走 `Ack.Accepted.Note`（同 `provider.test` 的用法）。

⚠️ **`preset set` 的 `content` 是必给字段**（`GetProperty`，不是 `Opt`）：空串是**合法值**
（= 纯聊天），而「没给」只可能是发命令的程序写错了——用 `Opt` 会把两者并成同一个 `null`，
于是「我要纯聊天」变成一条含义不明的命令。

⚠️ **`cwd` 与 `title` 是 2026-10-05 加的**（原文只有 `projectKey?` / `preset?`）：
- `cwd` = 新会话的**工作目录**，而工作目录**决定它落在哪个项目**（`ProjectKey.FromPath` 是纯函数）
  ⇒ 「选项目」与「选工作目录」在核心侧是同一件事。不给 ⇒ 回落核心的工作目录。
  **不存在 ⇒ 拒绝，核心不替你建目录**（建目录是策略，[`00` §1.3](00-设计哲学.md)）。
- ⚠️ **`projectKey?` 那一半没做，而且做不了**：键是从路径推出来的，**反向推不回去**；
  盘上唯一记着目录的地方是**会话的** `spec.json`，而一个项目可能一个会话都不剩（全删了）。
  那样的命令会**有时候**可用、其余时候报一句用户无从补救的错。头那边本来就有路径，直接交路径。
- `title` 只在建会话那一刻写一次，**此后没有任何命令能改它**（所以也没有 `session.renamed` 事件）。

⚠️ **`archive` 的 `archived` 是三态**（`bool?`）：缺省 = 归档、`false` = 取消归档。
**线上解析只认 JSON 的布尔字面量**——字符串 `"false"` 会被当「没给」⇒ 归档（刻意的取舍，
见 `ControlServer.OptBool`）。⚠️ 别把它写成 `bool archived = false` 那种带默认值的形状：
那会让每一个「只写了归档」的调用点**静默变成取消归档**，而这条命令没有别的测试拦得住。

⚠️ **三条销毁命令都拒绝「正在跑」的会话**（`Rejected`，不是原地掐断）。完整理由见 [`01` §8](01-会话设计.md)。

⚠️ **`session.deactivate` 会切出一个读盘窗口**：会话被摘出内存之后，一个**还在跑**的会话
（头那一侧看着还是「在跑」）若被重拉快照，会落到磁盘那份 **`Idle`** ⇒ 用户以为没在跑、
再点一次发送 ⇒ 队列两条 ⇒ **烧钱**。⇒ 快照端点在激活表 miss 时**必须回落 `Activate`**
（`ControlServer.TryFind` 与 `SessionQueries.StateOf` 的调用方都写了这一条），不许直接交磁盘那份。

# 推进
session.send(sessionId, blocks)      # 用户消息（块列表，见本文件 §9）= 入队 + 启动
session.start(sessionId)             # ⚠️ 启动（[`01` §6.1](01-会话设计.md)）——步进档唯一的前进方式
session.interrupt(sessionId)         # 停当前推进
session.continue(sessionId)          # ⚠️ 与 `start` 同义，保留别名（`01` §6.1 只有「启动」一个概念，没有「续跑」）

# 行为控制（六轴，见 [`01` §3.5](01-会话设计.md)）
session.setAxis(sessionId, axis, value)

# 会话的模型选择（换绑供应商 / 换模型）
⚠️ **`session.configure(sessionId, providerId?, modelId?, askTimeoutMinutes?)` 不在原设计表里**（2026-10-05 新增）。
三个字段都可空，语义是「没提到 = 保留」（与 `provider.upsert` 同构）；都没给 ⇒ rejected。
它补的是一个**设计好的落点缺的另一半**：`provider.delete` 刻意不阻止删除被引用的提供商，
于是「会话绑的提供商没了」是可预期的——而此前**没有改绑的办法**。
⚠️ `askTimeoutMinutes` 是 2026-10-11 加的（同 `session.create` 那一格，必须 > 0）。
⚠️ **「取消超时」今天没有入口**——字段是 `double?`，而「没给」与「给了个表示取消的值」
在这个形状下分不开（本仓那条「一个值承担两种含义」的老毛病）⇒ 如实记着，不发明
一个 `--ask-timeout none`（那会让 `none` 与「没给」长得一样）。

# 权限闸门
approval.respond(sessionId, askId, outcome, answers?, remember?)
⚠️ **`answers.decision`**（`"allow"` / `"deny"`）是核心判「批没批」的**唯一**依据
（2026-10-11 显式化：头原先从这一格整个漏了，而控制台一直在发 ⇒ **在头上点批准落成拒绝**）。
`remember`（`"args"` / `"tool"`）只决定**粒度**——批准本身**无条件写一条「这一次」的记忆**。
                                     # outcome: submit | cancel | modify
                                     # answers: 问题 id → 答案（submit 时允许缺项）
                                     # remember: args | tool（省略 = 只这一次）
                                     # ⚠️ **挂起会话的唯一解除入口**——`session.send`
                                     #    撞上 WaitingForInput 会被拒（两条路都能解除 ⇒ 判据漂）
# 资源
claim.release(sessionId, scope)      # 头强制释放（模型失控时的逃生口）
                                     # ⚠️ 清单查询走 GET /claims（§6），不做 claim.list 命令
                                     # ⚠️ **它不写时间线**（2026-10-11 明确）：摘锁是逃生口，
                                     #    与「我说这批资源用完了」是两件事。模型侧那个 `release`
                                     #    工具才画线（01 §12.4）——两者今天并存，只有后者触发回收。

# 配置
provider.upsert(...)
provider.delete(id)                  # ⚠️ 不存在 / id 不合法 ⇒ rejected（**不是幂等成功**：拼错一个 id 若回 ✓，用户以为删了）
project.setConfig(...)
tool.setEnabled(...)
```

⚠️ **`interrupt` 与 `deactivate` 必须分开** —— 这是 [`01` §2](01-会话设计.md)「停推进 ≠ 停会话」在接口上的样子。同理 `deactivate` ≠ `archive` ≠ `delete`。

**回执只有两类**：`ack(id)` / `rejected(id, reason)`。`rejected` 用于**命令本身不合法**（会话不存在、轴取值非法），**不用于业务结果**。

session.deactivate · session.archive · session.delete · session.gc
preset.set · preset.list · preset.delete
claim.release · approval.respond · provider.upsert · provider.delete · provider.test
```

| `blocked` | [`01` §5](01-会话设计.md) Blocked | 实现里**到不了**该状态：`State.Status` 只被写 `Idle` / `Running` |

> ⚠️ **未上线的那些，多数等的不是「一条事件」，是一个子系统**（工具面 / 附件 / GC / 子会话）。把它们逐个补成空壳事件**没有意义而且有害**——头会画出永远不动的面板。

> ⚠️ **已上线的那些里有一条是死投递**：`session.created` 按本表发到**项目流 + 会话流**两份，
> 但今天只有**项目流**那份被消费（`src/Lilara.Head/wwwroot/app.js`）。会话流那份**没有任何消费者**——
> 头要等 `ack` 拿到 `sessionId` 才会去订 `session:<id>`，那时 `session.created` 早发完了。
> 两份是**两个命名空间**，不是两个收件人。

**每个事件带 `seq`**（流内单调增）+ `sessionId`（会话级流上的事件额外带）。

### 4.1 关于流式输出

⚠️ **流式是一个标志，不是一套机制**（[`01` §11.9](01-会话设计.md)）：

- **流式期间模型输出只存在于内存，不落盘**——步是持久化的原子单位，而前缀在**步的中间**本来就不可用（要构造请求必须先知道完整输出）
- `term.delta` 是**转发**，不是记录
- **步结束才合并成一条完整模型消息并落盘**——那才是唯一的事实
- ⚠️ **不支持断线续传**：重连时只能拿到已完成的，未完成的那一步**尚不存在于记录里**。这不是缺陷，是"事实不可变"的必然

唯一留给头的策略：**半截文本立刻显示** vs **取完整块后一次显示**。核心两种都支持，只负责把增量转发出去。

### 4.2 载荷的形状

> ⚠️ **真相来源是代码，不是本节。** 本节是**人读的摘要**；线层的**权威**是
> `src/Lilara.Core/Control/WireEvent.cs`（类型与判别式）+ `WireJson.cs`（序列化设置）+
> `WireFormatTests.cs`（闸）。**三家不一致时以那三处为准**——本节会腐，它们会红。

**所有事件共有的形状**（`WireFrame.Event` 是信封，`WireEvent` 是载荷）：

```json
{ "kind": "event", "topic": "session:s1", "seq": 42,
  "payload": { "kind": "session.step.begin", "sessionId": "s1", "turn": 3, "at": "..." } }
```

| 事件 | 载荷字段 |
|---|---|
| `session.created` | `sessionId` · `projectKey` |
| `session.step.begin` | `sessionId` · `turn` · `at` |
| `session.step.end` | `sessionId` · `turn` · `refused` · `stopReason` |
| `message.appended` | `sessionId` · `from`（`user` / `model`）· `blocks` · `at` |
| `session.state` | `sessionId` · `status` · `turn` |
| `axis.changed` | `sessionId` · `axis` · `value` |
| `spec.changed` | `sessionId` · `model`（`providerId` / `modelId` / `protocol` / `effort` / `maxTokens`）· `systemPromptPreset`（可空） |
| `session.deactivated` | `sessionId` · `projectKey` |
| `session.archived` | `sessionId` · `projectKey` · `archivedAt`（**`null` = 取消归档**） |
| `session.deleted` | `sessionId` · `projectKey` |
| `claim.acquired` / `.released` | `sessionId` · `path` |
| `approval.requested` | `sessionId` · `askId` · **`askKind`**（`"permission"` / `"question"`，小写——线上枚举一律 camelCase）· `items` · `remember` · `deadlineAt`（可空 = 不超时） |
| `approval.resolved` | `sessionId` · `askId` · `outcome`（`submit` / `cancel` / `expired`） |
| `error` | `sessionId` · `message` |

**帧（信封）有三类**，判别式同样是 `kind`：

| 帧 | 字段 |
|---|---|
| `event` | `topic` · `seq` · `payload` |
| `ack` | `id` · `accepted` · `sessionId?` · `reason?` · `note?` |
| `resync_required` | `topic` |

**块**（`message` 与 `message.appended` 都可能带）：`text`、`reasoning`（`reasoningKind` · `text` · `signature?`）、`toolUse`（`callId` · `name` · 原文 `arguments`）、`image`、`store`。工具结果不是块，而是独立的 `toolResult` 历史项（`callId` · `blocks`）。

**历史项身份**：`/history.rendered` 的每一项带 `id`，它是 `TimelineEvent.Id`；`toolUse.callId` 只用于和对应的 `toolResult.callId` 配对，不能替代历史项 `id`。`message.appended.historyId` 在持久消息上复用同一记录 id，头按它去重；没有持久 id 的事件不得假定为历史记录。

**历史分页**：

```text
GET /sessions/{id}/history?limit=50
GET /sessions/{id}/history?limit=50&before=<opaque-cursor>
```

缺省取最新一页，`limit` 当前限制为 1..200；`before` 取游标之前的更旧项。响应保留 `highWater`，并增加 `hasMore` 与 `nextCursor`；`highWater` 是 WS 订阅游标，`nextCursor` 是历史游标，二者不能混用。游标由核心生成，头不得解析或自行拼接。返回项按时间正序排列，头加载更早记录时向时间线顶部插入。

分页发生在核心完成解引用、回收替换、framing 和内部事件过滤之后；第一批只减少响应和头侧内存，核心仍可能扫描完整记录。折叠/展开是头的视图状态，不写入会话记录。

⚠️ **当前头可展示的详情**：思考块默认可折叠；工具调用显示原始参数；工具结果通过 `callId` 配对并可折叠。`reasoningKind:"redacted"` 只显示隐藏状态，不能把 `signature` 当正文。大工具结果的单项懒加载端点尚未实现，`store` 块仍按库引用语义显示。

⚠️ **快照的形状（§6 各端点）本节不展开**：端点不止两个，而本节此刻只在核对时读了 `/sessions/{id}/state` 一个，**没穷举**。要列的是**全部**端点（含 `/axes` · `/queue` · `/claims` · `/providers` · `/provider-schema`），**逐个核对后再写**——半份清单比没有更坏：头会以为某端点不在。

## 6. 快照 / 查询（HTTP，一次性）

⚠️ **补充（2026-10-12 打断批）——「在内存里」与「有东西在动」今天同延，而那是本批的形状**：

## 8. 头的状态处理

| 层 | 谁保持 | 怎么更新 |
|---|---|---|
| **真相** | 核心 | —— |
| **视图** | 头 | 事件增量更新 |
| **重建** | 头 | 快照 + 游标重放 |

> **头从不假设自己是最新的。** 这和"核心不关心头在不在"是同一条判据的两面。

### 8.1 控制台：没有视图的客户端

核心自带一条**命令面**（标准输入，[`04` §1.1](04-插件与内部结构.md)），**不是另一套接口**——它与头**走同一条命令通道、同一个命令集（§3）、同一个回执**。

⚠️ **它减掉的只有一件事：视图。**

```
头    = 观察者 + 命令源        （[`00` §1.1](00-设计哲学.md)）
控制台 =        命令源         ← 就是减掉观察者的头
```

| | 头 | 控制台 |
|---|---|---|
| 命令 | 全部（§3） | ⚠️ **除 `session.start` 外**（见下） |
| **事件** | 订阅 + 游标 | ⚠️ **不订阅任何流**（本文件 §5） |
| **快照** | 视图增量更新 | ⚠️ **只按需拉取**——"检查消息"就是拉一次快照 + 分页拉历史 |

> ⚠️ **实现（2026-10-05）**：上表说的是「命令 = 全部（§3）」，而控制台**够不到 `session.start`**——
> `CoreCommandParser` 只认 `session create / activate / interrupt`，没有 `start` 规则。
> 敲 `session start x` 会落到 `(null, null)`，被 `Repl` 当成**普通消息发给模型**。
> （其余「命令」一列今日一致。）
>
> ⚠️ **2026-10-12 打断批已补上**（`session start <id>`）。而缺它这件事**不只是「少一条命令」**：
> 它正是**唯一**能在「崩在步中」之后把那个会话收回来的命令（那时队列是空的，`send` 用不上）
> ⇒ 缺了它，`01` §12.8 那个洞在控制台上是**关不上的**。
> ⚠️ 而「敲它会变成一条消息」与别的「掉进 `AsMessage`」同形——**静默**，且**烧一次模型调用**。

> ⚠️ **控制台还有几条「本地查询」，它们**不是**命令**（2026-10-11 补）：`history` · `status`
> · `claim list` · `provider list` · `session list` · **`fetch &lt;id&gt;`**。
> 判据是**它们只读**（拉一次快照 / 读一次存档），而 §1 那条「HTTP 只读、改走 WS」的边界分的是**写**。
> ⇒ 它们不走命令通道，也就**没有 ack / 事件 / 四条线**——那是**对的**，不是欠账。
> ⚠️ 而 `fetch` 是其中**唯一带参数**的一条：控制台看的 `history` 与模型看的是**同一份渲染**
> ⇒ 它也会看见 `[已回收] … fetch(id="…")` 注记。看见一个地址却够不着它，
> 是这条链上最后一处只写了一半的地方（[`01` §8.0.2](01-会话设计.md) 九节之末）。
> ⚠️ **它认的是记录 id**（注记里给的那个），与模型那条**同一份语义**：读 `store/&lt;sha256&gt;` 原样交回。

**所以本节的三层，控制台只用两层**：命令（本文件 §3）+ 快照（本文件 §6）。**本文件 §4 事件与 §7 游标对它整体不适用**——那不是它"遵守"约束，是**它没有能挂住游标的地方**。

> 「命令投递即返回」在本地退化成**同步拿回执**（都在内存里）；协议语义不变，只是等待被物理地抹平了。

⚠️ **它存在，是因为头不该是唯一入口**：止血（`interrupt` / `claim.release` / `approval.respond`）与引导（`provider.upsert` / `session.create`）恰恰发生在**头最指望不上**的时候。

## 9. 附件与文件

### 9.1 两步：上传与发送

```
# 1. 上传（HTTP，不走命令通道）
POST /files?sessionId={id}&path={可选}  →  { ref }

# 2. 发送（WS 命令，只带引用）
session.send(sessionId, blocks: [
  { type: "text",       text: "看看这个" },
  { type: "attachment", ref }              # 或 { type: "file", path } 直接引用工作区（见本文件 §9）
])
```

**两步分离的收益**：

| | |
|---|---|
| 大字节不过命令通道 | 命令永远小、可重放 |
| **上传幂等** | 内容寻址 → 重复上传返回同一对象，**天然去重** |
| 可重试 | 上传失败重传，不会重复发命令 |
| 可复用 | 同一张图发给两个会话，只传一次 |

**粘贴 / 拖拽是头的职责**：先 POST 再 send。**核心不需要知道剪贴板存在。**

### 9.2 路由：按提供商的模态声明

> ⚠️ **客户端永远是"上传 + 发指令"两步，与类型无关。** 分岔在核心。

| | **库** (`store/`) | **工作区** (`.lilara/inbox/` 等) |
|---|---|---|
| 盛放 | **多模态兼容内容**（图片 / 协议支持的 PDF） | **其余一切**（zip / 大 csv / 代码） |
| 模型看到 | **就是那张图本身**（协议原生块） | **一个普通文件路径**，走工具处理 |
| 模型知道 | ⚠️ **无机制、无 id、无来源——压根不该意识到库存在** | 文件系统（它本来就知道） |
| 生命周期 | 内容寻址 + 引用计数 | [`01` §12](01-会话设计.md) 声明 + [`00` §5](00-设计哲学.md) 指纹（全套现成机制） |

> **库面向「模型的眼睛」，工作区面向「模型的手」。**
> **眼睛看的东西不需要名字；手要操作的东西必须有路径。**

**判据 = 提供商配置里的模态能力声明**（配置提供商时选择），核心**不维护"哪些格式能喂"的清单**。

- ⚠️ 副作用要认：**同一文件发给不同协议的会话，可能落进不同地方** —— 目的地由"**它将被如何消费**"定义
- ⚠️ **路由结果必须可见**（头要显示"进了工作区，路径是 X"）
- ⚠️ **不给"文本类小文件直接内联"开绿灯** —— 内联会**绕过工具结果的全套机制**（[`00` §5](00-设计哲学.md) 的指纹与优化、[`01` §11.3](01-会话设计.md) 的保护带、[`01` §12.7](01-会话设计.md) 的脏指示）。判据不是"是不是原生模态"，而是**能不能不绕过这套机制**

#### ⚠️ 换提供商之后：已记录的内容怎么办（2026-10-06 补的缺口）

⚠️ 上面那条只管**入口那一刻**（这个文件该进库还是进工作区）。而**全仓原先没有一条**写「**provider 换了之后，盘上已有的内容怎么办**」——而 `session.configure` 今天就能换绑定。

**症状**：一个当初在「认图像」的提供商下录进去的图片块，**换到纯文本的提供商之后，上游会拒**。

> **对策：渲染时按块降级。** 提供商不吃图 ⇒ 该块渲染成一个占位。

⚠️ **它复用「渲染的额外输入」那一族，不新增机制**——与 `now`（[`01` §3.2](01-会话设计.md)）、**快照可用性**（[`01` §8.0.2 §4](01-会话设计.md)）同形：都是「**渲染时才知道、而且不进记录**」的外部事实。

⚠️ **会破前缀——但那一刀是免费的**：换提供商**本来就要全破**（[`00` §0](00-设计哲学.md)：换模型 = 前缀全废）。

⚠️ **为什么不在入口就拦死（比如「拒绝给已含图片的会话换提供商」）**：那是**策略**，而且用户**无从补救**（他不能把已经录进去的图删掉）。渲染期降级让**数据留着、只是暂时看不见**——换回去就回来了。

### 9.3 工作区上传

- **路径**：客户端可指定；不指定则核心给默认落点（`.lilara/inbox/`）
- ⚠️ **上传是一条事件**（`workspace.file.added`）—— 这是"世界变了"，会话该收到**脏指示**（[`01` §12.7](01-会话设计.md)）
- ⚠️ **不受 [`01` §12](01-会话设计.md) 约束** —— 头往工作区写文件就是"**人类编辑**"那一格（[`01` §12.6](01-会话设计.md) 已认下的洞），**不新增机制**

### 9.4 库的访问

- `GET /store/{sha256}` 取字节（头显示用）
- ⚠️ **只读**（[`01` §8.4](01-会话设计.md)）—— 不可变 → **结构上排除冲突**，不受 [`01` §12](01-会话设计.md) 约束
- ⚠️ **模型侧没有任何库接口** —— 原生块直接渲染内容，模型看不到 id（"记录是骨架"在二进制上的样子）
- ⚠️ **但头侧有** —— `GET /store/{sha256}` 就是头的取字节通道；**"模型不该意识到库"与"头必须能显示"是两回事**（对应 [`01` §3.4](01-会话设计.md) 的**托管载荷**）

## 10. 刻意的取舍

| | |
|---|---|
| **不做请求 / 响应配对**（除查询） | 一旦有 RPC，头就会开始阻塞，头核分离就破了 |
| **命令粒度 = 一次操作**，不是事务 | 多步操作由头串起来，或由插件做成一条命令 |
| **鉴权最小** | 核心是本设备唯一的，本机进程即可信。**默认只监听本机** |
| **核心不做转码** | 缩放 / 换格式会改变用户给的东西 —— 那是策略，归插件。核心给明确理由的拒绝 |
| **大小限制在入口就拒** | 上游协议有硬上限，**不要等到模型调用失败**（早失败） |
| **孤儿对象** | 上传了但没 send → 靠引用计数 + 清理功能收掉（[`01` §8.4](01-会话设计.md)） |
