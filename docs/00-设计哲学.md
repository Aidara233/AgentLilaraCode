# 设计哲学

本文是 AgentLilaraCode 的**母原则**。所有具体设计都是这些原则的反复应用；遇到新问题时，先回到这里找判据。

---

## 0. 母原则：前缀稳定性

上下文是**逐字节**喂给上游的，而所有缓存（核心侧提示词缓存、上游侧 Responses 链）**只认前缀**——改第 N 位，N 之后全废。

> **"尽量别动前面的内容"不是优化建议，是宪法。**

由此，所有失效触发源坍缩成**同一个事件**：

| 表象 | 实质 |
|---|---|
| 提示词缓存过期 | 前缀失效 |
| Responses 链断 | 前缀失效（上游那份） |
| 换模型 / 换上游 / 换协议 | 前缀失效 |
| 闲置超时 | 前缀失效 |

**前缀失效 = 唯一的冷启动时刻 = 唯一的免费改写窗口。**

系统的全部经济学可以压缩成一句话：

> **平时克制以保前缀，失效时放肆以还债。**

## 1. 三个分离

### 1.1 头核分离 —— 核心不关心头在不在

头是**观察者 + 命令源**，不是执行路径的一部分。

- 命令**投递即返回**，执行结果以**事件**形式从另一端流出（绝不 RPC 式阻塞）
- 核心离线期间照常干活；头重连后按游标补齐
- 需要的不是"响应"，是**可续订的事件流**

副产物：**"卡住"必须是一等状态**（等决策 / 等外部 / 故障退避），且持久化——否则"头中途离线"接不上。

### 1.2 数据与行为分离 —— 会话是聚合物，不是对象

> **会话 = 提供商配置 ⊗ 结构化记录**

两半都是**数据**，行为发生在发请求的那一刻。推论：

- **换模型 = 改会话的配置部分**，不是旁路 override —— 所以历史自然延续
- 记录里没有"消息对象"，只有块

### 1.3 机制与策略分离 —— 谁的知识谁负责

| 层 | 提供 | 例子 |
|---|---|---|
| **核心** | 机制 | 事件、持久化、指纹原语、回收窗口 |
| **插件** | 策略 | 提供什么工具与提示词、渲染成什么块、何时优化 |
| **适配器** | 协议怪癖 | 增量、链状态、重传、错误分类 |

**"谁知道脏"的答案是：谁都不需要全局知道。** 知识待在知识所在的地方。

## 2. 上下文哲学

### 2.1 记录不是转录，是骨架

落盘的是**不可再约的事实**，不是字面文本。可替换的内容以**引用**存在，请求时**现场解析**。

```
会话(配置 ⊗ 骨架记录)
      │  解析引用 → 渲染
      ▼
  canonical（一次性中间物，不落盘）
      │  按配置的协议类型转换
      ▼
  Claude Messages / OpenAI Chat / OpenAI Responses
```

**canonical 是渲染产物，不是存储格式。** 它只在请求路径上短暂存在。

### 2.2 内容的分类

| 类别 | 内容 | 持久化 | 渲染位置 | 插件用途 |
|---|---|---|---|---|
| **系统提示词** | agent 能力、全局约定 | ❌ | 最前 | 能力说明 |
| **首要提示词** | 人设、项目约定、预设 | ❌ | 紧随其后 | **人设注入** |
| **历史消息** | 用户/模型消息 | ✅ | 中段 | —（雷打不动） |
| **工具调用结果** | 见本文件 §5（**引用 + 快照 + 指纹**，三件） | ⚠️ **骨架**（引用 + 指纹）✅ 永久；**快照**❌ 可回收（本文件 §4 的头号可回收物） | 中段 | — |
| **浮动上下文** | 态势、策略、模式 | ❌ | **永久尾部** | 附加临时消息 |

**这套分类有三重身份**：持久化策略 · 渲染位置 · **插件 API 的表面**。插件不写"往数组塞一条"，而是**选一个语义化的缝**——选缝即选定生存期和成本，插件作者不做生命周期管理。

**内容全部由插件提供**——**含系统提示词**，核心自带零内容（[`04` §1.3](04-插件与内部结构.md)）；**装配机制归核心**（本文件 §1.3 机制与策略分离）。推论：

⚠️ **块数恒定。** 无论多少插件贡献，**协议看到的块数固定**——系统提示词 1 块、首要提示词 1 块、浮动 1 块，多个插件的贡献**自动拼合**。否则块结构随插件数漂移，缓存断点与位置语义全部跟着动。

> **块边界 = 缓存断点 = 失效爆炸半径的边界。** 该一起失效的东西，才进同一个块。

推论：**能进工具描述的，绝不进系统提示词。** 工具描述与工具同生共死、随核心版本发布、不会被 fork 掉；系统提示词只留**没法挂在单个工具上的全局约定**。与本文件 §7 判据 5 同源。

> ⚠️ **这句话改过一半**（2026-10-07）。原文后半是「系统提示词是**可替换内容**」——那句是拿
> **首要提示词**的性质去说**系统提示词**，而两块的可写面是**不对称**的（[`01` §3.1](01-会话设计.md)）：
> **系统块是核心提供的恒定单文件，插件不可注入**；插件贡献一律进首要块。
>
> ⚠️ **理由不在这场辩论里，在「谁来 fork」这件事上**：系统块的失效半径是**整个变体**
> （所有挂这个预设的会话），而**用户 fork 掉一个插件自己的提示词，只影响他一个人**。
> ⇒ **系统块里一句被 fork 的话，是整个变体在承担；首要块里被 fork 的，只废 fork 者自己。**
> ⇒ **越低风险的东西，越该允许被 fork**——而「全局约定」恰恰是**最坏情况影响最广**的那一类。
>
> ⚠️ **这不是把 forks 挡在外面**：系统块本身**可删、可换**（预设的一个字段），用户仍然能定制整块
> ——只是**插件不能替他定制**。区分是「**谁**能改这份共享字节」，不是「**能不能**改」。

### 2.3 挥发度梯度

| 区 | 块数 | 变更频率 | 缓存命运 |
|---|---|---|---|
| **系统提示词** | 恒定 1 | 核心版本 / 用户改那个文件 | **同变体**共享前缀 |
| **首要提示词** | 恒定 1 | 项目 / 用户配置 | **本项目内**共享 |
| 时间线 | 增长 | 只追加 | 前缀稳定，全缓存 |
| **浮动块** | 恒定 1 | **每步** | **永不缓存，每步全价** |

> **挥发度决定归属。** 头放"永远为真"，中段放"发生过"，尾放"此刻为真"。

**两级头槽位的分野**：

| | 回答 | 随谁走 | 改一次的爆炸半径 |
|---|---|---|---|
| **系统提示词** | 「你是什么、能做什么」 | 核心（与工具表一一对应）；**插件不可注入** | **同变体**（挂同一份系统提示词的会话） |
| **首要提示词** | 「你要怎么做」 | 用户 / 项目 / 插件 | **只废本项目** |

这就是"首要提示词地位稍弱"的本体——**它的爆炸半径小**：同变体 vs 本项目。

⚠️ **「全设备」改过**（2026-10-07）：那**预设了所有会话位置 0 相同**，而系统提示词现在是
**可按会话选**的（预设的一个字段，见 [`01` §3.1](01-会话设计.md) / §7.1）⇒ 改为**按变体分片**。
两套完全不同任务的提示词本来就不该共享位置 0——那里省下的缓存换不来答对。
⚠️ **「不能进头的东西」这条判据一个字没动**（每步在变的仍然不许进，见 [`01` §3.1](01-会话设计.md) 那张表）。

⚠️ **系统提示词是纯建议层。** 核心对它说的每一句都有机械兜底：该用哪个工具 → 工具表 + `tool_choice`；大工程前先声明 → 声明本就是 opt-in；上下文长了要压缩 → 阈值兜底。**用户把它换成别的、或者干脆留空（纯 chat 预设），系统不会坏，只会降级。**

### 2.4 浮动上下文 = 槽位，不是消息

> **"水面" —— 永远在最后。**

- **替换而非追加** → 成本恒定、内容永远新鲜、**不累积**
- 位置在尾部 → 替换它不破坏前缀
- 省 token 的机制：同一信息，注入列表会堆 N 份，注入槽位**永远是 1 份**
- **可降级**：开关切换为普通上下文（每步追加），用于 Responses 这类"链不可逆"的协议
- **但降级 ≠ 放弃清理** —— 降级只改刷新方式，**清理仍由失效窗口统一执行**

> 降级 = 用 token 换缓存；浮动 = 用缓存换 token。**两者语义等价，只是性能曲线不同。** 所以这是个**纯粹的旋钮，不是正确性开关**。

开关取值：`Auto`（按适配器能力） / `Always` / `Never`。⚠️ `Always` 在 Responses 上会持续破缓存，应禁止或告警。

**`Always` / 降级的代价 ∝ 浮动体积** —— 每步追加一份、"永远 1 份"的前提没了。所以浮动是**状态栏，不是倾倒场**（本文件 §2.5 的硬约束 1）。

**归位规则**（[`01-会话设计.md` §12.7](01-会话设计.md) 的推广）：

| | 去哪 |
|---|---|
| **状态**（"是"什么） | **槽位** |
| **事件**（"发生"了什么） | **时间线** |

**状态天然可被覆盖，事件天然不可变**——正好对上两个位置的性质。插件问"我这条东西该放哪"，答案就是这一个问句。

⚠️ **头与尾本不该出现同方向的内容**——出现了就是**归位错误**（把状态塞进头，或把恒定的东西塞进尾）。**拦不住，但看得见**：头的 UI 原样显示两个槽位，用户一眼认出"人设怎么出现在两个地方"。真出现时**以最新的为准**——recency 天然如此。

> **不要为此写"尾部优先"之类的硬规则，那会把归位错误合法化。**（见 §8.8）

### 2.5 浮动块的契约

**字段集，不是自由文本。** 贡献者提交 `(字段名, 值)`：

- **同名字段归并**而非拼接 → 三个插件都塞时间，不会变成三份
- **位置稳定** → 同名字段永远在同一处，模型学得会
- **可裁剪** → 按模式 / 预设决定显不显示
- 核心预留一组，插件用命名空间（`persona.mood`）

```
态势：时间 · 步数 · 用量
策略：主动性 · 权限 · 安全 · 验证强度
其他：<插件贡献>
```

> **尾槽位存在的真正理由：它是行为控制面板。** 「浮动上下文就是为了这一碟醋包的饺子。」见 [`01-会话设计.md` §3.5](01-会话设计.md)。

⚠️ **「给头看」≠「给模型看」。** 一条轴可以「有机械层 / 无」，也可以「进上下文 / 不进」——**两者独立**。思考强度（effort）两边都走极端（纯参数、零暴露）；安全与验证强度反过来（纯提示、全暴露）。

**两条硬约束**：

1. **有界。** 浮动块在时间线**之后**，而时间线每步都在长 → 它**永远不可能被任何缓存覆盖，每步全价支付**。**浮动块的每步成本 = 它的体积**，是全系统唯一一处"体积 × 步数"线性放大。
2. **可信来源。** 尾槽位紧贴生成，是全上下文**注入杠杆最高**的一点。只有插件 / 核心能贡献；**绝不把文件字节原样透传**——脏文件状态是"路径 + 哈希 + 时间"这样的**字段**，不是文件说了什么。

⚠️ **`now` 冻结在步开始。** 渲染是纯函数（本文件 §5 铁律 1），而"当前时间"不是纯输入：签名是 `render(贡献, now)`，`now` 在**步开始时取一次**并冻结，同一步内重复渲染必须逐字节相同。

⚠️ **浮动里的"策略"是告知，不是要求。** 它让模型**知道自己处在什么环境里**（"当前串行执行"），不是命令它怎么做——**真正的约束在机械层**（并发由核心定、工具表由核心定）。这与"能进工具描述的绝不进系统提示词"同源：**能进机械层的，绝不靠嘴说**。

## 3. 缓存经济学

| 模式 | 时机 | 纪律 |
|---|---|---|
| **热**（前缀完好） | 平时 | 落盘即写成简化形态；**绝不事后清理**（那会破坏前缀） |
| **冷**（前缀已失效） | 失效窗口 | **放肆手术**——前缀反正要重建，边际成本为零 |

> **能在写入期解决的绝不留到读期；必须留到读期的，攒到失效期一起做。**

## 4. 回收窗口 = 系统的 GC

**触发源是「事件」**——前缀失效是其中最常见的一个，但不是唯一：

| 触发事件 | 见 |
|---|---|
| **前缀失效**（过期 / 换模型 / 断链 / 闲置） | §0 |
| **主动压缩** | 它自己制造前缀失效，顺手打开窗口 |
| **资源释放** | §4.1 —— **事件驱动，不是主动请求**。⚠️ **扩张不算**（它不动内容，见 [`01` §12.3](01-会话设计.md)） |
| **激活** | 恢复即事件（[`01` §8.3](01-会话设计.md)） |

所有"可回收"的东西在此集中处理：

- 工具结果的快照
- 浮动上下文（含降级后堆积在上游的那些）
- 旧的首要提示词
- 适配器侧的上游链状态

> **任何"临时"的东西，都不要指望它自己消失；要有一个统一的失效窗口来收尸。**

⚠️ **「回收」与「压缩」不是两条线，是同一条线上的两种产物**（2026-10-11 补）：
线下放**地址**（注记 / `fetch`）叫回收，放**摘要**叫压缩。⇒ 它们**代价只付一次**，
**不要给两者各设一个触发点**——两个触发点 = 同一处失效被付两遍，而且两次之间内容还会漂。
完整形态见 [`01` §11.1](01-会话设计.md) 与 [`01` §12.4](01-会话设计.md)。

关键是：**降级 / 浮动 / 快照这些策略都只影响"过程中的 token 曲线"，收敛终点相同**——历史不会永久脏下去。

### 4.1 释放即回收：事件，不是主动请求

**"任务边界"是比"前缀失效"更早、更可控的窗口。**

文件系统是这个系统里最贵、最大、最易脏的东西。模型可以在开工前**主动声明独占**一片区域（见 [`01-会话设计.md` §12](01-会话设计.md)），任务完成时释放。

⚠️ **但注意因果方向：模型做的是「释放资源」，GC 是这件事引发的「事件」。**

```csharp
if (释放集 ≠ ∅)  回收(释放集)      // 条件性的，不是 promise
```

- 模型**不需要理解 GC，只要正常释放**——做它本来该做的事
- **释放集为空时什么也不会发生**：整个工作集不在上下文里，就没有可回收的东西
- 所以「主动 GC 是收费的」这个顾虑**根本不成立**——**它不是主动的，是被触发的**

```
release(scope: [...], summary: "...")
          │             │
          │             └─→ 取代被清扫的字节 → 保留「知识」，扔掉「字节」
          └─→ 既是解锁清单，也是 GC 清单
```

它同时做三件事：**解锁** · **触发 GC** · **清理未改动的残留**。

> **`release` ≈ 作用域化的 `compact`。** 全局历史用 `compact`，本任务工作集用 `release`。
>
> **"保留知识、扔掉字节"** —— 摘要就是那个"记得"。

**为什么这依然不"超前"**：`release` 落在**任务边界**上——工作集在这里**真的是垃圾**。此时为保缓存留着它，等于为一批只剩缓存价值的内容永久付费。而且它**自我调节**：不在任务中段 GC，只在边界 GC；若不在此 GC，上下文继续膨胀，最终仍要压缩，**只是那时垃圾更多**。

**三种回收各司其职**：

| 场景 | 回收方式 |
|---|---|
| 随手改几个文件（未声明） | 被动 GC（前缀失效时） |
| **声明式大工程** | `release` → **事件触发** GC + 清理 |
| 历史太长 | `compact` |

**没有重叠、没有遗漏。** 而且"GC 只被**我明确宣告过的工程边界**触发"，比"模型可随时要求 GC"语义更清晰。

## 5. 工具观：工具是渲染器

工具不只是执行器，契约是**四个钩子**：

| 钩子 | 时机 | 返回 | 性质 |
|---|---|---|---|
| **执行** | 被调用时 | 副作用 + 记录 | 有副作用 |
| **渲染** | 构造聊天记录时 | `(块, 位置)` | **纯函数，绝不重执行** |
| **优化** | 回收窗口打开时 | **给出降级渲染** | 有损、**不写盘** |
| **取消** | 推进被打断时 | 清理在飞调用 | 见 [`01` §9](01-会话设计.md) |

⚠️ **「优化」那一格改过**（2026-10-06）：原文写「**改写自己的记录**」，读起来像**磁盘改写**，而裁定是「**GC 只处理注入，不处理持久化**」（[`01` §8.0.2](01-会话设计.md)）。上面那两行其实已经写对了（「优化掉必须落成**极简占位**」——**那句就是注记**），只是这一格在往反方向读。

⚠️ **它也不是一个新钩子**：`优化` 就是**「渲染」多了一个输入**（快照还在不在）。⇒ `渲染(结果, 快照可用性)`。
**决定性理由**：MCP 工具**只给得出执行**（下面那段），若回收行为是新钩子，**所有 MCP 工具都提供不出来 ⇒ 全都没法回收**。
⚠️ 而 **「恢复」连钩子都不需要**：取回 = 读 `store/<sha256>` **原样交回**（快照本身就是渲染产物，**重渲染不是恢复**）。

⚠️ **工具是插件的贡献，不是独立实体**——没有"工具注册表"这种东西，工具表是**派生**的（[`04` §1](04-插件与内部结构.md)）。

**工具调用结果 = 引用 + 快照 + 指纹**：

- **引用** —— 依赖什么（读了哪个文件）
- **快照** —— 上次实际喂给模型的**渲染产物**（不是文件原文）
- **指纹** —— 哈希，判断世界动没动

三态判定：

| 指纹 | 动作 |
|---|---|
| 一致 | 用快照（≡ 新值）→ **缓存不破** |
| 不一致 · 窗口已开 | 用新值 + 优化 |
| 不一致 · 窗口未开 | **抉择**：忍陈旧保缓存 / 牺牲缓存求新鲜 |

> **快照存在的唯一意义，是让你在"不想破缓存"时还有旧内容可喂。** 缓存一破，字节等同再也买不到任何东西——所以优化是**有损且不可逆的，而这不是缺陷**。

⚠️ **这张表的第三格，就是回收的「点杀」判据**（2026-10-11 补交叉引用）——
「这条结果过时了，换成注记」，与 [§11.1](01-会话设计.md) 的「线」并列，是**判据轴上的另一档**。

⚠️ **而它有消费者了**（2026-10-11）：`Reclaim.Stale` 重读那个源、重算指纹、与记录里那个比。
⚠️ **但它今天一条都收不动**——每一条结果都还在「最近 N 条」保护带里（见
[`01` §11.3](01-会话设计.md)）。⇒ 「谁写的」那件事**接上了**，「省到上下文」那件事**还没有**。
⚠️ **它不能住进渲染**：比对要碰文件系统，而渲染必须是纯的（下面铁律 1）——
⇒ 判定在渲染**外**算、作为输入传进来，见 [§12.7](01-会话设计.md)。

**三类工具结果**：

| 类别 | 例 | 指纹 | 可优化 |
|---|---|---|---|
| 可重演 | `read` / `list_dir` | 依赖源哈希 | ✅ |
| 外部易变 | HTTP / DB | ETag / version | ✅（可能自变） |
| **不可重演** | 执行命令 / 发邮件 / 取时间 | **无** | **❌ 永久保留** |

⚠️ **不可重演类还要冻结形态**：其渲染结果直接落成**「具体」载荷**，此后不再被重新渲染（[`01` §3.4](01-会话设计.md)）。否则**插件热重载会让已发出的邮件在上下文里改写**——这是"渲染必须是纯函数"的另一面。

**两条铁律**：

1. **渲染必须是纯的** —— 否则重建历史会**重发邮件**
2. **位置一次声明，不可每步变** —— 否则每步破前缀

**结构性红利**：工具记录是**一块的两面**（call / result 是同一记录的两半，由工具填充），所以**悬空不可能发生**——不是靠规则禁止，是结构上排除。

⚠️ 但"优化掉"必须落成**极简占位**，不能真的不显示（协议强制 tool_use / tool_call_id 配对）。

**MCP = 适配器插件** —— 与上游协议适配器**镜像**（一个入、一个出）。MCP 工具走**同一套**生命周期与权限类别；但 MCP **只给得出执行**——渲染 / 优化钩子不在 MCP 原语里，那部分走核心侧默认策略（[`04` §4](04-插件与内部结构.md)、[`04` §5](04-插件与内部结构.md) 的能力表）。

## 6. 协议适配：核心全量，适配器做减法

- **核心永远发全量 canonical**，压根不知道 Responses 为何物
- **增量、链状态、失败重传全部关在适配器里**
- **块 id ≠ 上游 id**：前者是记录内身份，后者是**适配器贴上去的外来键**，作为不透明元数据跟着落盘

**漂亮的统一**：Responses 的链**就是一个前缀缓存**。所以适配器侧的"链断"和核心侧的"缓存失效"**是同一个事件的两种表征**——落进同一个回收窗口。

适配器必须自己扛：链状态（丢了降级全量）· 错误分类（链断 vs 瞬时错误，混了会静默错乱）· 重试幂等 · `store:false` 识别 · 推理块逐字回传（含 `encrypted_content`，**永不可优化**）· 换上游 / 换模型时主动弃链。

## 7. 贯穿始终的判据

1. **前缀优先** —— 任何设计先问"会不会动前面"。
2. **知识与责任同处** —— 脏不脏问工具、协议怪癖问适配器、执行边界问头、**提示词问插件、装配问核心**。**没有全局裁判。** ⚠️ 脏不脏的**产生者**仍是缺口——见 [`01` §14](01-会话设计.md)。
3. **临时物由窗口收尸** —— 没有任何东西"自己会消失"。
4. **结构上排除，而非规则禁止** —— 好设计让错误不可能发生（如工具记录的两面性），而不是加一条禁令。
5. **意图靠工具表表达，不靠提示词请求** —— 想让模型只做 X，就把别的都拿走。工具表是硬约束，提示词是软请求。⚠️ 但改工具表是最贵的操作（Claude 协议下 tools 位于前缀最前端），**只该在冷窗口做**（§3 的失效窗口 / 压缩 / 释放 / 重载，都算）。
6. **单核心是进攻性优势** —— 核心是本设备唯一的，这不止是"避免竞争"，而是**天然持有统一调度权**。多 agent 的分布式冲突问题，在此降级成一次路径判定。

7. **分级保障：能防的防，能察的察** —— 不假装能防住一切。预防（写入前检查）覆盖可控范围，**检测（指纹）覆盖全域**，人类编辑与进程外改动**明说尽力而为**。声明管住的是"会话之间"，不是"世界"。

8. **能派生的就不要持久化** —— 持久化状态可以因为**与真相无关的原因**变化（重装、迁移、漂移、损坏），而**每一次这样的变化都是一次缓存失效**。派生值不会——**它只在其输入变化时变化**。这是本文件 §2.1「落盘的是不可再约的事实」应用到新位置：**顺序、指纹这类东西不是事实，算得出来就不该落盘**。⚠️ 由此，**指纹变了 ⇔ 缓存必然失效**——不是猜测，是同义反复（[`04` §7.3](04-插件与内部结构.md)）。

## 8. 已作废的设计

记录"为什么不做"，避免重蹈。

### 8.1 分层折叠（fold 套 fold）

曾提议用**覆盖层**做压缩（时间线上一个记录覆盖一段区间，渲染时以摘要代偿，可层叠）。

**作废**：压缩采用**加载边界**模型（见 [`01-会话设计.md` §11.2](01-会话设计.md)）——从最近的压缩记录开始加载，之前的根本不加载。更省、更纯粹，且绝对保住"事实不可变"。覆盖层还得维护"哪段被谁覆盖"，是自找的结构。

### 8.2 会话轮替（旧会话封存 + 新会话接续）

曾提议用会话轮替作为"增长的归宿"。

**作废**：同一个加载边界模型解开了"事实不可变 vs 必须缩减"的死结，且**省掉一整个会话实体的生命周期管理**。轮替方案还要求维护会话链（"会话"不是一段对话的单位，会话链才是），复杂度没必要。

### 8.3 显式 GC 的"标记 / 回收分离"

曾提议模型随时**标记**（零成本），核心在下一个免费窗口**回收**。

**作废**：`release` 已提供该能力的唯一有价值形态，且落在**任务边界**上（前缀代价被摊掉），粒度是整棵声明树。任务中段的细粒度标记是**微操**——为省一点上下文主动破坏前缀，不抵代价。详见 [`01-会话设计.md` §11.8](01-会话设计.md)。

### 8.4 「轮」这一时间单位

曾以「步 + 轮」为两个时间单位。

**作废**：持有轮的概念太麻烦，且优化/回收的触发点本来就只靠前缀失效。**「步」是唯一的时间单位。**

### 8.5 「实例」这一术语

曾用"实例"指"可能多开的程序"（如两个 Claude Code）。

**作废**：核心是本设备唯一的，不存在多开。只保留 **核心** 与 **会话** 两个名词。

### 8.6 ALP 的端口权重激活

曾考虑沿用 ALP 的 `IInputPort.Weight`（mention=100 立即 / normal=5 攒满 100）。

**作废**：那是"消息攒够才唤醒"的频道中断模型，来自 QQ 场景。本项目用**事件驱动的显式唤醒**替代。

### 8.7 横向会话通信（平级注入）

曾考虑给平级会话之间开一条投递通道（"互相通气"）。

**作废**：三个理由——

1. **注入权背后没有责任关系支撑。** 父注入子是对的（父能停子、父在等汇报，权威有来源）；平级注入则**接收方无法区分「对方真的知道」和「对方被它读到的脏文件骗了」**——这是 prompt injection 的横向版本，而纵向注入天然免疫。
2. **它架空可见性。** [`01` §13](01-会话设计.md) 已认下"语义冲突无法自动消解，只能靠头的可见性让用户看见"；A、B 私聊则共同父瞎了。兄弟间通信的正确形态是**上提到父**。
3. **频繁横向通信是架构异味的信号**——需要频繁同步 ⇒ 信息本该同源 ⇒ 当初为什么分开？

**替代**：**脏指示就是免费的横向通知**（[`01-会话设计.md` §12.7](01-会话设计.md)）——通知**不携带内容，只提示「去读」**，接收方保留判断权与时机选择权，**前缀一根毛都不动**。

⚠️ 不堵路：注入原语本就是通用的，横向放开只是**权限层的放宽**，不是架构改动。

### 8.8 「尾部优先」的提示词优先级规则

曾提议在内置提示词里写死"尾部浮动信息与本文冲突时，以浮动信息为准"，以消除头尾冲突。

**作废**：头尾本就**不该出现同方向的内容**——冲突是**归位错误，不是优先级问题**。写一条优先级规则等于**把归位错误合法化**。真出现时 recency 天然让最新的赢，无需规则；正确做法是让它**看得见**（头的 UI 原样显示两个槽位）。

### 8.9 插件自带 UI

曾考虑允许插件向头提供 UI（注入代码或自定义渲染）。

**作废**：**UI 全是头的事**（本文件 §1.1 头核分离）。真要做定制 UI 得与头单独协商——**不划算**。

**替代**：插件**声明「控制点」（数据）**，头**通用渲染**（按钮 / 下拉 / 开关）。"插件提供按钮"存在于**声明层，不存在于代码层**（[`04` §3.1](04-插件与内部结构.md)）。

### 8.10 「只能追加」的排序键（安装序号）

曾提议用 **(优先级, 安装序号)** 排序，靠"新插件拿最大序号 → 只能追加、不扰动既有顺序"来保前缀。

**作废**：这个场景**实际上不存在**。

1. **工具表在 system 之前** —— 往后塞一个工具，工具表那段是保住了，**可它后面的 system 块和全部历史全被顶掉**，而 system 才是重的那个
2. **插件贡献本来就是多面的** —— 一个加工具的插件**几乎必然也往系统提示词里塞一段说明**，那位置 0 直接炸

于是"只能追加"**买到的是一小段工具定义，丢掉的是整个系统提示词**。而代价是一个**持久化的计数器**——正是判据 8 要避免的东西。

**替代**：排序键退回纯函数 `(priority, pluginId)`，**不持久化**。既然插件变化本来就全炸（`01` §3.1：变更时机 ⊂ 已经要失效的时机），追求"无扰动"就毫无价值。⚠️ 由此，**"不能按插件名排"这条也一并作废**——扰动的代价是零。
